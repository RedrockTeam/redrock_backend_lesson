# 第五节课：Etcd

## 0. 本课目标

了解raft算法的原理。

掌握 Go 微服务中服务注册、服务发现的核心流程。

掌握怎么将Etcd作为分布式配置中心。

了解四种负载均衡的策略。

## 1. 为什么需要服务注册 & 服务发现、配置中心？

### 1.1. 单体架构 vs 微服务架构

#### 1.1.1. 单体项目

所有代码写在一个项目里：用户服务、订单服务、商品服务全在一起。

服务之间调用：本地方法直接调用，不需要网络、不需要地址；

缺点：耦合严重、改一点就要全量发布、无法单独扩容、容错差。

#### 1.1.2. 微服务项目

项目拆分成多个独立部署的小型服务：

用户服务、订单服务、支付服务、商品服务、库存服务独立部署、独立扩容、独立迭代；

服务和服务之间，必须通过网络跨进程远程调用（HTTP/gRPC）。

一旦拆成微服务，会出现两个核心难题：


1. 服务通信问题：A 服务怎么找到 B 服务？
2. 配置管理问题：所有服务的公共配置、动态参数如何统一管理、实时更新？

这就是服务注册发现和配置中心要解决的两大核心问题。

### 1.2. 没有「服务注册发现 + 配置中心」会发生什么？

#### 1.2.1. 微服务通信痛点（无注册发现）

场景举例:订单服务需要调用商品服务查询商品信息。

方式 1：硬编码写死 IP + 端口

```go
// 代码里写死 goodsAddr = "192.168.1.100:8080"
```

致命问题：


1. 地址写死：服务换服务器、改端口、容器重启 IP 变化，代码必须改、重新打包发布；
2. 无法扩容：商品服务要部署 3 个实例做集群，写死一个地址，另外两台完全用不上；
3. 故障无法感知：某一台商品服务宕机了，订单服务还一直往故障机器发请求，直接报错雪崩；
4. 维护爆炸：服务几十上百个，每个服务多实例，人工维护所有 IP 端口，完全不现实。

方式 2：统一配置文件维护所有服务地址

把所有服务 IP 写到配置文件：

新增实例、下线实例、机器更换，要改所有依赖服务的配置、重启所有服务；

配置更新不实时，不能动态感知服务上下线；

规模一大，运维成本极高，极易出错。

#### 1.2.2 项目配置管理痛点（无配置中心）

微服务项目中，数据库地址、超时时间、限流阈值、功能开关、第三方密钥等都是公共配置。如果不使 用配置中心，所有配置都写在本地配置文件中，会出现严重问题：


1. 配置分散混乱：每个服务独立维护配置文件，多服务、多环境下配置不统一、难以管控；
2. 更新成本极高：修改任意一个公共配置，需要逐个修改所有服务配置、重新打包、重启服务；
3. 无法动态更新：线上参数调整、功能灰度、紧急开关无法实时生效，必须停机重启；
4. 安全性差：密钥、数据库账号密码硬编码在项目中，容易泄露，无法统一加密管理。

## 2. 如何实现服务注册发现 + 配置中心？

Etcd 本质是一个分布式、数据强同步、高可用的键值数据库，集群所有节点数据实时同步、保持一致， 依托它可以完美解决微服务通信和配置管理两大难题。

### 2.1. 服务注册与服务发现原理

当任意微服务启动时，会主动将自身的服务名、IP、端口以键值对的形式写入 Etcd 数据库，同时绑定租 约持续心跳保活，这个过程就是服务注册。

当服务需要远程调用其他服务时，本地服务会实时监听 Etcd 对应服务目录，动态查询并缓存目标服务的 所有可用 IP、端口列表，实时感知服务上下线，这个过程就是服务发现。

### 2.2. 配置中心原理

我们将项目所有公共配置、动态参数，统一以键值对的形式集中存储在 Etcd 中，替代各个服务的本地配 置文件。

所有微服务启动时，主动从 Etcd 拉取最新全局配置并加载；同时持续 Watch 监听配置节点，一旦配置 在 Etcd 中被修改、新增或删除，Etcd 会实时推送变更事件，服务自动加载新配置、无需重启服务即可热 更新，这就是 Etcd 配置中心的核心实现。

## 3. Raft算法

### 3.1. 什么是Raft算法

Raft 算法是业界最主流、最易理解、工程落地最成熟的分布式一致性算法，专门解决分布式集群多节点 数据同步、数据一致、集群容错、主节点切换的核心难题，也是 Etcd、Kubernetes 云原生体系底层赖 以生存的核心算法。

我们先思考一个核心问题：Etcd 为什么必须集群部署？如果只有单节点，一旦宕机，整个微服务的服务 注册、服务发现、配置中心全部瘫痪。所以生产环境 Etcd 一定是 3 节点、5 节点集群部署。但多节点会 带来致命问题：不同机器数据不同步、读写数据错乱、节点故障后数据新旧不一致。

Raft 算法的唯一目标：让集群中所有机器最终数据完全一致、全局状态统一，并且容忍少数节点故障。 正因为有 Raft 强一致性保证，我们微服务连接任意一台 Etcd 节点，查到的服务注册列表、配置内容、 节点状态都是一模一样、绝对可靠的。

在 Raft 出现之前，工业级一致性算法主流是 Paxos，但 Paxos 逻辑极其复杂、难以理解、难以落地、极 易出 bug。而 Raft 算法将复杂的一致性问题拆分为三大独立子问题：领导者选举、日志复制、安全性保 障，逻辑清晰、模块化强、易于工程实现。因此 Etcd、Consul 等主流云原生中间件全部首选 Raft 算 法。

### 3.2. Raft算法三种角色

Raft 集群中每一个节点，同一时刻只会拥有三种身份之一：Leader（领导者）、Follower（跟随者）、 Candidate（候选者）。三种角色可以根据集群状态、心跳超时、节点故障自动动态切换，无需人工干 预。同时 Raft 引入任期（Term）概念，每一次重新选举都会产生一个全新的递增任期号，用来区分数 据新旧、判断节点有效性，杜绝旧数据覆盖新数据。

* **Leader（领导者）——集群唯一写入口**：Raft 严格规定，整个集群同一时间只能有一个合法 Leader。所有的写操作（服务注册写入IP端口、配置新增修改删除、租约创建更新）必须统一交给 Leader 处理，Follower 不接收任何写请求。Leader 负责接收客户端请求、生成日志、同步日志、 通知集群提交数据，是整个集群的数据总指挥。单写入口的设计，从根源避免了多节点同时写入导 致的数据冲突问题。
* **Follower（跟随者）——被动同步、负责读**：Follower 是集群的普通节点，全程被动角色。它不会 主动发起请求、不会主动选举、不会处理写操作。它只做两件事：第一，持续接收 Leader 的心跳 包，证明主节点存活；第二，持续同步 Leader 下发的操作日志，保证自身数据和主节点完全一 致。客户端的读请求可以直接由 Follower 响应，分担集群压力。
* **Candidate（候选者）——临时过渡角色**：该角色仅用于选举阶段，非正常工作状态。当 Follower 超过规定时间没有收到 Leader 心跳，就会判定 Leader 宕机或失联，自动转变为 Candidate 候选 者，开启新一轮选举。选举成功则变成新 Leader，选举失败则退回 Follower，全程是临时状态。

### 3.3. Raft核心工作流程

#### 3.3.1. Leader选举机制

Raft 集群依靠心跳机制 + 超时机制 + 半数投票机制完成自动选举，是集群高可用的核心。


1. 正常运行状态：集群稳定后，唯一的 Leader 会定时向所有 Follower 发送心跳包，告知所有从节点： 主节点正常工作，无需选举。Follower 收到心跳后，会重置自身超时计时器，持续保持跟随状态。
2. 故障触发条件：当 Leader 宕机、进程崩溃、服务器断电、网络断连后，Follower 无法收到心跳包， 心跳超时触发。所有超时的 Follower 自动切换为 Candidate 候选者。
3. 选举发起过程：Candidate 首先给自己投票，同时向集群所有节点发送选举请求，携带自己的最新任 期号和日志数据。其他节点会判断：请求节点日志是否足够新、任期是否合法，合法则投出一票。
4. 半数获胜原则（核心）：Raft 规定，候选者必须获得集群半数以上有效投票，才能当选新 Leader。例 如 3 节点集群需要至少 2 票，5 节点集群需要至少 3 票。
5. 选举结果处理：竞选成功的节点立即变为新 Leader，立刻向全网发送心跳，稳定集群状态；竞选失败 的节点自动退回 Follower 状态，跟随新主节点。整个过程秒级完成，业务无感知。
6. 为什么必须过半？ 过半机制保证：同一任期内绝对不会出现两个 Leader，彻底杜绝脑裂问题，保证 集群全局唯一主节点，数据写入绝对统一。

#### 3.3.2 数据同步机制（核心）

Leader选举只解决了"谁是主节点"的问题，日志复制（数据同步）才是 Raft 保证 Etcd 数据强一致、支撑 服务注册发现和配置中心的最核心底层能力。所有服务注册、配置修改、租约更新，本质都是一次 Raft 日志写入与同步。


1. 统一接收写请求：客户端发起的所有写操作（服务注册KV写入、配置更新、节点删除、租约续 期），只能提交给 Leader 节点，Follower 不处理写业务。
2. 日志预写入：Leader 不会立刻直接写入磁盘生效，而是先将本次操作封装成一条Raft日志，记录 操作内容、任期号、日志索引，先在本地暂存，等待同步。
3. 全网同步日志：Leader 将这条日志批量同步给集群所有 Follower 节点，Follower 收到日志后，校 验合法性，写入本地日志，但暂时不生效、不提交。
4. 过半确认才可提交（重中之重）：当 Leader 收到集群半数以上节点同步成功的回执后，才会判定 本次操作合法有效，执行日志提交，正式写入 Etcd 状态机，对外生效。同时在下一次心跳中，通知 所有 Follower 提交该日志，所有节点数据同步一致。

**如果没有过半确认机制会怎么样：**

举 3 节点集群：A (Leader)、B、C


1. A 是 Term2 的 Leader，只把一条日志复制给了自己，只 1 台节点有，没过半
2. 此时 A 立刻宕机
3. B、C 随机超时，B 先发起选举，Term3 成为新 Leader
4. 新 Leader B 完全没有那条旧日志，正常写入新数据
5. 之后 A 重启，变回 Follower

A 发现 B 是更高 Term 的 Leader

会被 Leader 强制覆盖、删掉自己那条旧日志


6. 最终效果：只要过半节点同步成功，就代表数据安全可靠。即使剩余少数节点宕机、离线，数据依 然可以正常写入、正常对外提供服务。故障节点重启后，会自动对比日志差异，补全缺失数据，自 动追平集群最新状态。

### 3.4. 为什么Etcd一定要用Raft算法

结合我们本节课 Etcd 实现微服务的三大能力（服务注册、服务发现、配置中心），Raft 算法解决了分布 式场景下两个绝对致命、无法规避的核心问题，是 Etcd 可以用于生产环境的底层基石：


1. **彻底解决分布式数据不一致问题**：如果没有 Raft，Etcd 多节点之间数据无法同步，会出现严重业务 bug：客户端连接A节点查到服务已上线，连接B节点却查不到；或者配置修改后，部分节点更新、 部分节点旧数据。Raft 通过「唯一Leader写入+过半同步提交」，保证集群所有节点最终数据完全 一致，所有服务发现、配置读取结果全局统一、精准无误。
2. **彻底解决单点故障问题，实现高可用**：单节点Etcd一旦挂掉，整个微服务注册中心、配置中心全部 瘫痪。依托Raft选举机制，集群允许少数节点故障（3节点集群允许挂1台，5节点集群允许挂2 台），剩余节点自动选举新主节点，数据不丢失、服务不中断，保证微服务注册发现、动态配置全 程可用。

### 3.5. 总结

Raft 算法就是 Etcd 集群的高可用+强一致底层保障。它通过任期机制区分数据新旧、唯一Leader统一写 入口、心跳检测感知故障、半数投票杜绝脑裂、日志同步保证全局一致，让 Etcd 集群容错、稳定、数据 可靠，最终支撑 Go 微服务实现稳定的服务注册发现、客户端负载均衡、动态配置热更新。

## 4. 实战篇

### 4.1. Etcd数据存储整体说明 & 格式总结

#### 4.1.1 Etcd Key 设计核心原则

Etcd 作为一个非关系型数据库，不能像MySQL一样分库分表，只能靠key的设计来区分项目、环境、资 源类型、服务名等，因此key的设计必须遵守规范。

#### 4.1.2 服务注册数据（动态临时数据 · 生产规范）

核心定位：用于维护微服务集群在线节点列表，动态感知服务上下线，属于临时性、可自动销毁的协调 数据，必须绑定 Etcd 租约 Lease ，服务宕机自动清除脏数据。

**补充知识：租约是什么？**

租约 = 带 TTL 的 "临时凭证"：

* 客户端创建租约并指定 TTL（如 10s）
* 把 KV 绑定到租约
* 租期内客户端必须续租（KeepAlive），否则租约到期后，etcd 会自动删除该租约及其所有绑定的 KV。

**租约生命周期**

* Grant（创建）：申请一个 LeaseID，指定 TTL（秒），etcd 返回唯一 ID。
* Attach（绑定）：Put KV 时带上 LeaseID，KV 与租约关联etcd。
* KeepAlive（续租）：客户端定期发请求，重置租约剩余 TTL（通常在 TTL 过半时触发）。
* Expire（过期）：未及时续租 → 租约到期 → etcd 自动删除租约及所有绑定 KV。
* Revoke（撤销）：主动删除租约，立即清理所有关联 KVetcd。

**Etcd租约与Redis TTL的区别**

| 特性  | Etcd Lease | Redis Expire |
|-----|------------|--------------|
| 绑定关系 | 租约可绑定多个 KV，级联删除 | 每个 Key 独立 TTL，互不影响 |
| 续租方式 | 批量续租一个租约即可 | 每个 Key 单独续期  |
| 一致性 | 基于 Raft，集群内过期行为一致 | 单节点 / 主从，可能不一致 |
| 核心用途 | 服务注册、分布式锁、健康检测 | 缓存淘汰、临时数据    |
| 性能  | 适合少量高频保活（如服务发现） | 适合海量缓存       |

**标准 Key 格式**

格式模板： `/{namespace}/{env}/services/{service-name}/{instance-id}`

字段释义

* namespace：项目命名空间（项目名），用于多项目隔离
* env：运行环境（dev/test/prod），用于多环境隔离
* services：资源类型固定标识，区分配置数据
* service-name：微服务名称
* instance-id：服务实例唯一标识（推荐 IP:Port / UUID）

规范示例

`/mall/dev/services/user-service/127.0.0.1:8080`

**Value 存储规范（结构化 JSON，生产标准）**

不再单纯存储 IP:Port，采用 JSON 结构化存储，携带实例扩展信息，支持负载均衡、灰度发布、节点权 重配置，适配复杂生产场景。

```json
{
  "ip": "127.0.0.1",
  "port": 8080,
  "version": "v1",
  "weight": 100
}
```

各字段作用

* ip/port：服务真实调用地址，服务发现核心数据
* version：服务版本，用于灰度发布、版本流量隔离
* weight：节点权重，用于加权负载均衡流量分发

数据生命周期：绑定租约 TTL（5-10秒），服务正常运行持续续约，数据常驻；服务宕机、断网、崩溃 后停止续约，租约过期 Key 自动删除，无人工脏数据。

**服务发现实现原理**

消费者通过前缀查询批量获取同服务所有实例，无需遍历全量数据：

查询前缀： `/mall/dev/services/user-service/`

配合 Watch 前缀监听，实时感知实例上线（Put）、下线（Delete），动态更新本地节点列表。

#### 4.1.3 配置中心数据（持久化静态数据 · 生产规范）

核心定位：统一托管微服务公共配置，实现配置集中管理、动态热更新、全局统一生效，属于永久持久 化节点，不绑定租约，不会自动过期删除。

**标准 Key 格式**

格式模板： `/{namespace}/{env}/config/{service-name}/{config-key}`

字段释义

* namespace：项目命名空间，与服务注册统一，保证项目规范统一
* env：运行环境，实现多环境配置隔离
* config：资源类型固定标识，区分服务注册数据
* service-name：所属微服务名称
* config-key：具体配置项/配置目录

结构化层级示例（推荐，适配前缀监听）

```
/mall/dev/config/user-service/database/host
/mall/dev/config/user-service/database/port
/mall/dev/config/common/log/level
```

优势：层级清晰，可针对某一类配置前缀监听，比点号分割格式更适配 Etcd 机制。

**Value 存储规范**

单配置项 Key 对应单一 Value，存储纯配置值，简洁易解析：

示例：Key = `/mall/dev/config/user-service/database/host` ，Value = `127.0.0.1`

示例：Key = `/mall/dev/config/user-service/database/port` ，Value = `3306`

数据生命周期：永久持久化存储，仅支持手动修改、删除，服务重启、节点宕机不会丢失配置，保障服 务稳定运行。

格式模板： `/{app}/{env}/config/{service}/{key}`

#### 4.1.4 生产进阶扩展规范（灰度、多机房、高可用）

基础格式满足通用业务，生产高并发、灰度发布、跨机房场景，可在基础格式上扩展层级，不破坏原有 规范：


1. **版本灰度扩展**（支持多版本共存、流量灰度）

   格式： `/{namespace}/{env}/services/{service-name}/{version}/{instance-id}`

   示例：

   ```
   /mall/prod/services/user-service/v1/10.0.0.1:8080
   /mall/prod/services/user-service/v2/10.0.0.2:8080
   ```

   作用：实现 v1、v2 版本服务共存，支持灰度流量分发、版本平滑迁移。
2. **多数据中心/区域扩展**

   格式： `/{namespace}/{env}/services/{service-name}/{region}/{instance-id}`

   示例：

   ```
   /mall/prod/services/user-service/cn-east/10.0.0.1:8080
   /mall/prod/services/user-service/cn-west/10.0.0.2:8080
   ```

   作用：区分不同机房节点，实现就近调用、异地容灾。
3. **节点类型严格区分（临时节点 & 永久节点）**
   * 服务注册节点：带 Lease 租约临时节点，动态存活、自动清理脏数据
   * 配置中心节点：永久普通节点，持久化存储、保证配置不丢失

### 4.2. 服务注册与服务发现实战

#### 4.2.1. Etcd 服务注册步骤

Etcd 服务注册是微服务生产者主动上报自身信息、完成节点入驻集群的核心流程，依托 Etcd 键值存储、 Lease 租约机制实现自动保活与故障自愈，全程分为 6 个标准步骤，严格遵循生产标准层级规范：


1. **初始化基础环境**

   微服务启动完成，读取自身运行配置，确认当前部署环境（dev/test/prod）、项目名称、服务名 称、本机 IP、监听端口，确定唯一实例标识。
2. **建立 Etcd 客户端连接**

   服务启动后初始化 Etcd 客户端，配置集群地址、连接超时时间，与 Etcd 集群建立长连接，为后续 注册操作提供通信基础。
3. **创建生命周期租约（Lease）**

   向 Etcd 服务端申请指定 TTL（通常 5\~10 秒）的租约。租约是服务健康存活的凭证，所有注册信息 均绑定该租约，实现数据自动过期能力。
4. **写入注册信息并绑定租约**

   通过 Put 接口将结构化的 Key、JSON 格式 Value 写入 Etcd，并绑定上一步创建的租约，使服务注 册数据具备时效性。
   * Key 格式： `/{namespace}/{env}/services/{service-name}/{instance-id}`
   * Value 格式：使用 JSON 存储服务实例信息（IP、端口、版本、权重等），用于灰度发布、负 载均衡等生产场景。

   每个 Key 唯一对应一个服务实例，确保集群中多实例不重复、可区分。
5. **开启自动心跳续约**

   调用 KeepAlive 接口开启后台自动续约机制。服务正常运行期间持续向 Etcd 发送续约请求，刷新 租约有效期，保证注册信息不被自动删除。

   **KeepAlive 接口说明：**

   KeepAlive 是 Etcd 提供的租约自动续约接口，用于服务实例启动后，在后台持续向 Etcd 集群发送 心跳信号，刷新租约剩余时间。

   只要服务正常运行，客户端会自动按策略发送续约请求，保证注册信息不会因租约过期而被删除。

   当服务宕机、断网或进程退出时，续约自动终止，Etcd 会在租约到期后自动清理该节点数据，实现 故障自愈与脏数据自动清理。
6. **故障自动下线**

   当服务宕机、进程崩溃、服务器断电或网络断连时，续约机制自动终止。租约到期后，Etcd 会自动 删除该服务实例的注册 Key，实现故障节点自动清理，杜绝脏数据残留。

#### 4.2.2. Etcd服务发现步骤

服务发现是微服务消费者获取目标服务可用节点、动态维护服务列表的核心流程，依托 Etcd 前缀查询、 Watch 监听机制，实现服务节点实时感知、动态更新，彻底解决硬编码地址的痛点，具体步骤如下：


1. 初始化Etcd客户端：消费者服务启动后，初始化 Etcd 客户端，连接同一套 Etcd 集群，保证与生产 者服务数据互通。
2. 定义服务查询前缀：根据目标服务的命名空间、环境、服务名，拼接统一查询前 缀： `/{namespace}/{env}/services/{service-name}/` ，用于批量匹配所有同服务实例。
3. 一次性拉取全量服务节点：通过前缀查询方式，从 Etcd 批量获取该服务下所有存活的实例Key与 Value，解析出所有可用的IP+端口，缓存到本地内存，作为初始调用节点列表。
4. 开启全局Watch监听：对上述服务前缀开启持续监听，实时订阅该目录下所有的新增、删除事件， 无需轮询查询，降低性能开销。

   **Watch监听工作机制：**

   
   1. 消费者启动
   2. 调用 Watch 监听一个前缀（例如 `/services/user-service/` ）
   3. 进入阻塞等待状态（不占 CPU）
   4. 一旦 etcd 里该目录下：
      * 新增 key（服务上线）
      * 删除 key（服务宕机 / 下线）
      * 修改 key（服务更新）
   5. etcd 主动推送事件给消费者
   6. 消费者更新本地服务列表，实现实时感知
5. 动态更新本地节点列表：监听服务上线（Put事件）、服务下线（Delete事件），实时新增或剔除 本地缓存的服务节点，始终保证本地列表与Etcd集群数据一致。
6. 结合负载均衡选择节点调用：每次发起远程调用前，从本地最新的健康节点列表中，通过负载均衡 算法选取最优节点，完成HTTP/gRPC远程调用。

#### 4.2.3. 代码示例

本次代码严格遵循层级规范，完整实现服务注册、自动续约、服务发现、实时监听核心能力，可直接编 译运行：

```go
package main

import (
	"context"
	"fmt"
	"go.etcd.io/etcd/client/v3"
	"time"
)

// 全局统一配置 遵循规范层级：/{namespace}/{env}/services/{service-name}/{instance- id}
const (
	Namespace = "mall"                // 项目命名空间
	Env       = "dev"                 // 运行环境
	Service   = "user-service"        // 服务名称
	LocalAddr = "127.0.0.1:8080"      // 实例唯一标识
	TTL       = 5                     // 租约有效期5秒
)

// 创建Etcd客户端
func NewEtcdClient() (*clientv3.Client, error) {
	return clientv3.New(clientv3.Config{
		Endpoints:   []string{"127.0.0.1:2379"}, //etcd 集群的所有节点地址列表
		DialTimeout: 5 * time.Second,
	})
}

// 服务注册 完全对齐生产规范Key格式
func RegisterService(cli *clientv3.Client) error {
	// 拼接标准生产Key
	key := fmt.Sprintf("/%s/%s/services/%s/%s", Namespace, Env, Service, LocalAddr)
	// 结构化JSON Value，适配生产扩展字段
	value := `{"ip":"127.0.0.1","port":8080,"version":"v1","weight":100}`

	// 创建租约
	leaseResp, err := cli.Grant(context.Background(), TTL)
	if err != nil {
		return err
	}

	// 写入注册信息并绑定租约
	_, err = cli.Put(context.Background(), key, value, clientv3.WithLease(leaseResp.ID))
	if err != nil {
		return err
	}

	// 后台自动续约（心跳保活）
	keepAliveChan, err := cli.KeepAlive(context.Background(), leaseResp.ID)
	if err != nil {
		return err
	}
	go func() {
		for range keepAliveChan {
			// 持续续约，维持服务在线状态
		}
	}()

	fmt.Printf("服务注册成功，注册路径：%s\n", key)
	return nil
}

// 服务发现：获取所有在线节点
func DiscoverService(cli *clientv3.Client) ([]string, error) {
	// 标准前缀查询，匹配同服务所有实例
	prefix := fmt.Sprintf("/%s/%s/services/%s/", Namespace, Env, Service)
	resp, err := cli.Get(context.Background(), prefix, clientv3.WithPrefix())
	if err != nil {
		return nil, err
	}

	var nodeList []string
	for _, kv := range resp.Kvs {
		nodeList = append(nodeList, string(kv.Value))
	}
	return nodeList, nil
}

// 实时监听服务上下线变化
func WatchServiceChange(cli *clientv3.Client) {
	prefix := fmt.Sprintf("/%s/%s/services/%s/", Namespace, Env, Service)
	watchChan := cli.Watch(context.Background(), prefix, clientv3.WithPrefix())

	fmt.Println("开始监听服务节点动态变化...")
	for watchResp := range watchChan {
		for _, event := range watchResp.Events {
			switch event.Type {
			case clientv3.EventTypePut:
				fmt.Printf("服务新节点上线：%s\n", string(event.Kv.Key))
			case clientv3.EventTypeDelete:
				fmt.Printf("服务节点下线：%s\n", string(event.Kv.Key))
			}
		}
	}
}

func main() {
	// 初始化客户端
	cli, err := NewEtcdClient()
	if err != nil {
		panic(fmt.Sprintf("Etcd连接失败：%v", err))
	}
	defer cli.Close()

	// 执行服务注册
	_ = RegisterService(cli)

	// 初始拉取服务列表
	nodes, _ := DiscoverService(cli)
	fmt.Printf("当前在线服务节点：%v\n", nodes)

	// 异步监听节点变化
	go WatchServiceChange(cli)

	// 阻塞常驻运行
	select {}
}
```

### 4.3. 配置中心实战

#### 4.3.1. 配置中心步骤

传统微服务将配置存放在本地配置文件，存在配置分散、更新繁琐、无法热更新、多环境配置混乱等问 题，基于 Etcd 实现配置中心，可完成配置统一托管、动态更新、全局同步。Etcd 配置中心同样采用标准 化Key值存储结构，区分于服务注册数据，各司其职，标准落地步骤如下：


1. **规范配置存储路径，明确存储数据**：统一配置中心Key层级格 式： `/{namespace}/{env}/config/{service-name}/{config-key}` 。 Etcd配置存储规则：Key 为分层结构化配置路径，精准区分项目、环境、服务、配置项，完全隔离多项目、多服务配置； Value存储纯配置文本值，单Key对应单一配置项，结构清晰、便于程序解析与热更新，无冗余嵌 套。
2. **提前录入全局配置**：通过 etcdctl 命令或代码，将数据库配置、超时时间、功能开关、限流阈值、 第三方密钥等公共配置写入Etcd。
3. **服务启动拉取初始配置**：微服务启动后，连接Etcd，通过配置Key拉取最新配置数据，解析后加载 到程序内存，完成初始化配置加载。
4. **开启配置Watch监听**：对当前服务的配置Key开启持续监听，实时订阅配置新增、修改、删除事 件。
5. **配置动态热更新**：当运维人员修改Etcd中的配置后，Watch机制实时推送变更事件，程序自动重新 解析、加载新配置，无需重启服务、无需重新打包部署。
6. **全局配置统一生效**：所有依赖该配置的服务同步感知变更，保证集群内所有服务配置统一，解决多 实例配置不一致问题。

#### 4.3.2. 代码示例

以下代码实现 Etcd 配置中心核心能力：初始化拉取配置、实时监听变更、热更新加载，可与上述服务注 册发现代码无缝整合：

```go
package main

import (
	"context"
	"fmt"
	"go.etcd.io/etcd/client/v3"
	"log"
)

// Key规范
const (
	Namespace = "mall"
	Env       = "dev"
	Service   = "user-service"
	// 标准结构化配置Key
	ConfigKey = "/mall/dev/config/user-service/database/host"
)

// GetConfig 获取Etcd配置
func GetConfig(cli *clientv3.Client) (string, error) {
	resp, err := cli.Get(context.Background(), ConfigKey)
	if err != nil {
		return "", err
	}
	if len(resp.Kvs) == 0 {
		return "", fmt.Errorf("暂无配置数据")
	}
	return string(resp.Kvs[0].Value), nil
}

// WatchConfig 监听配置热更新
func WatchConfig(cli *clientv3.Client) {
	watchChan := cli.Watch(context.Background(), ConfigKey)
	fmt.Println("开始监听服务配置变更...")

	for watchResp := range watchChan {
		for _, event := range watchResp.Events {
			switch event.Type {
			case clientv3.EventTypePut:
				fmt.Printf("配置更新成功，最新配置：%s\n", string(event.Kv.Value))
				// 此处可扩展：重新加载配置、刷新全局变量、更新参数
			case clientv3.EventTypeDelete:
				fmt.Println("配置被删除，请及时补充配置信息")
			}
		}
	}
}
```

### 4.4. 负载均衡

#### 4.4.1. 为什么需要负载均衡

在微服务架构中，为了保证服务高可用、支持高并发，核心服务都会部署多实例集群，单纯依靠服务发 现获取多节点列表，无法实现合理流量分发，因此必须引入负载均衡机制，核心必要性如下：


1. **解决流量集中单点压力问题**：若所有请求都访问同一个服务实例，会导致单节点CPU、内存、网络 过载，出现响应超时、服务卡顿甚至宕机，负载均衡可将流量分散到多个节点。
2. **实现服务高可用容错**：当集群中某一个服务实例故障下线后，负载均衡算法可自动避开故障节点， 只分发流量到健康实例，避免单点故障导致整体服务不可用。
3. **最大化利用服务器资源**：多实例集群部署后，通过合理的流量分发策略，让所有节点资源均衡利 用，避免部分节点空闲、部分节点过载的资源浪费问题。
4. **支持服务动态扩缩容**：新增服务实例后，服务发现动态更新节点列表，负载均衡自动纳入新节点分 发流量，无需修改代码和配置，适配弹性扩容场景。
5. **提升系统整体吞吐量与并发能力**：多节点并行处理请求，大幅提升服务整体并发上限，支撑更高的 业务流量。

#### 4.4.2. 负载均衡的四种实现方式比较


1. **随机负载均衡**

   原理：消费者从本地缓存的健康服务节点列表中，通过随机算法随机选取一个节点发起调用，完全无 规律分发流量。

   优点：实现极简、无状态、无需记录调用轨迹、性能开销极低；节点数量充足时，流量分布相对均匀。

   缺点：无法适配节点性能差异，高性能机器和低性能机器分配流量一致；流量极端场景可能出现分配 不均。

   适用场景：测试环境、小规模集群、服务节点配置统一、对流量均匀度要求不高的通用业务。
2. **轮询负载均衡**

   原理：按照节点列表顺序，依次循环选取节点调用，遵循「1→2→3→1→2→3」的固定顺序，逐个 分配流量。

   优点：流量分配绝对均匀，所有节点请求量基本一致；逻辑简单、无计算压力、稳定性高。

   缺点：完全忽略节点硬件性能、负载差异，老旧低配置机器会承载和高性能机器相同的流量，容易出现 单点瓶颈；不支持会话保持。

   适用场景：生产环境标准化集群、所有服务实例配置一致、无状态接口服务。
3. **加权负载均衡（加权轮询/加权随机）**

   原理：为不同性能的服务节点配置权重值，高性能机器权重高、低性能机器权重低，流量优先分配给高 权重节点，实现按需分配流量。

   优点：适配差异化节点配置，资源利用率最大化；可灵活通过调整权重实现灰度发布、流量切分、节点 下线预热。

   缺点：需要手动维护权重配置，增加运维成本；算法复杂度高于随机、普通轮询。

   适用场景：生产环境混合配置集群、服务灰度迭代、节点逐步扩容下线、核心高并发业务。
4. **一致性哈希**

   原理：对客户端请求IP进行哈希计算，将哈希值对节点数量取模，固定映射到某一个服务节点，同一客 户端IP始终访问同一实例。

   优点：天然实现会话保持，同一用户请求落地同一节点，适合需要本地缓存、会话存储的业务。

   缺点：服务节点上下线、数量变更时，哈希映射关系彻底打乱，大量用户请求重新分配，可能导致短暂 业务异常；流量分配容易不均。

   适用场景：需要会话保持、本地缓存复用、状态型服务的业务场景。
