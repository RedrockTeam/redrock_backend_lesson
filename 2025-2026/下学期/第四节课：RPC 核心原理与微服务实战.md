## 一、开篇：为什么我们需要 RPC？

同学们，大家好！今天我们来聊 RPC。

首先，我想问大家一个问题：**在一个电商系统中，用户下单这个操作，背后发生了什么？**

让我们来想象一下：

### 1.1 单体架构时代

在很久以前，我们的系统是这样的：

```
┌─────────────────────────────────┐
│        电商系统（单体）          │
│  ┌─────┐ ┌─────┐ ┌─────┐    │
│  │用户 │ │商品 │ │订单 │    │
│  │服务 │ │服务 │ │服务 │    │
│  └─────┘ └─────┘ └─────┘    │
│         （同一个进程内）         │
└─────────────────────────────────┘
```

所有代码都在一个项目里，下单就是：

```go
orderService.CreateOrder(userId, productId)  // 直接调用函数
```

简单，直接，高效！


---

### 1.2 但问题来了...

随着业务发展，系统越来越大：

* 代码量几十万行
* 几百人同时开发
* 每次发布要等所有人的代码合并
* 一个小 bug 可能导致整个系统挂掉

**于是，微服务架构出现了！**


---

### 1.3 微服务架构

我们把系统拆成多个独立的服务：

```
┌──────────┐      ┌──────────┐      ┌──────────┐
│  用户服务 │      │  商品服务 │      │  订单服务 │
│ (独立部署) │      │ (独立部署) │      │ (独立部署) │
└────┬─────┘      └────┬─────┘      └────┬─────┘
     │                   │                   │
     └───────────────────┼───────────────────┘
                         │
                  ┌──────┴──────┐
                  │   网络通信    │
                  └─────────────┘
```

现在问题来了：**订单服务怎么调用用户服务？**

它们不在同一个进程了，不能直接调用函数了！


---

### 1.4 这就是 RPC 要解决的问题！

**RPC = Remote Procedure Call = 远程过程调用**

简单来说：**让远程调用像调用本地函数一样简单！**

单体时代：

```go
result := userService.GetUser(123)  // 直接调用
```

微服务时代（用 RPC）：

```go
result := userClient.GetUser(ctx, &UserReq{Id: 123})  // 远程调用，但看起来一样！
```

这就是 RPC 的魔力！🎉

## 二、RPC 基础概念详解

### 2.1 什么是 RPC？

**RPC（Remote Procedure Call）** 是一种**跨进程、跨机器**的通信方式。

它让你可以：

* 像调用本地函数一样
* 调用另一台机器上的函数
* 不用关心网络细节


---

### 2.2 RPC 的完整流程

一次 RPC 调用，背后发生了什么？让我们来看一个完整的时序图：

```
┌─────────┐                    ┌─────────┐
│ 客户端  │                    │ 服务端  │
└────┬────┘                    └────┬────┘
     │                              │
     │  1. 调用 client.Add(1, 2)   │
     │─────────────────────────────>│
     │                              │
     │  2. 序列化请求（编码）        │
     │─────────────────────────────>│
     │                              │
     │  3. 网络传输（TCP）         │
     │─────────────────────────────>│
     │                              │
     │  4. 反序列化请求（解码）      │
     │─────────────────────────────>│
     │                              │
     │  5. 执行业务逻辑 Add(1,2)   │
     │                              │
     │  6. 序列化响应              │
     │<─────────────────────────────│
     │                              │
     │  7. 网络传输                │
     │<─────────────────────────────│
     │                              │
     │  8. 反序列化响应            │
     │<─────────────────────────────│
     │                              │
     │  9. 返回结果 3              │
     │<─────────────────────────────│
```

**一共 9 步！** 但作为开发者，我们只需要关心：

* 第 1 步：调用方法
* 第 5 步：写业务逻辑
* 第 9 步：拿到结果

其他 6 步，**RPC 框架都帮我们处理了！** 这就是为什么要用 RPC 框架！


---

### 2.3 RPC 的核心组件

一个完整的 RPC 框架，包含这些部分：

| 组件  | 作用  |
|-----|-----|
| **IDL** | 接口定义语言（.proto / .thrift） |
| **序列化** | 对象 ↔ 二进制数据（Protobuf / Thrift） |
| **网络传输** | TCP / HTTP2 |
| **客户端** | 调用远程方法 |
| **服务端** | 实现业务逻辑 |


---

### 2.4 常见的 RPC 框架

| 框架  | 开发者 | 语言  | 序列化 |
|-----|-----|-----|-----|
| **gRPC** | Google | 跨语言 | Protobuf |
| **Kitex** | 字节跳动 | Go  | Thrift / Protobuf |
| **Dubbo** | 阿里巴巴 | Java | 多种  |
| **Thrift** | Facebook | 跨语言 | Thrift |


---

### 2.5 什么是 IDL？

**IDL = Interface Definition Language = 接口定义语言**

为什么需要 IDL？

* 跨语言：Go 写的服务，Java 也能调用
* 统一规范：客户端和服务端用同一份接口定义
* 自动生成代码：不用手写数据结构

比如 gRPC 用的 Protobuf：

```protobuf
message AddReq {
    int32 a = 1;
    int32 b = 2;
}

service Calc {
    rpc Add(AddReq) returns (AddResp);
}
```

Kitex 用的 Thrift：

```thrift
struct AddReq {
    1: required i64 A
    2: required i64 B
}

service CalcService {
    AddResp Add(1:AddReq req)
}
```


---

### 2.6 什么是序列化？

**序列化 = 把对象变成二进制数据**

**反序列化 = 把二进制数据变回对象**

为什么需要序列化？

* 网络只能传二进制，不能传 Go 的 struct
* 二进制比 JSON 小，传输更快
* 二进制比 JSON 解析更快

**Protobuf vs JSON 对比：**

| 特性  | Protobuf | JSON |
|-----|----------|------|
| 大小  | 小（二进制）   | 大（文本） |
| 速度  | 快        | 慢    |
| 可读性 | 差        | 好    |
| 适用场景 | 内部服务调用   | 前端接口 |

举个例子，同样的数据：

* JSON: `{"a":1,"b":2}` → 13 字节
* Protobuf: 二进制 → 约 4 字节

**Protobuf 小了 3 倍多！** 这在高并发场景下很重要！

## 三、RPC vs HTTP：如何选择？

很多同学会问：**既然有 HTTP，为什么还要用 RPC？**

今天我们就来好好对比一下！


---

### 3.1 HTTP 我们都熟悉

HTTP 是应用层协议，我们每天都在用：

* 浏览器打开网页
* 前端调用后端接口
* 第三方 API 调用

HTTP + JSON 的方式：

```go
// 客户端
resp, _ := http.Post("http://api.example.com/add", 
    "application/json", 
    strings.NewReader(`{"a":1,"b":2}`)
)

// 服务端
http.HandleFunc("/add", func(w http.ResponseWriter, r *http.Request) {
    var req AddReq
    json.NewDecoder(r.Body).Decode(&req)
    sum := req.A + req.B
    json.NewEncoder(w).Encode(AddResp{Sum: sum})
})
```


---

### 3.2 RPC vs HTTP 详细对比

让我们从多个维度对比：

| 维度  | RPC（gRPC/Kitex） | HTTP + JSON |
|-----|-----------------|-------------|
| **性能** | ⭐⭐⭐⭐⭐ 极高        | ⭐⭐ 一般       |
| **序列化** | Protobuf/Thrift（二进制） | JSON（文本）    |
| **传输协议** | HTTP2 / TCP     | HTTP1.1     |
| **类型安全** | ✅ 编译时检查         | ❌ 运行时检查     |
| **接口定义** | ✅ IDL 统一管理      | ❌ 文档/注释     |
| **代码生成** | ✅ 自动生成          | ❌ 手写        |
| **易用性** | ⭐⭐⭐⭐ 像本地调用      | ⭐⭐ 需要处理 HTTP 细节 |
| **浏览器支持** | ❌ 不直接支持         | ✅ 完美支持      |
| **适用场景** | 内部微服务调用         | 对外 API、前端   |


---

### 3.3 性能差距有多大？

让我们看一个真实的性能对比（仅供参考）：

| 指标  | gRPC | HTTP + JSON |
|-----|------|-------------|
| QPS | 50,000 | 10,000      |
| 延迟（p99） | 10ms | 50ms        |
| CPU 使用率 | 低    | 高           |
| 网络传输量 | 小    | 大           |

**gRPC 性能是 HTTP+JSON 的 5 倍！**

在高并发场景下，这个差距非常重要！


---

### 3.4 什么时候用 RPC？什么时候用 HTTP？

**用 RPC，如果你：**

* ✅ 内部微服务之间调用
* ✅ 对性能有要求
* ✅ 团队内部使用，不需要浏览器支持
* ✅ 想要类型安全，减少 bug
* ✅ 想要自动生成代码，提高开发效率

**用 HTTP + JSON，如果你：**

* ✅ 对外提供 API（给前端、第三方用）
* ✅ 需要浏览器直接调用
* ✅ 需要调试方便（JSON 可读）
* ✅ 简单的接口，性能要求不高


---

### 3.5 企业真实用法

实际的企业中，通常是**混用**的：

```
                    ┌─────────────┐
                    │   浏览器/APP │
                    └──────┬──────┘
                           │ HTTP + JSON
                           │
                    ┌──────▼──────┐
                    │   API 网关   │
                    └──────┬──────┘
                           │
        ┌──────────────────┼──────────────────┐
        │                  │                  │
   RPC  │              RPC  │              RPC  │
        │                  │                  │
   ┌────▼────┐       ┌────▼────┐       ┌────▼────┐
   │ 用户服务 │       │ 商品服务 │       │ 订单服务 │
   └─────────┘       └─────────┘       └─────────┘
```

* **对外**：用 HTTP + JSON（给前端）
* **对内**：用 RPC（服务之间调用）

这就是最佳实践！

## 四、从单体到微服务的演进

### 4.1 阶段一：单体应用

```
┌─────────────────────────────────┐
│      电商系统（单体）            │
│  ┌─────┐ ┌─────┐ ┌─────┐    │
│  │用户 │ │商品 │ │订单 │    │
│  │代码 │ │代码 │ │代码 │    │
│  └─────┘ └─────┘ └─────┘    │
│         （一个数据库）           │
└─────────────────────────────────┘
```

**特点：**

* 开发简单
* 部署简单
* 适合小团队
* 业务量小


---

### 4.2 阶段二：垂直拆分

业务发展了，按业务垂直拆分：

```
┌──────────┐  ┌──────────┐  ┌──────────┐
│ 用户系统 │  │ 商品系统 │  │ 订单系统 │
│ (独立部署)│  │ (独立部署)│  │ (独立部署)│
└────┬─────┘  └────┬─────┘  └────┬─────┘
     │               │               │
     └───────────────┼───────────────┘
                     │
              ┌──────┴──────┐
              │  HTTP 调用   │
              └─────────────┘
```

**特点：**

* 系统分开了
* 但还是用 HTTP 调用
* 性能开始成为问题


---

### 4.3 阶段三：引入 RPC

性能不够用，引入 RPC 框架：

```
┌──────────┐  ┌──────────┐  ┌──────────┐
│ 用户服务 │  │ 商品服务 │  │ 订单服务 │
│ (gRPC)   │  │ (gRPC)   │  │ (gRPC)   │
└────┬─────┘  └────┬─────┘  └────┬─────┘
     │               │               │
     └───────────────┼───────────────┘
                     │
              ┌──────┴──────┐
              │   RPC 调用    │
              │ (高性能)      │
              └─────────────┘
```

**特点：**

* 性能提升
* 开发效率提升
* 类型安全


---

### 4.4 阶段四：服务治理

服务越来越多，新问题出现了：

* ❓ 服务 A 怎么找到服务 B？
* ❓ 服务 B 挂了怎么办？
* ❓ 流量太大，服务 B 扛不住怎么办？
* ❓ 怎么监控所有服务？

这时候就需要**服务治理**了！

```
┌─────────────────────────────────────────────┐
│           服务治理平台                        │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐  │
│  │服务发现  │ │熔断降级  │ │  监控    │  │
│  │(etcd)   │ │(hystrix) │ │(prometheus)│  │
│  └──────────┘ └──────────┘ └──────────┘  │
└─────────────────────────────────────────────┘
         │                  │                  │
         └──────────────────┼──────────────────┘
                            │
    ┌───────────────────────┼───────────────────────┐
    │                       │                       │
┌───▼────┐            ┌───▼────┐            ┌───▼────┐
│ 用户服务 │            │ 商品服务 │            │ 订单服务 │
└────────┘            └────────┘            └────────┘
```

这就是我们下一节课要学的内容！

## 五、预告：下一节课我们学什么？

今天我们学了 RPC 的基础，**但这只是开始！**

微服务架构中，还有很多问题需要解决：


---

### 5.1 问题一：服务发现

**场景：**

* 订单服务要调用用户服务
* 用户服务部署了 10 个实例
* 订单服务怎么知道这 10 个实例的 IP 和端口？
* 如果有实例挂了，怎么自动剔除？

**解决方案：服务注册与发现**

* **etcd** / **Consul** / **Nacos**


---

### 5.2 问题二：熔断降级

**场景：**

* 订单服务调用用户服务
* 用户服务挂了，或者响应很慢
* 订单服务一直等，导致订单服务也挂了
* 故障传播，整个系统雪崩！

**解决方案：熔断与降级**

* **Hystrix** / **Sentinel**
* 快速失败，避免雪崩


---

### 5.3 问题三：负载均衡

**场景：**

* 用户服务部署了 10 个实例
* 订单服务的请求怎么分配？
* 随机？轮询？加权？

**解决方案：负载均衡**

* 多种策略可选


---

### 5.4 问题四：链路追踪

**场景：**

* 一个请求经过了 5 个服务
* 某个请求很慢，怎么定位是哪个服务慢？
* 怎么看到完整的调用链路？

**解决方案：分布式链路追踪**

* **Jaeger** / **Zipkin**


---

### 5.5 问题五：监控告警

**场景：**

* 服务出错了，怎么及时发现？
* QPS 下降了，怎么告警？
* 怎么看服务的性能指标？

**解决方案：监控与告警**

* **Prometheus** + **Grafana**


---

### 5.6 下节课预告

下一节课，我们会学习：

| 技术  | 作用  |
|-----|-----|
| **etcd** | 服务注册与发现 |
| **熔断降级** | 防止雪崩 |
| **负载均衡** | 合理分配请求 |
| **链路追踪** | 定位问题 |
| **监控告警** | 及时发现问题 |

这些技术合起来，就是**微服务治理**！
