# 第二节课：消息队列

# 消息队列：三大消息队列对比及底层浅析

## 1. 什么是消息队列

消息队列（Message Queue，简称 MQ）本质上是一种异步通信机制。

在没有消息队列的时候，一个系统通常会直接调用另一个系统；而在引入消息队列之后，消息会先进入一个中间系统，再由后面的服务按各自节奏处理。

这意味着，消息队列不只是"传递消息"的工具，更重要的作用是协调系统之间的关系。

例如，用户下单之后，系统可能还要继续完成下面这些动作：

* 扣减库存
* 发起支付流程
* 增加积分
* 发送短信
* 推送物流通知

如果这些动作全部同步完成，那么主流程会变长；只要某一个下游服务变慢，整个请求就会跟着变慢；只要某一个服务不可用，主流程就可能受到影响。

因此，消息队列的核心价值主要体现在以下几个方面：

* **解耦**：订单服务不需要直接依赖每一个下游系统
* **异步**：主流程优先完成核心动作，非核心动作延后处理
* **削峰**：高峰流量先进入队列缓冲，后续再慢慢消费
* **广播分发**：同一条消息可以被多个下游系统消费
* **最终一致性**：适合订单、积分、通知等业务链路

可以把消息队列理解成一个中转站。发送消息的一方先把消息送到中转站，后续由不同系统按需要取走并处理。

## 2. 为什么系统需要消息队列

以"用户下单"为例，如果没有消息队列，订单服务通常要自己依次调用多个下游服务，例如：

* 库存服务
* 支付服务
* 积分服务
* 短信服务
* 物流服务

这种做法有几个明显问题：

* 一个服务变慢，整条链路就会变慢
* 一个服务异常，主流程可能失败
* 系统之间耦合严重，修改成本高
* 高峰流量容易直接压垮下游服务

引入消息队列之后，订单服务只需要先完成最核心的动作，例如写订单、扣库存、发起支付。至于积分、短信、通知等动作，则可以在订单创建成功后，通过消息异步通知后续系统处理。

**使用消息队列**

```text
用户请求
    ↓
订单服务
    ↓ (库存和支付等核心动作)
消息队列
    ↓        ↓        ↓        ↓
积分服务  短信服务  物流服务  通知服务
```

**不使用消息队列**

```text
用户请求
    ↓
订单服务
    ↓        ↓        ↓        ↓        ↓
库存服务  支付服务  积分服务  短信服务  物流服务
```

从这个例子可以看出，没有消息队列时，订单服务既要处理核心业务，又要兼顾大量后续动作；引入消息队列后，订单服务主要负责核心链路，其他动作则拆分为异步处理，从而使整体系统更加稳定。

## 3. 消息队列中的核心概念

| 术语  | 中文含义 | 直接理解 |
|-----|------|------|
| Producer | 生产者  | 负责发送消息的一方 |
| Consumer | 消费者  | 负责处理消息的一方 |
| Broker | 中间件服务器 | 负责存储和转发消息 |
| Topic / Queue | 主题 / 队列 | 消息的分类方式或存放位置 |
| Partition | 分片   | 把同一类消息拆成多份，提高并发能力 |
| Offset | 消费位点 | 记录消息读到哪里了 |
| ACK | 确认应答 | 告诉中间件"这条消息已经处理完成" |
| Retry | 重试   | 处理失败后再次消费 |
| DLQ | 死信队列 | 多次失败后暂时存放异常消息的位置 |

从消息的生命周期来看，整个过程通常如下：

```text
发送方 (Producer) → 消息中间件 (Broker) → 主题或队列 (Topic/Queue) → 处理方 (Consumer)
                                                                    ↓
                                                              ACK 确认应答
                                                                    ↓
                                                              处理成功？ → 是 → 结束
                                                                    ↓ 否
                                                                  重试 (Retry)
                                                                    ↓
                                                              多次失败 → 死信队列 (DLQ)
```

这张图表达的流程很清楚：


1. 先由生产者发送消息
2. 中间件接收并保存消息
3. 消费者负责处理消息
4. 处理成功后返回确认应答
5. 处理失败后进入重试流程
6. 多次失败后进入死信队列，等待排查或补偿处理

## 4. 三大消息队列的整体印象

在区分三大消息队列之前，先抓住三个关键词：

* **RabbitMQ**：路由灵活
* **Kafka**：吞吐很高
* **RocketMQ**：业务能力较强

换一种更容易理解的说法：

* RabbitMQ 更像一个擅长分拣和转发的业务消息总线
* Kafka 更像一个很能承受流量的日志平台
* RocketMQ 更像一个更贴近订单和交易场景的消息中间件

只要先记住这三个关键词，后面的对比就容易建立整体框架。

## 5. 三者核心对比

下面这张表不需要逐项死记，重点看"各自最擅长什么"。

| 对比维度 | RabbitMQ | Kafka | RocketMQ |
|------|----------|-------|----------|
| 核心定位 | 传统消息队列   | 日志型消息平台 | 业务型消息中间件 |
| 典型场景 | 业务异步、路由分发 | 日志采集、埋点、流处理 | 订单、交易、通知、电商 |
| 吞吐量  | 中等       | 很高    | 高        |
| 路由能力 | 很强       | 较弱    | 中等       |
| 顺序消息 | 支持       | 分片内有序 | 支持       |
| 事务消息 | 一般       | 相对弱   | 较强       |
| 延时消息 | 支持       | 一般    | 较强       |
| 更适合优先考虑 | 灵活路由     | 海量吞吐  | 业务消息     |

从课堂理解角度看，这张表最值得关注的维度主要有四个：

* 吞吐量
* 路由能力
* 顺序消息
* 事务与延时能力

如果进一步压缩成最短记忆法，可以概括为：

* **RabbitMQ 看路由**
* **Kafka 看吞吐**
* **RocketMQ 看业务能力**

## 6. RabbitMQ 怎么理解

RabbitMQ 最值得记住的特点，不是吞吐最高，而是**路由灵活**。

它的核心结构可以概括为：

```text
Producer -> Exchange -> Queue -> Consumer
```

如果换成中文理解，就是：

```text
发送方 -> 交换机 -> 队列 -> 处理方
```

这里最关键的角色是 **Exchange（交换机）**。消息先到交换机，再由交换机根据规则，把消息投递到不同队列。

```text
订单创建 → 交换机 → 积分队列 → 积分服务
                 → 短信队列 → 短信服务
订单支付 → 交换机 → 支付通知队列 → 通知服务
```

例如，"订单创建"这条消息可以同时进入积分队列和短信队列；而"订单支付"这条消息则进入支付通知队列。由此可以看出，RabbitMQ 更关心的是：

* 这条消息应该发给谁
* 是发给一个队列，还是多个队列
* 使用什么规则完成分发

因此，RabbitMQ 的典型特点是：

* 路由能力强
* 功能相对完整
* 可靠性机制成熟
* 适合业务系统中的异步通知和事件分发

RabbitMQ 中常见的交换机类型，也可以直接按中文含义理解：

* **Direct**：直连型，消息类型完全匹配才投递
* **Fanout**：广播型，不看消息类型，直接发给所有绑定队列
* **Topic**：主题型，支持模糊匹配，适合复杂路由
* **Headers**：消息头型，按消息附加属性匹配

所以，RabbitMQ 更适合哪些场景？可以概括为：

* 业务异步通知
* 系统之间的事件分发
* 一个消息需要被多个下游系统处理
* 路由规则比较复杂的业务系统

简单总结就是：只要业务比较在意"消息怎么灵活分发"，RabbitMQ 往往就值得优先考虑。

## 7. Kafka 怎么理解

Kafka 最值得记住的，不是路由，而是它把消息当成了\*\*日志（Log）\*\*来处理。

也就是说，Kafka 不是特别强调一条消息怎么灵活分发，而是更强调：

* 如何把大量消息高效写进去
* 如何让大量消费者高效读出来
* 如何承受很大的数据量和吞吐量

Kafka 中，一类消息会被拆成多个 **Partition（分片）**。每个分片都可以理解成一本只会不断往后追加内容的日志册子。

```text
发送方 → 主题
           ├── 分片 0 → 消费者 1
           ├── 分片 1 → 消费者 2
           └── 分片 2 → 消费者 3
```

Kafka 吞吐高，主要可以从三个角度理解：

* **顺序写入**：消息总是往后追加，写入效率更高
* **批量处理**：不是一条一条处理，而是一批一批处理
* **分片并行**：多个分片可以同时写、同时读

Kafka 还有一个非常重要的概念叫 **Offset（消费位点）**，意思是"当前读到哪里了"。

```text
主题中的某个分片
消费组 A → 位置 0  位置 1  位置 2  位置 3
消费组 B → 位置 0  位置 1  位置 2  位置 3
```

这张图体现了三个特点：

* 不同消费组可以读取同一份数据
* 每个消费组都记录自己的读取位置
* 因此消息可以回放，也就是重新读取历史数据

需要注意的是，Kafka 一般不是"全局有序"，通常只是**分片内有序**。也就是说，同一个分片中的消息顺序能够保证，不同分片之间则不一定严格有序。

所以，Kafka 最适合的场景通常是：

* 日志采集
* 用户埋点
* 实时数仓
* 数据流处理
* 海量消息堆积

简单总结就是：Kafka 最擅长的，是把大量消息当作日志高效存储，再高效地分片消费。

## 8. RocketMQ 怎么理解

RocketMQ 可以理解成一种更偏业务场景的消息队列。

它不像 RabbitMQ 那样把重点放在路由灵活上，也不像 Kafka 那样把重点放在超高吞吐上，它更关注的是：

* 订单场景是否好用
* 交易场景是否好用
* 顺序、事务、延时这些能力是否完整

RocketMQ 的整体结构可以先简化理解为：

```text
发送方 → 路由发现服务 → 消息存储服务 → 主题或消息队列 → 消费方
```

这张图表达的重点并不在于记住每一个组件名称，而在于理解：RocketMQ 既有负责路由发现的部分，也有负责存储和转发消息的部分。

RocketMQ 常见的存储结构，也可以用更直白的方式理解：

* 一部分负责存消息正文
* 一部分负责存消费索引
* 一部分负责做检索

```text
发送方 → 消息日志文件
          ↓
       消费队列索引 → 消费方
          ↓
       检索文件
```

RocketMQ 真正的重点，不是记文件名，而是理解它背后的设计目标：

> 在保证消息存储效率的同时，把业务系统里常用的能力做好。

因此，RocketMQ 的强项通常在这些方面：

* 顺序消息支持较好
* 事务消息支持较好
* 延时消息能力较强
* 比较适合订单、支付、交易、电商链路

例如，电商里有一个典型场景：用户下单后，三十分钟未支付，就自动关闭订单。这种需求本质上就是**延时消息**。又例如，订单状态流转过程中，希望同一个订单的消息按顺序处理，这就是**顺序消息**的典型场景。再例如，希望本地业务和消息发送之间保持更高一致性，就会用到**事务消息**。

所以，RocketMQ 最适合的记忆方式可以概括为：如果系统更像电商、交易、订单系统，那么 RocketMQ 往往会更顺手。

## 9. 三者底层设计思想怎么总结

三者最大的区别，不在于谁更"高级"，而在于它们最初要解决的问题不同。

| 产品  | 更在意什么 | 最容易记住的关键词 |
|-----|-------|-----------|
| RabbitMQ | 消息怎么灵活分发 | 路由        |
| Kafka | 消息怎么高吞吐存储和消费 | 日志        |
| RocketMQ | 业务消息能力是否完整 | 业务能力      |

```text
RabbitMQ  →  复杂分发  →  路由
Kafka     →  海量吞吐  →  日志
RocketMQ  →  订单交易  →  业务能力
```

因此可以把三者概括为：

* **RabbitMQ 是路由型思路**
* **Kafka 是日志型思路**
* **RocketMQ 是业务型思路**

## 10. 怎么选型

真正做选型时，不应该问"哪个最好"，而应该问"哪个最适合当前场景"。

### 10.1 场景 1：订单下单后发短信、发券、发积分

这类场景更偏业务消息，通常优先考虑：

* RabbitMQ
* RocketMQ

因为它们都比较适合业务异步通知。

### 10.2 场景 2：应用埋点、日志采集、实时数仓

这类场景最适合：

* Kafka

因为这些场景更在意吞吐量、堆积能力和数据处理能力。

### 10.3 场景 3：电商交易链路，要求顺序、事务、延时

这类场景优先考虑：

* RocketMQ

因为它在顺序消息、事务消息、延时消息这些方面更贴近业务需求。

### 10.4 场景 4：系统之间做灵活事件分发

这类场景优先考虑：

* RabbitMQ

因为它的路由模型更灵活，一个消息可以根据规则分发给不同下游。

## 11. 引入消息队列后会带来什么问题

消息队列确实能解决解耦、异步、削峰这些问题，但它并不是"引入之后系统就自动变简单"。

原来系统之间是同步调用，问题往往比较直接：调用超时了、接口报错了、链路断了。引入消息队列之后，系统表面上解耦了，但新的问题也随之出现，而且这些问题通常更隐蔽。

最常见的代价主要有下面几类。

### 11.1 系统复杂度上升

原来只有"调用成功"或"调用失败"两种状态，现在会多出很多中间状态，例如：

* 本地业务成功了，但消息没有成功发出去
* 消息发出去了，但消费者还没处理
* 消费者收到了消息，但业务执行失败
* 消费者业务成功了，但确认应答没有返回成功

这意味着，引入消息队列之后，系统不再只是"调接口"，而是变成了"发消息、存消息、消费消息、确认消息、失败重试"这一整套流程。

### 11.2 问题排查更难

同步调用出问题时，通常只要沿着调用链往下查。异步系统出问题时，往往要连续回答下面这些问题：

* 生产者到底有没有发出消息
* 中间件到底有没有收到消息
* 消息是否持久化成功
* 消费者有没有收到消息
* 消费者有没有处理成功
* 失败后有没有重试
* 重试之后为什么还没有成功

也就是说，异步系统一旦出问题，排查链路会明显变长。

### 11.3 一致性问题更复杂

同步调用时，上游系统通常能立刻知道下游是否成功。异步场景下，这种"立刻知道结果"的能力会变弱。

例如，订单服务创建订单成功后，发送一条"订单已创建"的消息，用于通知积分服务加分。这个时候就会出现两个经典问题：

* 订单已经创建成功了，但消息没有发出去
* 消息已经发出去了，但积分服务处理失败了

这也是为什么消息队列经常和"最终一致性"一起出现。它的意思不是所有系统立刻一致，而是允许经过一段时间和补偿之后，最终达到一致。

### 11.4 运维成本会增加

引入消息队列之后，除了业务代码本身，还要关注消息系统运行是否正常，例如：

* 队列长度是否异常增长
* 消费延迟是否过高
* 是否出现大量重试
* 是否出现大量死信消息
* 副本是否同步正常
* 某个节点是否已经不健康

因此，消息队列不是只写代码就结束了，它还需要持续监控和运维。

### 11.5 重复消费、乱序、积压会变得更常见

这些问题在同步接口里也可能存在，但在消息系统里更典型：

* 因为重试机制，消息可能会重复投递
* 因为并发消费，消息可能会乱序
* 因为生产速度过快，消息可能会积压

因此，引入消息队列之后，系统虽然更松耦合了，但对"可靠性设计"和"运维能力"的要求也更高了。

## 12. 如何保证消息可靠性

消息可靠性是消息队列中最核心的问题之一。

很多时候，所谓"消息可靠"，并不是单纯地指"消息发出去了"，而是要同时回答下面四个问题：

* 消息会不会丢
* 消息会不会重复
* 消息顺序会不会乱
* 消费失败后怎么办

如果把一条消息从头到尾看一遍，通常会经历三段链路：


1. 生产者发送消息
2. 中间件保存消息
3. 消费者处理消息

只要这三段中的任何一段出问题，都可能影响可靠性。

### 12.1 如何理解"消息不丢"

"消息不丢"不能只看某一个环节，而要分三段来看。

**第一段：生产者到中间件**

这一段最关键的问题是：生产者以为自己发送成功了，中间件真的收到消息了吗？

如果没有发送确认机制，就可能出现这种情况：

* 生产者发出消息
* 网络中途抖动
* 中间件实际上没有收到
* 但生产者误以为已经发送成功

所以这一段通常需要"发送确认"。也就是说，只有中间件明确回复"我收到了"，生产者才认为发送成功。

**第二段：中间件内部存储**

即使中间件收到了消息，也不等于消息一定安全。因为还可能出现：

* 消息刚收到，还没来得及写入磁盘
* 节点突然宕机
* 这条消息直接丢失

所以中间件这一层通常还需要：

* 持久化
* 副本机制
* 节点故障切换能力

**第三段：中间件到消费者**

这一段的核心问题是：消费者到底有没有真正处理成功？

例如：

* 消费者已经收到消息
* 业务代码刚执行到一半，服务崩了
* 如果这时中间件误以为已经处理完成，就会丢消息

因此，比较合理的做法通常是：

* 先处理业务
* 处理成功后再返回确认应答

也就是说，消息不丢的真正含义是：

> 发送端发得出去，中间件存得住，消费端处理成功之后再确认。

### 12.2 为什么会重复消费

重复消费并不是异常情况，而是消息系统里非常常见的一种现象。

例如下面这个场景：

* 消费者收到消息
* 业务逻辑执行成功
* 但确认应答在网络中丢失
* 中间件以为这条消息还没处理完
* 于是再次投递这条消息

这时，同一条消息就被消费了两次。

因此，大多数消息队列更接近"至少投递一次"，而不是"绝对只投递一次"。

这也是为什么消费端必须考虑**幂等**。

### 12.3 什么叫幂等

幂等的意思是：一条消息处理一次和处理多次，结果应该保持一致。

例如，一条消息表示"订单1001增加100积分"。如果这条消息被重复消费两次，结果就会变成加了 200 积分，这显然是错误的。

为了避免这种问题，消费端通常要做去重或防重处理。常见做法有：

* 根据订单号、消息号、业务流水号去重
* 使用数据库唯一索引做兜底
* 使用 Redis 记录某条消息是否已经处理过

所以可以这样理解：

> 消息队列可以尽量减少消息丢失，但很难保证绝对不重复；重复消费通常要靠业务端幂等来兜住。

### 12.4 顺序消息应该怎么理解

顺序消息最容易被误解成"所有消息天然全局有序"，但实际情况通常不是这样。

更常见的顺序语义是：

* 同一个队列内有序
* 同一个分片内有序
* 同一个业务键有序

例如，订单状态变化通常希望按下面这个顺序执行：


1. 创建订单
2. 支付订单
3. 发货
4. 签收

如果"发货"消息先于"支付"消息被处理，业务结果就会出错。

所以顺序消息真正要保证的，通常不是"整个系统所有消息都排成一条线"，而是：

* 同一个订单号的消息进入同一个队列或分片
* 消费者按顺序处理这类消息
* 重试时不要打乱原有顺序

### 12.5 消费失败后怎么办

消费失败后，通常不会立刻把消息丢掉，而是进入失败处理流程。常见做法有：

* 立即重试
* 延迟一段时间后再重试
* 多次失败后进入死信队列
* 后续由人工补偿或后台任务继续处理

```text
生产者发送消息 → 中间件保存消息 → 消费者处理业务
                                    ↓
                              处理成功 → 返回确认应答
                                    ↓ 失败
                                重试
                                    ↓
                              重试成功 → 结束
                                    ↓ 多次失败
                              进入死信队列
```

这张图表达的逻辑很简单：

* 成功就确认
* 失败就重试
* 重试很多次还不行，就进入死信队列

因此，消息可靠性可以浓缩成一句话：

> 发送要确认，存储要持久，消费要幂等，失败要重试，异常要兜底。

## 13. 三大消息队列的高可用方式

高可用的意思是：某个节点挂掉之后，消息系统不要立刻整体瘫痪，而是还能继续提供服务，或者能尽快恢复服务。

从本质上看，高可用主要依赖两件事：

* 数据不能只放在一个地方
* 某个节点出问题后，系统要能切换到其他可用节点

三大消息队列都在做这两件事，但实现方式不完全一样。

| 消息队列 | 常见高可用方式 | 核心思路 |
|------|---------|------|
| RabbitMQ | 镜像队列、Quorum Queue、集群部署 | 通过多副本保证队列数据可恢复 |
| Kafka | 副本机制、Leader/Follower、ISR | 通过分片副本和主从切换保证可用性 |
| RocketMQ | 主从部署、Broker副本、NameServer集群 | 通过路由发现和主从结构提高高可用性 |

### 13.1 RabbitMQ 的高可用怎么理解

RabbitMQ 的核心思路比较直观：一个队列不要只放在一台机器上，而是尽量有多个副本。

这样做的好处是：

* 某个节点挂了，不至于这条队列的数据直接消失
* 其他副本有机会继续接管服务

可以把它理解成：

* 原来只有一份队列数据，风险集中
* 现在一份队列数据有多份副本，单点故障风险降低

### 13.2 Kafka 的高可用怎么理解

Kafka 的高可用和它的分片结构联系非常紧密。

Kafka 里，每个分片都可以有多个副本：

* 一个副本负责对外读写，叫 **Leader**
* 其他副本负责同步数据，叫 **Follower**

当 Leader 出问题时，会从状态合适的副本中选出新的 Leader。

这意味着，Kafka 的高可用不是"整台机器一起切"，而是围绕"分片副本"来实现的。

例如：

* 一个主题有 3 个分片
* 每个分片有 3 个副本
* 即使某个节点挂了，只要每个分片还有可用副本，整个系统通常还能继续工作

这也是为什么 Kafka 会特别强调副本数量、同步状态和 Leader 切换。

### 13.3 RocketMQ 的高可用怎么理解

RocketMQ 常见的思路是主从部署，再配合路由发现服务。

这背后的意思是：

* 路由信息不能只有一份
* 存消息的节点也不能只有一个
* 某个节点异常之后，系统仍然要能找到其他可用节点

可以把它理解成两层保障：

* 第一层保障是"知道去哪找节点"
* 第二层保障是"找到了节点之后，还有可用副本可以接管"

### 13.4 高可用并不等于绝对无感知

这里还要注意一个常见误区：高可用不等于系统完全无感知，也不等于任何故障都不会影响业务。

高可用真正表达的是：

* 故障发生时，系统尽量不中断
* 即使中断，也能尽快恢复
* 尽量减少消息丢失和服务不可用时间

因此，高可用的目标不是"永远不出问题"，而是"出了问题之后还能扛住并恢复"。

## 14. 消息积压怎么处理

消息积压是生产环境中非常常见的一类问题。

所谓消息积压，本质上就是一句话：

> 生产消息的速度，持续大于消费消息的速度。

只要这种不平衡持续存在，队列里的消息就会越积越多。

### 14.1 先用一个例子理解消息积压

假设某个系统每秒产生 10000 条消息，但消费者每秒只能处理 2000 条消息。那么每过 1 秒，就会多积压 8000 条消息。

如果这种情况持续 10 秒，就会积压 80000 条；持续 1 分钟，就会积压更多。这也是为什么消息积压往往会越积越严重，而不是自己恢复。

### 14.2 为什么会出现消息积压

常见原因主要有下面几类。

**第一类：消费端处理太慢**

例如：

* 消费代码里有复杂数据库操作
* 消费代码里还要远程调用多个下游系统
* 单条消息处理时间过长

这种情况下，消费者不是没工作，而是工作效率太低。

**第二类：消费者数量不够**

如果生产速度已经上来了，但消费者实例数量没有增加，也会造成积压。

例如：

* 高峰期生产量上涨了三倍
* 消费者还是原来那几台机器
* 处理能力跟不上生产速度

**第三类：分片或队列不够**

有些消息队列即使想扩容消费者，也会受到分片数量限制。

例如：

* 只有 2 个分片
* 就算开 10 个消费者，也不可能让所有消费者都同时高效工作

这说明，光加机器不一定够，还要看并行度是否足够。

**第四类：突发流量过高**

像秒杀、促销、热点活动这类场景，短时间内消息量会突然暴涨。即使平时系统没问题，也可能在峰值时出现积压。

### 14.3 消息积压会带来什么影响

消息积压最直接的后果，就是处理延迟越来越大。

例如，本来订单创建后 1 秒内就应该发短信，如果积压严重，可能要几分钟甚至更久。这就会让业务结果明显滞后。

除此之外，还可能带来这些问题：

* 队列长度持续增长
* 磁盘和内存压力增大
* 消费端恢复速度越来越慢
* 严重时影响整个消息系统稳定性

### 14.4 消息积压应该怎么处理

处理积压时，最重要的是先判断瓶颈在哪，再对症下药。

常见方法包括：

* **扩容消费者**：增加消费实例，提高总体处理能力
* **增加分片或队列**：提高并行消费能力
* **优化消费逻辑**：减少慢 SQL、慢接口、重复计算
* **批量消费**：一次处理多条消息，减少开销
* **限流或降级**：控制生产速度，优先保证核心消息
* **旁路处理低优先级消息**：把不紧急的消息暂时分流

### 14.5 如何提前预防消息积压

比起出了问题再补救，更重要的是提前做监控和容量规划。

常见做法有：

* 监控队列长度
* 监控消费延迟
* 监控失败重试次数
* 监控死信队列数量
* 高峰前评估生产速度和消费能力是否匹配

因此，消息积压问题不能只靠"系统自己扛住"，更要靠监控、扩容预案和容量规划提前防范。
