# 接口与测试

## 1. 接口协作

### 为什么要做接口测试？

大家都知道，接口其实就是前端页面或APP等调用与后端做交互用的，所以好多人都会问，我功能测试都测好了，为什么还要测接口呢？OK，在回答这个问题之前，先举个栗子：

比如测试用户注册功能，规定用户名为6\~18个字符，包含字母（区分大小写）、数字、下划线。首先功能测试时肯定会对用户名规则进行测试时，比如输入20个字符、输入特殊字符等，但这些可能只是在前端做了校验，后端可能没做校验，如果有人通过抓包绕过前端校验直接发送到后端怎么办呢？试想一下，如果用户名和密码未在后端做校验，而有人又绕过前端校验的话，那用户名和密码不就可以随便输了吗？如果是登录可能会通过SQL注入等手段来随意登录，甚至可以获取管理员权限，那这样不是很恐怖？

所以，接口测试的必要性就体现出来了：

* 可以发现很多在页面上操作发现不了的bug
* 检查系统的异常处理能力
* 检查系统的安全性、稳定性
* 前端随便变，接口测好了，后端不用变

### 如何进行接口测试


1. **通过性验证**：首先肯定要保证这个接口功能是好使的，也就是正常的通过性测试，按照接口文档上的参数，正常传入，是否可以返回正确的结果。
2. **参数组合**：现在有一个操作商品的接口，有个字段type，传1的时候代表修改商品，商品id、商品名称、价格有一个是必传的，type传2的时候是删除商品，商品id是必传的，这样的，就要测参数组合了，type传1的时候，只传商品名称能不能修改成功，id、名称、价格都传的时候能不能修改成功。
3. **接口安全**：
   * 绕过验证，比如说购买了一个商品，它的价格是300元，那我在提交订单时候，我把这个商品的价格改成3元，后端有没有做验证，更狠点，我把钱改成-3，是不是我的余额还要增加？
   * 绕过身份授权，比如说修改商品信息接口，那必须得是卖家才能修改，那我传一个普通用户，能不能修改成功，我传一个其他的卖家能不能修改成功
   * 参数是否加密，比如说我登陆的接口，用户名和密码是不是加密，如果不加密的话，别人拦截到你的请求，就能获取到你的信息了，加密规则是否容易破解。
   * 密码安全规则，密码的复杂程度校验
4. **异常验证**： 所谓异常验证，也就是我不按照你接口文档上的要求输入参数，来验证接口对异常情况的校验。比如说必填的参数不填，输入整数类型的，传入字符串类型，长度是10的，传11，总之就是你说怎么来，我就不怎么来，其实也就这三种，必传非必传、参数类型、入参长度。

### 1.2 MOCK数据与用例管理

#### 什么是MOCK以及MOCK的作用

Mock是为了解决不同的单元之间由于耦合而难于开发、测试的问题。所以，Mock既能出现在单元测试中，也会出现在集成测试、系统测试过程中。

Mock最大的功能是帮你把单元测试的耦合分解开，如果你的代码对另一个类或者接口有依赖，它能够帮你模拟这些依赖，并帮你验证所调用的依赖的行为。

#### mock数据的创建，使用，管理

以postman为例(其他的测试应用也是同理，包括go-mock包)，在左侧mock servers创建mock实例，也就是一个虚拟接口以及虚拟的响应结果，然后在正常创建mock相关的接口，此时就完成了mock测试的创建，这个mock实例接口的返回数据也就可以用于其他需要这个返回数据的接口。

之后可以在mock servers对mock进行统一的管理与查阅

**切记不可过于依赖mock**，在代码上线之前也应进行真正的测试，mock的东西终究是虚拟的，不能代表实际中的情况

## 2. 单元测试

### 表驱动测试：告别重复，拥抱清晰

传统的单元测试往往需要为每个输入输出组合编写重复的测试代码，导致测试文件冗长且难以维护。Uber Go规范推荐的表驱动测试通过将测试用例组织成结构化数据，显著减少重复代码，同时使测试逻辑更加清晰。

#### 从"Bad"到"Good"：测试重构实例

```go
// 传统重复测试 (Bad)
func TestSplitHostPort(t *testing.T) {
    host, port, err := net.SplitHostPort("192.0.2.0:8000")
    require.NoError(t, err)
    assert.Equal(t, "192.0.2.0", host)
    assert.Equal(t, "8000", port)

    host, port, err = net.SplitHostPort("192.0.2.0:http")
    require.NoError(t, err)
    assert.Equal(t, "192.0.2.0", host)
    assert.Equal(t, "http", port)

    // 更多重复的测试用例...
}

// 表驱动测试 (Good)
func TestSplitHostPort(t *testing.T) {
    tests := []struct{
        give     string
        wantHost string
        wantPort string
    }{
        {
            give:     "192.0.2.0:8000",
            wantHost: "192.0.2.0",
            wantPort: "8000",
        },
        {
            give:     "192.0.2.0:http",
            wantHost: "192.0.2.0",
            wantPort: "http",
        },
        // 简洁添加更多测试用例...
    }

    for _, tt := range tests {
        t.Run(tt.give, func(t *testing.T) {
            host, port, err := net.SplitHostPort(tt.give)
            require.NoError(t, err)
            assert.Equal(t, tt.wantHost, host)
            assert.Equal(t, tt.wantPort, port)
        })
    }
}
```

通过上述对比可见，表驱动测试将测试数据与测试逻辑分离，使测试用例一目了然，新增测试场景时只需添加结构体实例，无需修改测试逻辑。这种模式特别适合验证多种输入组合下的函数行为，如边界条件、异常情况等

#### 表驱动测试的核心要素

* **命名约定**：清晰即王道
* **避免过度复杂**：保持测试简洁。表驱动测试的优势在于简化而非复杂化。当测试用例需要包含条件断言、复杂mock逻辑或函数时，应避免使用表驱动测试，而应拆分为独立的测试函数
* **并行测试**：提升效率的关键技巧。Go 1.7引入的子测试（subtests）功能允许在表驱动测试中实现并行执行，大幅缩短测试套件的运行时间

### 测试夹具

测试夹具（Fixture）在软件测试中是一个非常重要的概念，它指的是为执行测试前准备和配置所需的测试环境。这个环境可能包括一系列预定义的输入数据、模拟对象、数据库配置、文件系统设置或者其他任何为测试准备的步骤。测试夹具的目的是确保测试运行在一个控制和预期的环境中，以便测试结果的可重复性和准确性。在不同的测试框架和编程语言中，测试夹具可能有不同的实现方式和命名，但其核心目的相同。以下是一些常见的测试夹具类型和用法：

#### 初始化和清理

* **设置（SetUp）**：在每个测试用例或一组测试用例开始前执行的代码，用于创建必要的测试环境。这可能包括实例化对象、配置数据库、准备输入数据等。
* **清理（TearDown）**：在每个测试用例或一组测试用例结束后执行的代码，用于清理测试环境，如关闭数据库连接、删除临时数据或回滚测试中做的任何更改。

#### 类型

* **静态/全局夹具**：对所有测试用例只设置一次，通常用于所有测试用例共享的资源或配置。
* **动态/局部夹具**：为每个测试用例或测试组设置，保证了测试之间的隔离，避免了测试之间的相互影响。

#### 在不同环境中的应用

* **数据库测试**：测试夹具可能用于创建临时的数据库表，填充测试数据，执行测试后删除这些临时表，保证测试的独立性。
* **Web 应用测试**：夹具可能包括启动一个本地的开发服务器、配置环境变量或模拟外部服务的响应。
* **智能合约/区块链测试**：夹具用于部署智能合约到一个干净的测试网络，设置初始状态，便于执行特定的合约交互测试。

测试夹具是自动化测试的一个重要组成部分，通过减少测试中的重复设置代码，提高了测试代码的可维护性和可读性。正确使用测试夹具可以大幅度提高测试效率和测试质量。

### 覆盖率


1. **定义**：覆盖率是用来度量测试完整性的一个手段，是测试技术有效性的一个度量。分为：白盒覆盖、灰盒覆盖和黑盒覆盖；测试用例设计不能一味追求覆盖率，因为测试成本随覆盖率的增加而增加。
2. **计算**：覆盖率=(至少被执行一次的item数)/item的总数。
3. **特点**：
   * 通过覆盖率数据，可以检测我们的测试是否充分；
   * 分析出测试的弱点在哪方面；
   * 指导我们设计能够增加覆盖率的测试用例，有效提高测试质量，但是测试用例设计不能一味追求覆盖率，因为测试成本随覆盖率的增加而增加。

#### 黑盒测试

黑盒测试，软件测试的主要方法之一，也可以称为功能测试、数据驱动测试或基于规格说明的测试。测试者不了解程序的内部情况，不需具备应用程序的代码、内部结构和编程语言的专门知识。只知道程序的输入、输出和系统的功能，这是从用户的角度针对软件界面、功能及外部结构进行测试，而不考虑程序内部逻辑结构。测试案例是依应用系统应该做的功能，照规范、规格或要求等设计。测试者选择有效输入和无效输入来验证是否正确的输出。

#### 白盒测试

白盒测试（white-box testing）又称透明盒测试（glass box testing）、结构测试（structural testing）等，软件测试的主要方法之一，也称结构测试、逻辑驱动测试或基于程序本身的测试。测试应用程序的内部结构或运作，而不是测试应用程序的功能（即黑盒测试）。在白盒测试时，以编程语言的角度来设计测试案例。测试者输入资料验证资料流在程序中的流动路径，并确定适当的输出，类似测试电路中的节点。测试者了解待测试程序的内部结构、算法等信息，这是从程序设计者的角度对程序进行的测试。

#### 灰盒测试

灰盒覆盖率


1. **接口覆盖(Interface Coverage)**\n接口覆盖，又称入口点覆盖，要求通过设计一定的用例使得系统的每个接口被测试到。\n接口覆盖=（至少被执行一次的接口数量）/（系统中接口的总数）
2. **函数覆盖(True Coverage)**\n函数覆盖是针对系统或一个子系统的测试的，它表示在该测试中，有哪些函数被测试到了，其被测试到的频率有多大，这些函数在系统所有函数中占的比例有多大，函数覆盖是一个比较容易自动化的技术，同时也易于理解。其公式如下：\n函数覆盖=（至少被执行一次的函数数量）/（系统中函数的总数）

### 基准测试

基准测试属于性能测试的一种，用于评估和衡量软件的性能指标。我们可以在软件开发的某个阶段通过基准测试建立一个已知的性能水平，称为"基准线"。当系统的软硬件环境发生变化之后再进行一次基准测试以确定那些变化对性能的影响。这是基准测试最常见的用途。

#### 使用testing包构建基准测试

Go的tesing包中内置了基准测试功能。在编写基准测试时基本和编写单元测试的原则相似：

* 文件名必须以 `_test.go` 为后缀
* 函数名必须以 `BenchmarkXxxx` 开头
* 基准测试函数的参数类型是 `*Testing.B`，而非 `*Testing.T`

```go
//需要测试函数
func singleFunc() {
    time.Sleep(100 * time.Millisecond)
}
//基准测试代码
func Benchmark_singleFunc(b *testing.B) {
    for n := 0; n < b.N; n++ {
        singleFunc()
    }
}
```

测试结果：


## 3. 性能与压测

### 什么是压测，为什么要进行压测

压测，即压力测试，是确立系统稳定性的一种测试方法，通常在系统正常运作范围之外进行，以考察其功能极限和隐患。是一种评估系统性能和稳定性的方法，通过模拟实际负载条件来测试系统的响应能力。其次，压力测试的目的是发现系统在高负载下的瓶颈和性能问题，以便进行优化和改进。最后，压力测试应该在控制环境中进行，并且需要事先制定明确的测试计划和指标

压测的目的就是通过压测(模拟真实用户的行为)，测算出机器的性能(单台机器的QPS)，从而推算出系统在承受指定用户数(100W)时，需要多少机器能支撑得住\n压测是在上线前为了应对未来可能达到的用户数量的一次预估(提前演练)，压测以后通过优化程序的性能或准备充足的机器，来保证用户的体验。

### 如何进行压测

压测要借助一些工具如hey/vegeta，下面对他们进行介绍：

#### hey

hey 压测工具（通常也被称为 hey 或 go-hey）是一个基于 Go 语言开发的轻量级 HTTP/HTTPS 压测工具，专门用于对 Web 服务（比如后端 API、网站等）进行负载测试，快速评估服务在高并发下的性能表现（比如响应时间、QPS、错误率等）。

**核心特点**

* 轻量高效：基于 Go 语言的并发特性，能生成高并发请求，资源占用低。
* 使用简单：命令行直接调用，参数简洁，不需要复杂配置。
* 输出清晰：测试后会给出请求总数、成功数、QPS、平均响应时间、响应分布（如 P50/P90/P99 等）等关键指标。

#### Vegeta

Vegeta是一款专为HTTP负载测试设计的强大工具，支持通过命令行界面直接操作以及作为开发包集成进项目中。以下是其详细介绍：

**核心特性**：命令行与库双重功能，既可以作为命令行工具直接使用，也能作为Go库集成到其他项目中。其命令行设计遵循UNIX的组合性原则，方便与其他UNIX工具配合使用。在测试过程中能够避免协调遗漏，更准确地模拟实际情况，减少因测试方法不当导致的结果偏差。还可以生成多种格式的详细报告，包括请求总数、速率、吞吐量、延迟、字节输入输出、成功率、状态码分布、错误集合等信息。此外，Vegeta易于进行分布式负载测试，通过简单的配置和组合多个测试节点，可实现大规模的负载模拟。

**安装方式**：提供预编译的可执行文件，支持多种操作系统的包管理器安装方式，也可以从源代码编译安装。例如，macOS系统可使用Homebrew安装，命令为 `brew update && brew install vegeta`；Arch Linux系统可使用 `pacman -S vegeta` 命令安装。

#### vegeta与hey的区别

Vegeta和hey都是基于Go语言开发的HTTP压测工具，它们的区别主要体现在以下几个方面：

* **功能复杂度**：hey的设计较为简单，主要用于快速执行基本的负载测试，适合初学者和简单场景的测试。而Vegeta功能更为复杂和强大，它不仅可以作为命令行工具使用，还能作为Go库集成到项目中，支持自定义请求模式、持续时间测试等更复杂的测试场景。
* **测试灵活性**：hey的测试配置相对简单，通常通过命令行参数进行基本的测试设置。Vegeta则提供了更灵活的配置方式，例如可以通过配置文件设置自定义头部信息，能够同时测试多个端点，还可以在不同主机上并行运行多个测试，增加测试总量。
* **速率控制**：hey支持精确的QPS（每秒查询率）控制，能够更真实地模拟负载。Vegeta的特点是可以以恒定的请求速度请求HTTP服务，这在寻找真正的操作限制时非常关键。
* **输出格式**：hey的输出格式包括摘要和CSV导出，便于自动化处理。Vegeta的输出格式更为丰富，支持Gob、CSV、JSON等多种编码格式，还可以将结果格式化为图表或动态显示当前结果，方便进行更深入的分析。
* **社区支持和流行度**：从GitHub的星数来看，Vegeta的星数相对较高，说明其在社区中更受欢迎，可能有更丰富的资源和案例可供参考。
