# Lesson5 计算机网路基础

## 1. 简介

### 1.1 什么是网络

网络是将世界各地的设备连接起来，并通过一系列事先约定好的规则，使他们之间可以进行信息传递的系统。

### 1.2 网络的分类

目前，我们使用的网络分为 **公网** 和 **私网**，或者你也可以叫 **广域网（WAN）** 和 **局域网（LAN）**。

顾名思义，**公网** 就是所有人都能访问的网络，例如 **红岩官网**，红岩官网的其中一个公网IP是 `222.177.140.110`，我们可以通过 `nslookup redrock.team` 命令来查询红岩官网的解析IP。

而内网，就并非所有人都能访问，当你想访问一个内网时，只有你的设备也处在同一个内网时，你才能访问这个内网内的其他设备，例如 **卷娘的web控制台** ，它的IP是 `172.22.160.216`，我们可以通过 `nslookup console.juan.team` 命令来查询红岩官网的解析IP。

现在就有一个问题了，我用浏览器打开 `222.177.140.110`，可以访问，但是会显示被拦截（这是红岩的WAF和反代的原因，以后会讲）。但是我用浏览器打开 `172.22.160.216` 就会直接超时，这是因为想要访问卷娘，我的电脑得连接红岩的内网才行。

虽然网络分为这两个，但是私网要能上网也同样离不开公网。举个例子，你在私网内访问了红岩的官网，是因为红岩的官网的IP在公网上，对你可见，但是对于红岩服务器来说，你的IP是个私网IP，对在公网中的服务器是不可见的，所以需要一个公网IP来做中转，这就是NAT技术，即网络地址转换技术（Network Address Translation）。

### 1.3 NAT技术简介

你可能要问了，为什么不为互联网上的每个设备都分配一个公网IP地址，非要分公网和私网呢:

1. 安全性上：如果我们都把自己的电脑暴露在公网上，那被黑客攻击的概率就会非常大，很不安全。
2. IPv4的局限性：我刚刚所说的 `222.177.140.110` 和  `172.22.160.216` 这两个IP地址都属于IPv4地址，目前我们上网绝大部分时候依赖的都是IPv4，但由于 IPv4 设计的原因，现在的 IP 地址极其紧缺，所以现在大多数运营商使用 NAT 来中继 IP。

![NAT](./NAT.png)

如图，不同私网（局域网）设备之间不能直接通信，需要 NAT 进行中转。但是同一个局域网中的设备可以使用局域网 IP 直接互相访问。

- *校园网就是一个局域网*
- *127.0.0.1（localhost）为本地 IP，只能本地访问，不能通过网络访问*

## 2. 网络的分层

### 2.1 概述

网络作为一个庞大的系统，各个设备间通信并不是一气呵成的，设备间通信这个流程被拆分成了五个阶段，对应目前被广泛使用的OSI7层模型：
![OSI](./OSI.webp)

但是，目前习惯把 **应用层，表示层，会话层** 合并成 **应用层**，所以OSI七层模型就变成了五层，正好对应设备间通信的五个阶段：

| 层级       | 说明                                                         | 工作协议                                |
| ---------- | ------------------------------------------------------------ | --------------------------------------- |
| 应用层     | Nginx，Openssh，Stalwart这些应用层服务所工作的层级           | HTTP/HTTPS，SSH，SMTP等                 |
| 传输层     | 应用层服务的数据包被加上TCP/UDP的数据贞头，并由操作系统按两种协议自身的约定处理数据包 | TCP，UDP                                |
| 网际层     | 数据包在这层中被加上IP的数据贞头然后被按IP路由，从而使得不同网络间的数据包可以互通 | IP，ICMP                                |
| 数据链路层 | 数据包在这层中被加上ARP数据贞头，ARP贞中的MAC地址决定在同一个局域网内，数据要被发往哪个电脑 | ARP                                     |
| 物理层     | 由各式各样的网络设备组成，负责物理意义上的网络收发           | IEEE 802.3（有线），IEEE 802.11（无线） |

> [!important]
>
> **本节课主要注重Go的网络应用的构建，以及常见的应用层协议，所以我们主要聚焦于应用层以及应用层的基础——传输层，其他层级不是本节课的重点，但是我仍然会用一个通易懂的例子给你们大致讲一下下四层在互联网中的作用**

### 2.2 为什么这样分层

某天，老站长创立了红岩，并购置了两台电脑，他希望他们能相互通信。他想到了用电缆将他们连接起来，这样两台电脑就能互相通信了。但是后来，红岩人气飙升，成员越来越多，需要的电脑变成了两台，三台，十台，二十台，如果他们之间都两两用电缆连接的话，那红岩迟早变成盘丝洞。这时，运维老祖提议，所有电脑只用一根线，接到一个机器上（**集线器**），这个机器接收到其中一个电脑电脑发来的数据包后，会向其他所有电脑原样广播这个数据包，电脑发现这个数据包是自己的话就接收，不是的话就丢弃，从此红岩的网络问题就解决了...吗？

某天，安全老祖意外发现，电脑的网卡有一个模式——混杂模式，这个模式下，电脑不会判断这个数据包是否有属于自己，他会把经过网卡的所有数据包都接收，这样一来安全老祖便可以看整个网络的数据包了，于是他便找到老站长报告了这个安全隐患，并提出了一个解决方法：每台电脑的网卡都有一个唯一的编号——**MAC地址**，我们在集线器上安装一个芯片，让它维护一张表格，这张表格记录了与他连接的每个电脑的网卡MAC地址，并将他们与自己的接口建立了映射关系（这样这个机器就变成了**交换机**）：
|         MAC         |  接口  |
| :-----------------: | :----: |
| `3A:7F:19:C4:B2:8D` | 接口一 |
| `9C:02:E5:6B:41:AF` | 接口二 |
|         ···         |  ···   |

这样一来，这个机器就不会广播数据包，而是定点发送，安全性大大增加。

后来，随着网校规模的不断扩大，我们引进了几台服务器，他们接入了另一个交换机组成了自己的网络，所以红岩访问不了他们，我们只能跑过去，把自己的电脑接在那里调试。但是，为了维护方便，运维小灯们都来求助运维老祖。运维老祖想出了一个办法：分别为红岩工区和服务器机房的每个设备再下发一个编号——**IP地址**，为了区分工区和服务器机房，我们规定工区的IP格式为`172.22.x.x`，服务器机房的IP格式为`172.20.x.x`，然后把两个交换机再连接到一个设备上（**路由器**），这个设备会维护两个表（路由表和ARP表），当工区的运维小灯要连接服务器时，由于机房和红岩不是同一个网络，它的电脑会先把包发给路由器，然后路由器收到这个包后，看了看里面的目标IP地址，然后查了一下自己的路由表，发现这个数据包要从 `172.22.x.x` 到 `172.20.x.x` 的话，自己从第二个网口发出去就行，然后查一下ARP表，发现目的IP对应的MAC是`D8:44:1E:90:7C:52`，于是把数据包内的MAC地址改为了这个，之后数据包便成功送到了目标服务器。

> 这就是 **数据链路层** 和 **网际层** 的工作方式，这两层已经解决了数据包在网络中的传输问题

在这之后，红岩开始做业务了，例如镜像站和掌上重邮。但是，如果按刚刚的方式，那数据包被发送到服务器后，就没有然后了，这样的话一个服务器就只能开一个业务，想开新业务就得买新服务器，但是红岩现在钱包空空，怎么办。后端老祖想出了一个方法，在服务器上再对这些流量进行区分，不同的流量给不同的服务，然后每个服务在服务器上会持有一个自己的代号——**端口**，不同的服务端口不同。这样一来，访问时，客户端只要再在数据包内指定一下端口就行，对前两层毫无影响。在这之后，为了不同的场景，后端老祖又设计出了两种协议：面向连接的TCP协议和面向数据包的UDP协议。在数据查询和远程连接服务器这种不需要高实时性但是需要稳定连接的场景下我们选用带有重传，拥塞控制等能力的TCP连接。在网络游戏，实时直播这类需要高实时性但是可以牺牲部分稳定性的场景下，我们使用UDP协议。

> 到这里 **传输层** 让我们可以按使用场景选择适合的协议，并在操作系统层面完善了计算机的网络能力

有了这些东西，红岩的业务应该能稳步推进了，但是在前后端对接的时候，前端老祖发现了个非常难受的问题，无论是TCP还是UDP，他们的data段传输的都是裸字节，可读性低不说使用起来也非常困难。为了应对这个问题，前端老祖提出了一个解决方案：我们在自己写的程序里面规定出一些大家共同遵守的约定，并把这些规定在裸字节里面写成报文的显示，在传输/接收数据的时候，按这个报文的标准进行编解码。这样一来，每一类服务都有了自己独特的约定，称为应用层协议，常见的应用层协议有：

1. 目前Web服务广泛使用的HTTP/HTTPS，占据80/443端口
2. 连接远程服务器的SSH，占据22端口

3. 将域名解析成IP地址的DNS，占据53端口

> 这就是 **应用层** 的功能，把每种应用所传输的数据按照自己的约定进行组织

所以，总结一下：当你访问一个网站时，请求到达服务器后，Web服务按照HTTP协议组织HTTP报文，然后选用TCP服务进行传输，数据包从80端口发出后，打上路由器的目的MAC和你电脑的目的IP，发送给交换机1，交换机1按照目的MAC与接口的关系将数据包发给路由器，路由器查询路由表和ARP表后，将数据包的目的MAC进行重写，然后从对应的接口发出，数据包到达交换机2后，交换机按照MAC和接口的映射关系发给你的电脑。

## 3. 常见的传输层协议

### 3.1 概述

传输层主要由操作系统实现，应用层通过系统提供的**套接字（Socket）**来使用TCP和UDP这两种协议，所以你写的程序并不需要直接操作网卡这类硬件，只需要操作套接字即可。

### 3.2 TCP

#### 3.2.1 什么是TCP

TCP是目前使用比较广泛的传输层协议，由于其具有面向连接，有序，支持重传，流控等特性，使其具有相对较高的可靠性，所以在文件传输，API访问这类需要强可靠性的场景下，都需要使用到TCP协议，HTTP/HTTPS，SSH，SMTP这些服务都依赖TCP协议。

#### 3.2.2 TCP报文结构

![tcp](./tcp.webp)

- **源端口**：发送方进程的端口，用于接收方回信时知道发给谁
- **目的端口**：接收方进程的端口
- **序列号（seq）**：TCP 是面向字节流的，这个字段表示**本报文段所发送数据的第一个字节的序号**，接收方靠它来排序、去重，以及检测是否有丢包。初始序列号（ISN）在三次握手时随机生成，防止历史报文干扰
- 确认应答号（ack）：客户端期待收到的下一个报文的序列号

> [!important]
>
> **只有当控制位中的 `ACK` 标志位为 1 时，这个字段才有效。**

- **首部长度 (Data Offset/Header Length，4 位)**：表示 TCP 头部一共有多少个 32 位字（即多少行 4 字节）。最大是 15（即 60 字节），最小是 5（即 20 字节）。因为“选项”字段长度可变，所以需要这个字段指明数据从哪里开始
- **保留 (Reserved，6 位)**：目前未使用，置为 0，留给未来扩展用
- **控制位 (Flags，6 位)**：

| 缩写    | 全称               | 说明                                             |
| ------- | ------------------ | ------------------------------------------------ |
| **URG** | **Urgent**         | 紧急指针有效。表示报文中有紧急数据，应优先处理。 |
| **ACK** | **Acknowledgment** | 确认号有效。连接建立后，通常都为 1               |
| **PSH** | **Push**           | 接收方应尽快将数据交给应用层，而不是留在缓冲区   |
| **RST** | **Reset**          | 重置连接。通常用于异常关闭或拒绝连接             |
| **SYN** | **Synchronize**    | 同步序列号。用于**三次握手**建立连接             |
| **FIN** | **Finish**         | 发送方没有数据要发了，用于**四次挥手**关闭连接   |

- **窗口大小 (Window Size，16 位)**：**流量控制**的核心。告诉对端自己的缓冲区还剩多少字节，发送方会根据这个值调整发送速度，防止接收方被压垮
- **校验和 (Checksum，16 位)**：对整个 TCP 报文段（头部+数据）进行校验。如果传输过程中数据损坏，接收方会丢弃该包，等待发送方重传
- **紧急指针 (Urgent Pointer，16 位)**：配合 `URG` 标志使用。指出本报文段中紧急数据的最后一个字节的序号
- **选项 (Options，长度可变)**：TCP 头部最初的规范只定义了 20 字节，后来为了扩展功能加了这个字段。常见的选项有：
  - **MSS (最大报文段长度)**：握手时协商每个包最大能带多少数据
  - **窗口扩大因子**：因为 16 位窗口最大只有 65535 字节，现代网络需要更大窗口，用这个选项把窗口扩大
  - **SACK (选择性确认)**：告诉发送方我收到了哪些不连续的块，避免重复发送
  - **时间戳**：用于更精确地计算 RTT（往返时间）和防止序列号回绕

> [!important]
>
> 注：选项部分必须是 4 字节的整数倍，不足时用填充（Padding）补齐

- **数据 (Data)**：真正的应用层负载（比如 HTTP 请求、图片、音乐等）。TCP 本身不关心这里是什么，只负责可靠地把它搬到对端

#### 3.2.3 建立连接-三次握手

两个客户端在建立TCP连接前，会进行一个特殊阶段——**三次握手**

![TCP三次握手](./TCP三次握手.webp)

1. 第一阶段：客户端向服务端发送`SYN=1, seq=m`，告知服务端我想与你建立TCP连接，并且我的初始序列号是`m`
2. 第二阶段：服务端回复`SYN=1, ACK=1, ack=m+1, seq=n`，告知客户端可以进行连接，我的初始序列号是`n`，我期待你的下一个数据包的序号是`m+1`
3. 第三阶段：客户端回复`ACK=1, ack=n+1`，告知服务端我们已经建立连接，我期待你的下一个数据包的序号是`n+1`

> [!note]
>
> **为什么是三次握手**
>
> - **为了防止旧的重复连接初始化造成混乱**
> - **一来一回，才能确保双方的初始序列号能被可靠的同步**

#### 3.2.4 断开连接-四次挥手

两个客户端在断开TCP连接前，会进行一个特殊阶段——**三次握手**

![TCP四次挥手](./TCP四次挥手.webp)

1. 第一阶段：客户端发送`FIN=1`，告知服务端我希望关闭连接
2. 第二阶段：服务端发送`ACK=1`，告知客户端我知道了，但是先等一下，看看东西发完没有
3. 第三阶段：数据全部发完后，服务端发送`FIN=1`，告知客户端可以断开了
4. 第四阶段：客户端发送`ACK=1`，告知服务端你关闭吧

> [!important]
>
> 之后服务端的TCP连接立刻关闭，而客户端会变为`TIME_WAIT`状态，客户端在经过`2MSL`一段时间后，自动进入 `CLOSE` 状态（`MSL` 是 Maximum Segment Lifetime，即报文最大生存时间，它是任何报文在网络上存在的最长时间，超过这个时间报文将被丢弃）

### 3.3 UDP

#### 3.3.1 什么是UDP

UDP是另一个被广泛使用的传输层协议，其拥有面向数据报，开销小，延迟低，传输效率高的特点，在某些需要强实时性，低延迟，但是不一定要强可靠的场景下（如网络直播，实时游戏对战），会使用UDP协议。

#### 3.3.2 UDP报文结构

![udp](udp.png)

- **IP伪头部**
  - **源地址（32位）**：发送方的 IP 地址
  - **目的地址（32位）**：接收方的 IP 地址
  - **全零（8位）**：填充字段，全部填 0
  - **协议类型（8位）**：标识上层协议，UDP 的协议号是 **17**
  - **UDP报文长度（16位）**：和下面 UDP 头部里的长度字段一模一样

> **为什么需要伪头部？**
> TCP/IP 体系中，IP 层只校验 IP 头部，不校验数据部分。UDP 为了保证数据送达了**正确的主机**和**正确的协议**，在计算校验和时，把源 IP、目的 IP、协议号加进来。如果 IP 地址在传输中被路由错误篡改，校验和就会失败，接收方就能丢弃这个包。

- **UDP头部**
  - **源端口（16位）**：发送方进程的端口号。如果不需要对方回信，可以置为 0。
  - **目的端口（16位）**：接收方进程的端口号（比如 DNS 是 53，DHCP 是 67/68）。
  - **报文长度（16位）**：UDP 头部 + 数据的总长度。**最小值是 8**（只有头部，没有数据），最大值是 65535 字节。
  - **校验和（16位）**：用于检测数据在传输过程中是否损坏。计算时，会把上面的“IP 伪头部” + “UDP 头部” + “数据”全部拼在一起算出一个值。接收方算出来如果不对，通常直接丢弃，**不会像 TCP 那样触发重传**。
  
- **数据（Data）**
  - 长度可变，包含真正的应用层数据（比如 DNS 查询报文、视频帧、游戏坐标等）。
  - UDP 对这部分数据**不做任何切分和重组**，发出去是什么样，接收方读出来就是什么样（保留了消息边界）。

#### 3.3.3 UDP的特点

- **无连接**：不需要三次握手建立连接，也不需要四次挥手断开。想发就发，发包即走。不维护连接状态（如序列号、窗口大小）。
- **不可靠交付（Best-Effort）**：不保证数据到达，不保证按序到达，不保证不重复。如果发生丢包，UDP 本身**不会重传**，应用层如果发现丢了，需要自己决定是否重发。
- **面向数据报（Datagram）**：**保留消息边界**。应用层交下来一个 1000 字节的包，UDP 就加上头部发出去；接收方要么完整收到这 1000 字节，要么一个都收不到，不会像 TCP 那样出现“半包”现象。
- **无流量控制、无拥塞控制**：应用层写多快，UDP 就发多快。即使网络极度拥堵，UDP 也不会降低发送速率。这在带来极低延迟的同时，也容易导致网络雪崩（所以现代协议如 QUIC 必须在 UDP 上自己实现拥塞控制）。
- **支持一对一、一对多、多对多**：支持广播（Broadcast）和多播（Multicast），这是 TCP 做不到的。

## 4. 常见的应用层协议

### 4.1 概述

URL，全称 **Uniform Resource Locator，统一资源定位符**，用来定位互联网上的资源。
通用格式可以简写为：

```
scheme://[userinfo@]host[:port]/path[?query][#fragment]
```

例如：

```
https://user:pass@www.example.com:443/a/b?x=1&y=2#top
```

拆解：

| 部分     | 示例              | 说明                           |
| :------- | :---------------- | :----------------------------- |
| scheme   | `https`           | 协议，决定怎么访问             |
| userinfo | `user:pass`       | 用户名和密码，现代很少用       |
| host     | `www.example.com` | 主机名或 IP                    |
| port     | `443`             | 端口，默认端口可省略           |
| path     | `/a/b`            | 资源路径                       |
| query    | `?x=1&y=2`        | 查询参数                       |
| fragment | `#top`            | 片段，客户端使用，不发给服务器 |

### 4.2 HTTP

#### 4.2.1 HTTP是什么

**HTTP** 是 **HyperText Transfer Protocol** 的缩写，中文叫 **超文本传输协议**。

它是 **Web 的基础通信协议**，规定了 **客户端（如浏览器）和服务器之间如何交换数据**。客户端发送 **HTTP 请求**，服务器返回 **HTTP 响应**。

#### 4.2.2 通用结构

HTTP/1.x 报文是文本格式，由四部分组成：

```
起始行\r\n
头部字段\r\n
\r\n
消息体
```

> [!important]
> 每一行用 CRLF（`\r\n`）分隔；头部和消息体之间的空行也是 `\r\n`。
> 因此，头部结束的标志是 `\r\n\r\n`。

| 元素         | 说明                         |
| :----------- | :--------------------------- |
| **起始行**   | 请求行或状态行               |
| **头部字段** | 若干键值对，如 `Host: a.com` |
| **空行**     | 标志头部结束                 |
| **消息体**   | 实际传输的数据，可为空       |

请求报文的起始行是请求行：

```http
<方法> <请求目标> <HTTP版本>
```

响应报文的起始行是状态行：

```http
<HTTP版本> <状态码> <原因短语>
```

------

#### 4.2.3 请求报文

请求报文由 **请求行、请求头、空行、请求体** 组成。

示例：

```http
POST /api/login HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0
Content-Type: application/json
Content-Length: 35
Connection: keep-alive

{"username":"admin","passwd":"123"}
```

> 注意：`Content-Length` 是请求体的字节数。

**请求行**

格式：

```
<方法> <请求目标> <HTTP版本>\r\n
```

示例：

```http
GET /index.html?q=http HTTP/1.1
```

- 方法：GET、POST、PUT、DELETE、PATCH、HEAD、OPTIONS 等
- 请求目标：通常是 `/path?query`
- HTTP 版本：如 `HTTP/1.1`

**请求方法**

| 方法    | 说明                        | 安全 | 幂等 |
| :------ | :-------------------------- | :--- | :--- |
| GET     | 请求服务器资源              | 是   | 是   |
| HEAD    | 同 GET，但只返回响应头      | 是   | 是   |
| POST    | 向服务器提交数据            | 否   | 否   |
| PUT     | 创建或整体替换资源          | 否   | 是   |
| PATCH   | 部分修改资源                | 否   | 否   |
| DELETE  | 删除服务器上的资源          | 否   | 是   |
| OPTIONS | 查询支持的方法，CORS 预检   | 是   | 是   |
| CONNECT | 建立隧道，常用于 HTTPS 代理 | 否   | 否   |
| TRACE   | 回显请求，用于诊断          | 是   | 是   |

> 常见写法是 `DELETE`，不是 `DEL`。

**请求头**

| 头部              | 作用                   | 示例                                      |
| :---------------- | :--------------------- | :---------------------------------------- |
| Host              | 目标主机和端口         | `Host: www.example.com`                   |
| User-Agent        | 客户端信息             | `User-Agent: Mozilla/5.0`                 |
| Accept            | 能接收的媒体类型       | `Accept: text/html,application/json`      |
| Accept-Language   | 语言偏好               | `Accept-Language: zh-CN,zh;q=0.9`         |
| Accept-Encoding   | 能接收的压缩方式       | `Accept-Encoding: gzip, deflate, br`      |
| Content-Type      | 请求体类型             | `Content-Type: application/json`          |
| Content-Length    | 请求体长度             | `Content-Length: 35`                      |
| Content-Encoding  | 请求体压缩方式         | `Content-Encoding: gzip`                  |
| Cookie            | 携带 Cookie            | `Cookie: sid=abc123`                      |
| Authorization     | 认证信息               | `Authorization: Bearer xxx`               |
| Referer           | 来源页面               | `Referer: https://example.com/`           |
| Origin            | 请求来源，CORS 相关    | `Origin: https://example.com`             |
| Connection        | 连接管理               | `Connection: keep-alive`                  |
| Cache-Control     | 缓存策略               | `Cache-Control: no-cache`                 |
| If-Modified-Since | 条件请求，资源修改时间 | `If-Modified-Since: Tue, 14 Oct 2026 ...` |
| If-None-Match     | 条件请求，ETag 比较    | `If-None-Match: "abc123"`                 |
| Range             | 请求部分内容           | `Range: bytes=0-1023`                     |

**请求体**

请求体不是所有请求都有。GET、HEAD 通常没有；POST、PUT、PATCH 常有。

常见类型：

| Content-Type                        | 说明         |
| :---------------------------------- | :----------- |
| `application/x-www-form-urlencoded` | 普通表单     |
| `multipart/form-data`               | 文件上传表单 |
| `application/json`                  | JSON 数据    |
| `application/xml`                   | XML 数据     |
| `text/plain`                        | 纯文本       |
| `application/octet-stream`          | 二进制流     |

**注意点**

- 请求头和请求体之间必须有一个空行。
- `Content-Length` 和 `Transfer-Encoding: chunked` 通常不同时出现。
- HTTP/1.1 默认持久连接，`Connection: keep-alive` 可省略。
- HTTP/2 中请求报文变成二进制帧，使用伪首部 `:method`、`:path`、`:scheme`、`:authority`。

------

#### 4.2.4 响应报文

响应报文由 **状态行、响应头、空行、响应体** 组成。

示例：

```http
HTTP/1.1 200 OK
Date: Tue, 14 Oct 2026 10:00:00 GMT
Server: nginx
Content-Type: text/plain; charset=utf-8
Content-Length: 13

Hello, world!
```

**状态行**

格式：

```http
<HTTP版本> <状态码> <原因短语>\r\n
```

示例：

```http

```

| 部分     | 说明                        | 示例       |
| :------- | :-------------------------- | :--------- |
| HTTP版本 | 协议版本                    | `HTTP/1.1` |
| 状态码   | 三位数字，表示处理结果      | `200`      |
| 原因短语 | 状态码的可读描述，HTTP/2 无 | `OK`       |

**常见状态码**

| 状态码 | 含义                   | 说明                   |
| :----- | :--------------------- | :--------------------- |
| 100    | Continue               | 继续发送请求体         |

| 201    | Created                | 资源创建成功           |
| 204    | No Content             | 成功，但无响应体       |
| 206    | Partial Content        | 部分内容               |
| 301    | Moved Permanently      | 永久重定向             |
| 302    | Found                  | 临时重定向             |
| 303    | See Other              | 重定向到其他资源       |
| 304    | Not Modified           | 资源未修改，可使用缓存 |
| 307    | Temporary Redirect     | 临时重定向，保持方法   |
| 308    | Permanent Redirect     | 永久重定向，保持方法   |
| 400    | Bad Request            | 客户端请求错误         |
| 401    | Unauthorized           | 未认证                 |
| 403    | Forbidden              | 已认证但无权限         |
| 404    | Not Found              | 资源不存在             |
| 405    | Method Not Allowed     | 请求方法不被允许       |
| 408    | Request Timeout        | 请求超时               |
| 409    | Conflict               | 请求冲突               |
| 413    | Payload Too Large      | 请求体过大             |
| 415    | Unsupported Media Type | 不支持的媒体类型       |

| 500    | Internal Server Error  | 服务器内部错误         |

分类：

- 1xx：信息响应
- 2xx：成功
- 3xx：重定向
- 4xx：客户端错误
- 5xx：服务器错误

**响应头**

| 头部                        | 作用               | 示例                                            |
| :-------------------------- | :----------------- | :---------------------------------------------- |
| Date                        | 响应生成时间       | `Date: Tue, 14 Oct 2026 10:00:00 GMT`           |
| Server                      | 服务器软件信息     | `Server: nginx`                                 |
| Content-Type                | 响应体媒体类型     | `Content-Type: application/json; charset=utf-8` |
| Content-Length              | 响应体长度         | `Content-Length: 13`                            |
| Content-Encoding            | 响应体压缩方式     | `Content-Encoding: gzip`                        |
| Transfer-Encoding           | 传输编码方式       | `Transfer-Encoding: chunked`                    |
| Connection                  | 连接管理           | `Connection: keep-alive`                        |
| Cache-Control               | 缓存策略           | `Cache-Control: max-age=3600`                   |
| ETag                        | 资源标识           | `ETag: "abc123"`                                |
| Last-Modified               | 资源最后修改时间   | `Last-Modified: Tue, 14 Oct 2026 09:00:00 GMT`  |
| Expires                     | 缓存过期时间       | `Expires: Tue, 14 Oct 2026 11:00:00 GMT`        |

| Location                    | 重定向目标地址     | `Location: https://example.com/login`           |

| WWW-Authenticate            | 认证挑战信息       | `WWW-Authenticate: Bearer`                      |
| Vary                        | 缓存键参考的请求头 | `Vary: Accept-Encoding`                         |
| Retry-After                 | 建议重试等待时间   | `Retry-After: 120`                              |

**响应体**

响应体可以是：

- HTML：`text/html`
- JSON：`application/json`
- XML：`application/xml`
- 纯文本：`text/plain`
- CSS、JavaScript
- 图片、音频、视频
- 二进制文件流

以下情况通常没有响应体：

- `HEAD` 请求的响应
- `204 No Content`
- `304 Not Modified`
- `1xx` 信息响应

**注意点**

- 响应头和响应体之间必须有一个空行。
- `Content-Length` 和 `Transfer-Encoding: chunked` 通常不同时出现。
- HTTP/1.x 有原因短语；HTTP/2 没有原因短语，状态码在 `:status` 伪首部中。
- 响应头字段名不区分大小写，HTTP/2 中要求全小写。
- `Content-Type` 告诉客户端如何解析响应体，例如 `application/json`、`text/html`、`image/png`。
- 重定向响应常用 `Location` 指定新地址；`304` 响应通常配合 `ETag`、`Last-Modified` 做缓存校验。

### 4.3 TLS

#### 4.2.1 TLS是什么

TLS 是一种旨在保护互联网通信安全的加密和身份验证协议。当你访问一个HTTPS网站时，你的浏览器便会触发TLS握手过程，以便建立加密的隧道来传输明文HTTP流量，也就是说 **HTTPS = HTTP over TLS**，即将明文HTTP流量通过TLS建立的加密隧道进行传输，从而进一步提升安全性。

> [!important]
>
> 这里，我们着重介绍TLS的握手流程，也是面试里面经常会被问到的东西

#### 4.2.2 对称加密与非对称加密和证书

- 发送方和接收方共用同一套规规则对数据包进行加解密，这样的加密方式称为**对称加密**，常见的有：AES
- 发送方持有一把公钥，接收方持有一把对应的私钥，发送方使用公钥加密的数据只有使用对应的私钥才能解密，接收方使用私钥加密的数据任何持有公钥的一方都能验证，这就是**非对称加密**，常见的有：RSA

> 举个非对称加密的例子，服务器同时持有 公钥 和 私钥，当与客户端通信时，他便公布自己的公钥给客户端，客户端使用公钥加密数据，然后发回服务器，这样一来，只有服务器才能用自己的私钥对数据进行解密

- SSL证书可以理解为非对称加密里这对公钥+私钥的具体体现，但是有个很特殊的地方，SSL证书是经过 Certificate Authority 证书授权中心颁发的，是可信的，这样一来，当你的浏览器识别到下发的证书不是第三方授权机构颁发的时，他就会提示你，这就可以防止你被假冒的网站的假公钥诈骗，从而发送自己的隐私数据给对方

#### 4.2.3 TLS握手流程

1. [客户端 - 服务器] 客户端发送Client Hello给服务器，并告知服务端自己支持的TLS版本和支持的密码套件列表，然后生成一个随机数给服务端
2. [服务器 - 客户端] 服务端发送Server Hello给客户端，告知客户端确认的TLS版本和选择的密码套件，并且服务器也会生成一个随机数给客户端
3. [服务器 - 客户端] 服务器向客户端发送自己的SSL证书，以便客户端查询自己的信任列表确认服务器是否可信
4. [服务器 - 客户端] 服务器执行Server Key Exchange这里把自己的公钥给客户端（如果服务器需要客户端也提供自己的证书进行mTLS，那也会在这个响应内说明）

> [!important]
>
> 注意：服务器发证书和公钥使用了两个请求

5. [服务器 - 客户端] OK，现在服务器发东西发完了，发送这阶段最后一个数据包：Server Hello Down
6. [客户端 - 服务器] 客户端执行Client Key Exchange，生成第三个随机数并使用刚刚服务器给的公钥进行加密，称为**预主密钥**，然后发还给服务器
7. [客户端 - 服务器] 客户端进行Change Cipher Spec，确认密码套件和密钥
8. [客户端 - 服务器] 客户端发送Encrypted Handshake Message，向服务器发起握手
9. [服务器 - 客户端] 服务器回复Encrypted Handshake Message，双方握手成功，**TLS通道建立**

### 4.4 DNS

#### 4.4.1 DNS是什么

DNS 是 **Domain Name System**，中文叫 **域名系统**。它的核心作用是把人类容易记住的**域名**翻译成机器能路由的 **IP 地址**，比如把 `redrock.team` 解析成 `222.177.140.110`。

DNS 是一个**分布式、层级化的数据库**，也是应用层协议。默认使用 **UDP 53** 端口；区域传送、响应过大等情况会用 **TCP 53**；现代还有 **DoT（TLS 853）** 和 **DoH（HTTPS 443）** 来加密 DNS 查询。

> [!important]
>
> 面试常问：DNS 解析流程、递归查询与迭代查询、DNS 缓存、常见记录类型。

一句话理解：

**HTTP 负责传网页，TLS 负责加密，DNS 负责先找到服务器在哪。**

#### 4.4.2 域名结构、DNS记录和服务器

**域名结构**

域名是从右到左分层的：

```
www . example . com .
子域   二级域   顶级域  根域
```

- 根域：`.`
- 顶级域 TLD：`com`、`org`、`cn`
- 二级域：`example.com`
- 子域：`www.example.com`

**常见 DNS 记录类型**

| 记录类型 | 作用                       | 示例                              |
| :------- | :------------------------- | :-------------------------------- |
| A        | 域名指向 IPv4 地址         | `example.com -> 93.184.216.34`    |
| AAAA     | 域名指向 IPv6 地址         | `example.com -> 2606:2800::1`     |
| CNAME    | 域名别名                   | `www.example.com -> example.com`  |
| MX       | 邮件服务器                 | `example.com -> mail.example.com` |
| NS       | 该域名的权威 DNS 服务器    | `example.com -> ns1.example.com`  |
| TXT      | 文本记录，常用于验证       | SPF、DKIM、域名所有权验证         |
| SOA      | 起始授权记录，区域管理信息 | 主 NS、序列号、刷新时间等         |
| PTR      | 反向解析，IP 查域名        | `34.216.184.93 -> example.com`    |

**DNS 服务器类型**

| 类型                  | 作用                                                        |
| :-------------------- | :---------------------------------------------------------- |
| 本地 DNS / 递归解析器 | 接收客户端请求，帮客户端查到底，如 8.8.8.8、114.114.114.114 |
| 根域名服务器          | 知道顶级域服务器在哪，如 `.com`、`.cn` 去哪问               |
| 顶级域名服务器        | 知道二级域的权威服务器在哪                                  |
| 权威域名服务器        | 保存某个域名的最终解析记录，如 `example.com` 的 A 记录      |

------

#### 4.4.3 DNS解析流程

以客户端访问 `www.example.com` 为例，类比 TLS 握手，可以写成下面几步：

1. **[客户端 → 本地 DNS] 客户端发起递归查询**
   客户端问本地 DNS：“`www.example.com` 的 IP 是多少？”
   在问之前，通常会先查：

   - 浏览器缓存
   - 操作系统缓存
   - `hosts` 文件
     如果都没有，才向本地 DNS 服务器发起查询。

2. **[本地 DNS → 客户端] 本地 DNS 先查缓存**
   本地 DNS 如果有缓存且未过期，直接返回 IP。
   如果没有，就开始向上游查询。

3. **[本地 DNS → 根 DNS] 迭代查询根服务器**
   本地 DNS 问根服务器：“`www.example.com` 的 IP 是多少？”
   根服务器不知道具体 IP，但会告诉它：“你去问 `.com` 顶级域服务器。”

4. **[本地 DNS → 顶级域 DNS] 迭代查询 TLD 服务器**
   本地 DNS 问 `.com` 顶级域服务器。
   TLD 服务器也不知道具体 IP，但会告诉它：“你去问 `example.com` 的权威 DNS 服务器。”

5. **[本地 DNS → 权威 DNS] 迭代查询权威服务器**
   本地 DNS 问 `example.com` 的权威 DNS。
   权威 DNS 返回最终记录，比如：

   ```
   www.example.com -> 93.184.216.34
   ```

6. **[本地 DNS → 客户端] 返回结果并缓存**
   本地 DNS 把 IP 返回给客户端，并根据 TTL 缓存这个结果。
   下次再有客户端问同一个域名，就可以直接返回。

7. **[客户端 → Web 服务器] 建立连接**
   客户端拿到 IP 后，向该 IP 发起 TCP 连接，然后进行 TLS 握手，最后发送 HTTP 请求。

> [!important]
>
> **递归查询**：客户端只问一次，本地 DNS 负责查到底。
> **迭代查询**：本地 DNS 逐级去问根、顶级域、权威服务器，每次拿到下一跳地址。

------

#### 4.4.4 缓存与安全

**缓存**

DNS 查询结果会按 **TTL** 缓存，常见位置：

- 浏览器缓存
- 操作系统缓存
- 本地 DNS 缓存
- 权威 DNS 也可能有缓存

TTL 越短，更新越快，但查询压力越大；TTL 越长，解析越快，但变更生效越慢。

**常见安全问题**

| 问题         | 说明                           |
| :----------- | :----------------------------- |
| DNS 劫持     | 篡改解析结果，把用户带到假网站 |
| DNS 污染     | 伪造 DNS 响应，返回错误 IP     |
| DNS 放大攻击 | 利用 DNS 响应放大流量攻击目标  |
| 隐私泄露     | 明文 DNS 查询可能被中间人看到  |

**防护手段**

- **DNSSEC**：给 DNS 记录做数字签名，防止篡改
- **DoT**：DNS over TLS，用 TLS 加密 DNS
- **DoH**：DNS over HTTPS，用 HTTPS 加密 DNS

## 5. Go 标准库 `net` 包

### 5.1 概述

`net` 是 Go 标准库中网络编程的核心包，提供网络地址、TCP/UDP 连接、监听器、DNS 查询以及网络接口等功能。

### 5.2 核心网络接口

`net` 中常见的接口包括 `Addr`、`Conn`、`Listener` 和 `PacketConn`。

#### 5.2.1 `net.Addr`

```go
type Addr interface {
    Network() string
    String() string
}
```

- `Network()`：返回网络类型，例如 `"tcp"`、`"udp"` 或 `"unix"`。
- `String()`：返回地址的字符串表示。

`Addr` 是一个通用接口，具体类型可能是 `*net.TCPAddr`、`*net.UDPAddr`、`*net.IPAddr` 或 `*net.UnixAddr`。

#### 5.2.2 `net.Conn`

```go
type Conn interface {
    Read(b []byte) (n int, err error)
    Write(b []byte) (n int, err error)
    Close() error
    LocalAddr() Addr
    RemoteAddr() Addr
    SetDeadline(t time.Time) error
    SetReadDeadline(t time.Time) error
    SetWriteDeadline(t time.Time) error
}
```

`Conn` 表示面向连接的双向通信通道，常用于 TCP 和 Unix Domain Socket。

- `Read` / `Write`：读取或发送数据。
- `LocalAddr` / `RemoteAddr`：获取本地和远端地址。
- `SetDeadline`：同时设置读写截止时间。
- `SetReadDeadline` / `SetWriteDeadline`：分别设置读、写截止时间。

注意：`Read` 一次不一定读完所有预期数据；TCP 是字节流协议，不保留应用层消息边界。

#### 5.2.3 `net.Listener`

```go
type Listener interface {
    Accept() (Conn, error)
    Close() error
    Addr() Addr
}
```

`Listener` 用于接收新的连接，常见于 TCP 服务端。`Accept()` 会等待并返回一个新连接，直到连接到达或监听器关闭、发生错误。

#### 5.2.4 `net.PacketConn`

```go
type PacketConn interface {
    ReadFrom(b []byte) (n int, addr Addr, err error)
    WriteTo(b []byte, addr Addr) (n int, err error)
    Close() error
    LocalAddr() Addr
    SetDeadline(t time.Time) error
    SetReadDeadline(t time.Time) error
    SetWriteDeadline(t time.Time) error
}
```

`PacketConn` 面向数据报通信，常用于 UDP。与 TCP 字节流不同，UDP 保留数据报边界，但不保证数据一定送达、按序到达或只到达一次。

---

### 5.3 IP 地址操作

Go 中有两套常见的 IP 地址表示方式：

| 类型         | 所属包      | 特点                            |
| ------------ | ----------- | ------------------------------- |
| `net.IP`     | `net`       | 底层是 `[]byte`，属于较早的 API |
| `netip.Addr` | `net/netip` | 值类型、不可变，适合新代码      |

新代码优先选择 `netip.Addr`。它可直接比较，也可以作为 `map` 的 key，使用起来更适合 IP 白名单、路由规则和地址缓存。

#### 5.3.1 `net.ParseIP`

函数签名：

```go
func ParseIP(s string) IP
```

`net.ParseIP` 将字符串解析为 IP 地址。解析失败时返回 `nil`，不会返回 `error`。它**不会查询 DNS**，因此传入域名时不会自动解析为 IP。

```go
package main

import (
    "fmt"
    "net"
)

func main() {
    tests := []string{
        "172.22.160.211",
        "240e:330:20ba:5f00:8347:9b2a:bea2:6b6c",
        "redrock.team",
    }

    for _, s := range tests {
        ip := net.ParseIP(s)
        fmt.Printf("input=%q ip=%v isNil=%t\n", s, ip, ip == nil)
    }
}
```

```
input="172.22.160.211" ip=172.22.160.211 isNil=false
input="240e:330:20ba:5f00:8347:9b2a:bea2:6b6c" ip=240e:330:20ba:5f00:8347:9b2a:bea2:6b6c isNil=false
input="redrock.team" ip=<nil> isNil=true
```

注意：`net.IP` 是字节切片。通过 `net.ParseIP` 解析 IPv4 地址时，结果通常使用 16 字节的 IPv4-mapped 表示，因此不要假设 `len(ip) == 4`。如果需要判断或取得 IPv4 表示，可以使用 `ip.To4()`。

#### 5.3.2 `netip.ParseAddr`

函数签名：

```go
func ParseAddr(s string) (Addr, error)
```

`netip.ParseAddr` 是现代 Go 代码中更推荐的 IP 解析 API。解析失败时会返回错误，调用方可以明确处理非法输入。

```go
package main

import (
    "fmt"
    "net/netip"
)

func main() {
    tests := []string{
        "172.22.160.211",
        "127.0.0.1",
        "240e:330:20ba:5f00:8347:9b2a:bea2:6b6c",
        "redrock.team",
    }

    for _, s := range tests {
        ip, err := netip.ParseAddr(s)
        if err != nil {
            fmt.Printf("%q: invalid IP: %v\n", s, err)
            continue
        }

        fmt.Printf(
            "%s: IPv4=%t IPv6=%t private=%t loopback=%t\n",
            ip, ip.Is4(), ip.Is6(), ip.IsPrivate(), ip.IsLoopback(),
        )
    }
}
```

```
172.22.160.211: IPv4=true IPv6=false private=true loopback=false
127.0.0.1: IPv4=true IPv6=false private=false loopback=true
240e:330:20ba:5f00:8347:9b2a:bea2:6b6c: IPv4=false IPv6=true private=false loopback=false
"redrock.team": invalid IP: ParseAddr("redrock.team"): unexpected character (at "redrock.team")
```

常用方法：

| API                 | 含义                                             |
| ------------------- | ------------------------------------------------ |
| `Is4()`             | 是否为 IPv4                                      |
| `Is6()`             | 是否为 IPv6                                      |
| `Is4In6()`          | 是否为 IPv4-mapped IPv6，例如 `::ffff:192.0.2.1` |
| `IsPrivate()`       | 是否属于定义的私有地址范围                       |
| `IsLoopback()`      | 是否为环回地址，例如 `127.0.0.1`、`::1`          |
| `IsUnspecified()`   | 是否为未指定地址，例如 `0.0.0.0`、`::`           |
| `IsGlobalUnicast()` | 是否属于全局单播地址类别                         |
| `Zone()`            | 获取 IPv6 zone，例如 `fe80::1%eth0` 中的 `eth0`  |
| `Unmap()`           | 将 IPv4-mapped IPv6 地址转换为普通 IPv4 地址     |

**安全提示：** `IsGlobalUnicast()` 不等于“该 IP 一定能从公网访问”。私有地址及部分特殊用途地址也可能满足这个判断，不能单独用它实现公网 IP 安全校验。

#### 5.3.3 `netip.Addr.AsSlice` 与 `netip.AddrFromSlice`

这两个 API 用于在 `netip.Addr` 与字节切片之间转换：

```go
package main

import (
    "fmt"
    "net/netip"
)

func main() {
    ip := netip.MustParseAddr("172.22.160.211")

    raw := ip.AsSlice()
    fmt.Println(raw) // [172 22 160 211]

    restored, ok := netip.AddrFromSlice(raw)
    fmt.Println(restored, ok) // 172.22.160.211 true
}
```

```
[172 22 160 211]
172.22.160.211 true
```

`AsSlice()` 对 IPv4 返回 4 字节，对 IPv6 返回 16 字节。`AddrFromSlice()` 接受长度为 4 或 16 的切片；无法转换时，`ok` 为 `false`。

如果只需要比较 IP、判断网段或打印地址，通常不需要将地址转换为字节切片。

#### 5.3.4 `netip.AddrPort`

`netip.AddrPort` 用于表示 IP 地址和端口的组合：

```go
package main

import (
    "fmt"
    "net/netip"
)

func main() {
    ipv4 := netip.MustParseAddrPort("172.22.160.211:8090")
    ipv6 := netip.MustParseAddrPort("[2001:db8::1]:443")

    fmt.Println(ipv4.Addr(), ipv4.Port()) // 172.22.160.211 8090
    fmt.Println(ipv6.Addr(), ipv6.Port()) // 2001:db8::1 443
}
```

```
172.22.160.211 8090
2001:db8::1 443
```

IPv6 地址与端口组合时，地址必须使用方括号包围，例如 `[2001:db8::1]:443`。解析不可信输入时，使用 `netip.ParseAddrPort` 并检查错误；只有确定输入合法时才使用 `MustParseAddrPort`。

### 5.4 CIDR 网段操作

CIDR 使用“IP 地址/前缀长度”的形式表示一个网段，例如 `192.168.1.0/24`。前缀长度表示网络部分所占的位数。

常见用途：

- 判断客户端 IP 是否位于授权网段。
- 实现 IP 白名单或黑名单。
- 匹配 Kubernetes、VPN 或虚拟网络中的地址范围。
- 根据目标 IP 选择代理或路由规则。

#### 5.4.1 `netip.ParsePrefix`

函数签名：

```go
func ParsePrefix(s string) (Prefix, error)
```

示例：

```go
package main

import (
    "fmt"
    "net/netip"
)

func main() {
    prefix, err := netip.ParsePrefix("172.22.160.1/24")
    if err != nil {
        panic(err)
    }

    fmt.Println(prefix.Addr())  // 172.22.160.1
    fmt.Println(prefix.Bits())  // 24
    fmt.Println(prefix.Masked()) // 172.22.160.0/24
}
```

```
172.22.160.1
24
172.22.160.0/24
```

**重要：** `ParsePrefix` 不会自动清零主机位。`172.22.160.1/24` 解析后仍保留原始地址；调用 `Masked()` 才会得到规范化网段 `172.22.160.0/24`。

在保存或比较网段规则时，通常应先调用 `Masked()`。

#### 5.4.2 `Prefix.Contains`

`Contains` 用于判断一个 IP 是否属于某个网段：

```go
package main

import (
    "fmt"
    "net/netip"
)

func main() {
    prefix := netip.MustParsePrefix("192.168.1.0/24")
    ip1 := netip.MustParseAddr("192.168.1.100")
    ip2 := netip.MustParseAddr("192.168.2.100")

    fmt.Println(prefix.Contains(ip1)) // true
    fmt.Println(prefix.Contains(ip2)) // false
}
```

```
true
false
```

IPv4 网段不会匹配 IPv6 地址，IPv6 网段也不会匹配普通 IPv4 地址。如果输入可能包含 IPv4-mapped IPv6 地址，建议在进入匹配逻辑前统一调用 `Unmap()`。

#### 5.4.3 常用 `netip.Prefix` 方法

| API            | 含义                       |
| -------------- | -------------------------- |
| `Addr()`       | 返回前缀中保存的地址       |
| `Bits()`       | 返回前缀长度               |
| `Masked()`     | 清零主机位，返回规范化网段 |
| `Contains(ip)` | 判断地址是否属于该前缀     |
| `IsValid()`    | 判断前缀是否有效           |
| `IsSingleIP()` | 判断前缀是否表示单个 IP    |

#### 5.4.4 判断两个网段是否重叠

标准库没有直接提供 `Prefix.Overlaps()`。可以通过判断一个网段是否包含另一个网段的起始地址来实现：

```go
func PrefixesOverlap(a, b netip.Prefix) bool {
    if !a.IsValid() || !b.IsValid() {
        return false
    }

    a = a.Masked()
    b = b.Masked()

    // IPv4 与 IPv6 网段不重叠。
    if a.Addr().Is4() != b.Addr().Is4() {
        return false
    }

    return a.Contains(b.Addr()) || b.Contains(a.Addr())
}
```

示例：

```go
a := netip.MustParsePrefix("192.168.1.0/24")
b := netip.MustParsePrefix("192.168.1.128/25")
c := netip.MustParsePrefix("192.168.2.0/24")

fmt.Println(PrefixesOverlap(a, b)) // true
fmt.Println(PrefixesOverlap(a, c)) // false
```

```
true
false
```

### 5.5 DNS 解析

DNS 将域名解析为 IP 地址，或查询域名关联的其他记录。`net` 提供了多种高级查询 API。

#### 5.5.1 `net.LookupHost`

```go
addrs, err := net.LookupHost("redrock.team")
if err != nil {
    panic(err)
}

for _, addr := range addrs {
    fmt.Println(addr)
}
```

```
222.177.140.110
```

`LookupHost` 返回字符串形式的地址，结果可能同时包含 IPv4 和 IPv6。它不提供 `context` 参数；需要控制查询超时或取消时，建议使用 `net.Resolver`。

#### 5.5.2 `Resolver.LookupNetIP`

新代码更推荐使用 `LookupNetIP`，它返回 `[]netip.Addr`，并支持 `context`：

```go
package main

import (
    "context"
    "fmt"
    "net"
    "time"
)

func main() {
    ctx, cancel := context.WithTimeout(
        context.Background(),
        3*time.Second,
    )
    defer cancel()

    resolver := &net.Resolver{}
    ips, err := resolver.LookupNetIP(ctx, "ip", "redrock.team")
    if err != nil {
        panic(err)
    }

    for _, ip := range ips {
        fmt.Printf("%s IPv4=%t IPv6=%t\n", ip, ip.Is4(), ip.Is6())
    }
}
```

```
222.177.140.110 IPv4=true IPv6=false
```

`network` 参数支持：

- `"ip"`：查询 IPv4 和 IPv6。
- `"ip4"`：只查询 IPv4。
- `"ip6"`：只查询 IPv6。

#### 5.5.3 分别查询 IPv4 与 IPv6

如果业务只接受某一种地址族，可以通过 `LookupNetIP` 的 `network` 参数指定查询类型：

```go
ipv4, err := net.DefaultResolver.LookupNetIP(
    context.Background(),
    "ip4",
    "redrock.team",
)
if err != nil {
    panic(err)
}

ipv6, err := net.DefaultResolver.LookupNetIP(
    context.Background(),
    "ip6",
    "redrock.team",
)
if err != nil {
    panic(err)
}

fmt.Println("IPv4:", ipv4)
fmt.Println("IPv6:", ipv6)
```

- `"ip4"` 只查询 IPv4 地址，通常对应 DNS A 记录。
- `"ip6"` 只查询 IPv6 地址，通常对应 DNS AAAA 记录。
- `"ip"` 同时查询 IPv4 和 IPv6 地址。

注意：DNS 记录是否存在、解析器的返回顺序以及系统网络环境都会影响结果；不要假设每个域名都同时拥有 A 和 AAAA 记录。

#### 5.5.4 反向解析与其他记录查询

除了将域名解析为 IP，`net` 也提供了常见的反向解析和服务发现接口：

```go
ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
defer cancel()

resolver := net.DefaultResolver

// 反向 DNS：查询 IP 对应的 PTR 记录
names, err := resolver.LookupAddr(ctx, "8.8.8.8")
if err != nil {
    fmt.Println("reverse lookup failed:", err)
} else {
    fmt.Println("PTR:", names)
}

// 查询域名的规范名称（CNAME）
cname, err := resolver.LookupCNAME(ctx, "www.example.com")
if err != nil {
    fmt.Println("CNAME lookup failed:", err)
} else {
    fmt.Println("CNAME:", cname)
}

// 查询邮件服务器（MX）
mx, err := resolver.LookupMX(ctx, "example.com")
if err != nil {
    fmt.Println("MX lookup failed:", err)
} else {
    for _, record := range mx {
        fmt.Printf("MX host=%s preference=%d\n", record.Host, record.Pref)
    }
}
```

```
PTR: [dns.google.]
CNAME: www.example.com.
MX host=. preference=0
```

`LookupAddr` 是反向 DNS 查询，不是可靠的身份认证手段：PTR 记录可能不存在，也不能单凭反向解析结果确认对端身份。`LookupCNAME` 返回规范名称查询结果；如果域名没有 CNAME 链，返回值也可能是原始名称的规范化形式。

#### 5.5.5 DNS 解析器的选择与系统配置

```go
resolver := &net.Resolver{
    PreferGo: true,
}
```

`PreferGo: true` 表示优先使用 Go 实现的解析器，但**不会自动指定公共 DNS 服务器**。Go 解析器通常仍会读取系统的 DNS 配置；系统配置、`hosts` 文件、运行环境和 Go 版本都可能影响解析路径。

如果要明确指定 DNS 服务器，可设置 `Resolver.Dial`：

```go
resolver := &net.Resolver{
    PreferGo: true,
    Dial: func(ctx context.Context, network, _ string) (net.Conn, error) {
        d := net.Dialer{Timeout: 3 * time.Second}
        return d.DialContext(ctx, network, "10.0.0.53:53")
    },
}

ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()

ips, err := resolver.LookupNetIP(ctx, "ip", "example.com")
if err != nil {
    panic(err)
}
fmt.Println(ips)
```

将 `10.0.0.53:53` 替换为实际可达的 DNS 服务器。自定义 `Dial` 会让解析器通过指定目标发送 DNS 请求；应确保该服务器支持所需的查询，并且网络策略允许访问。此示例用于说明配置方式，实际部署还需要考虑 UDP/TCP 可达性和 DNS 服务器故障。

#### 5.5.6 超时、错误处理与缓存

DNS 查询可能失败或超时。处理外部域名时，建议传入有期限的 `context`，并根据业务决定重试、降级或返回错误：

```go
ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel()

ips, err := net.DefaultResolver.LookupNetIP(ctx, "ip", "example.com")
if err != nil {
    if ctx.Err() == context.DeadlineExceeded {
        fmt.Println("DNS lookup timed out")
    } else {
        fmt.Println("DNS lookup failed:", err)
    }
    return
}

fmt.Println(ips)
```

标准库 `net.Resolver` 不提供可直接配置 TTL 的通用 DNS 缓存接口。系统解析器、操作系统服务或上游 DNS 服务器可能有自己的缓存行为；如果应用需要按 TTL 缓存结果，应明确设计缓存策略，并注意 DNS 记录变化、负缓存和失效时间。

#### 5.5.7 DNS 解析不等于连接

下面两种操作的职责不同：

```go
// 只解析域名，得到 IP 地址
ips, err := net.DefaultResolver.LookupNetIP(ctx, "ip", "example.com")

// 解析域名并尝试建立 TCP 连接
conn, err := net.DialTimeout("tcp", "example.com:443", 3*time.Second)
if err == nil {
    defer conn.Close()
}
```

`LookupNetIP` 只负责名称解析，不会建立业务连接。`net.Dial` / `net.Dialer` 使用域名建立连接时，通常会在连接过程中触发解析，并继续尝试连接解析出的地址。

解析成功不代表目标端口可达；连接失败也不一定是 DNS 问题，还可能是路由、防火墙、端口监听或 TLS 等环节导致。DNS 指定服务器与连接出口网卡是两个独立问题：前者影响域名解析，后者由路由和连接配置决定。

#### 5.5.8 常用 DNS 查询 API

| API                    | 用途                                       |
| ---------------------- | ------------------------------------------ |
| `LookupHost`           | 将主机名解析为地址字符串                   |
| `LookupIP`             | 将主机名解析为 `[]net.IP`                  |
| `Resolver.LookupNetIP` | 查询 IP，返回 `[]netip.Addr`，支持 context |
| `LookupCNAME`          | 查询规范名称                               |
| `LookupAddr`           | 对 IP 地址进行反向 DNS 查询                |
| `LookupMX`             | 查询邮件服务器记录                         |
| `LookupNS`             | 查询名称服务器记录                         |
| `LookupSRV`            | 查询服务发现记录                           |
| `LookupTXT`            | 查询 TXT 记录                              |

#### 5.5.9 自定义解析器补充说明

```go
resolver := &net.Resolver{
    PreferGo: true,
}
```

`PreferGo: true` 表示优先使用 Go 自身的 DNS 解析器。它不代表自动改用公共 DNS；Go 解析器仍会参考系统 DNS 配置。

如果需要指定 DNS 服务器，可以使用 `Resolver.Dial`：

```go
resolver := &net.Resolver{
    PreferGo: true,
    Dial: func(ctx context.Context, network, address string) (net.Conn, error) {
        d := net.Dialer{Timeout: 3 * time.Second}
        return d.DialContext(ctx, network, "10.0.0.53:53")
    },
}
```

示例中的 `10.0.0.53:53` 应替换为实际可达的 DNS 服务器地址。`Dial` 回调会覆盖解析器传入的默认 DNS 目标，因此适合实现指定 DNS 服务器的场景。

DNS 解析与网络连接是两个独立环节：指定 DNS 服务器只控制域名如何解析，不会自动决定后续 TCP 连接走哪张网卡。连接路径仍由系统路由、策略路由及 `net.Dialer` 等机制决定。

### 5.6 TCP 服务端和客户端的实现

#### 5.6.1 TCP 通信的基本流程

介绍 TCP 是面向连接、可靠、有序的字节流协议，以及客户端和服务端的基本通信流程。

- 服务端通过 `net.Listen` 创建监听器。
- 服务端通过 `Accept` 接受客户端连接。
- 客户端通过 `net.Dial` 主动建立连接。
- 双方通过 `net.Conn` 读写数据。
- 通信完成后关闭连接。

核心类型：

```go
net.Listener
net.Conn
```

#### 5.6.2 TCP 服务端的实现

**创建 TCP 服务端**

```go
listener, err := net.Listen("tcp", ":8080")
if err != nil {
    panic(err)
}
defer listener.Close()

fmt.Println("listening on", listener.Addr())
```

需要说明：

- `"tcp"`：使用 TCP 网络协议。
- `":8080"`：监听本机所有可用的本地接口地址，具体可达性仍受系统网络配置影响。
- `"127.0.0.1:8080"`：仅监听本机 IPv4 回环地址。
- `"0.0.0.0:8080"`：监听所有本地 IPv4 接口。
- `listener.Addr()`：获取实际监听地址。

**接受客户端连接**

```go
for {
    conn, err := listener.Accept()
    if err != nil {
        fmt.Println("accept error:", err)
        continue
    }

    fmt.Println("client:", conn.RemoteAddr())
    fmt.Println("local:", conn.LocalAddr())

    conn.Close()
}
```

需要说明：

- `Accept` 通常会阻塞，直到有客户端连接或发生错误。
- 每次成功调用都会返回一个独立的连接对象。
- `RemoteAddr()` 获取客户端地址。
- `LocalAddr()` 获取本地连接地址。
- 实际服务端应当处理连接，而不是接受后立即关闭。

#### 5.6.3 TCP 客户端的实现

**客户端主动连接服务端**

```go
conn, err := net.Dial("tcp", "127.0.0.1:8080")
if err != nil {
    panic(err)
}
defer conn.Close()

fmt.Println("connected:", conn.RemoteAddr())
```

需要说明：

- `net.Dial` 会尝试建立连接，成功后返回 `net.Conn`。
- 目标地址通常采用 `主机名:端口` 格式。
- 如果主机名是域名，建立连接时通常还会涉及 DNS 解析。
- `net.Dial` 没有直接提供超时参数；需要控制连接超时时，可使用 `net.DialTimeout` 或 `net.Dialer`。

**读写 TCP 数据**

```go
conn, err := net.Dial("tcp", "127.0.0.1:8080")
if err != nil {
    panic(err)
}
defer conn.Close()

_, err = conn.Write([]byte("hello\n"))
if err != nil {
    panic(err)
}
```

```go
buf := make([]byte, 1024)
n, err := conn.Read(buf)
if err != nil {
    panic(err)
}

fmt.Printf("received: %s", buf[:n])
```

需要说明：

- `Write` 将字节写入连接。
- `Read` 读取连接中的一部分字节数据。
- 一次 `Read` 不保证恰好读取一次 `Write` 发送的数据。
- `Read` 返回的 `n` 才是本次有效数据长度。
- `io.EOF` 通常表示对端已关闭发送方向，读取到了流的末尾。

#### 5.6.4 TCP 消息边界与粘包问题

TCP 提供的是连续字节流，不会保留应用程序每次发送的数据边界。例如：

```go
conn.Write([]byte("hello"))
conn.Write([]byte("world"))
```

接收端可能一次读取到 `helloworld`，也可能分多次读到数据。

常见的消息分帧方式：

| 方式     | 说明                           | 适用场景       |
| -------- | ------------------------------ | -------------- |
| 固定长度 | 每条消息长度相同               | 固定格式协议   |
| 分隔符   | 使用 `\n` 等字符区分消息       | 文本协议       |
| 长度前缀 | 先发送消息长度，再发送消息内容 | 通用二进制协议 |

例如，使用换行符读取一条消息：

```go
reader := bufio.NewReader(conn)

msg, err := reader.ReadString('\n')
if err != nil {
    return
}

fmt.Print(msg)
```

需要强调：粘包不是 TCP 出错，而是应用层必须自行定义消息边界。

### 5.7 UDP 服务端和客户端的实现

#### 5.7.1 UDP 通信的基本流程

UDP 是一种无连接的数据报协议。与 TCP 不同，UDP 不需要先建立连接，也不保证数据可靠送达、按序到达或只送达一次。每次发送的数据都是一个独立的数据报。

- 服务端通过 `net.ListenPacket` 或 `net.ListenUDP` 监听 UDP 端口。
- 客户端可以通过 `net.DialUDP` 指定目标地址，也可以使用 `net.ListenPacket` 创建未连接的 UDP socket。
- 双方通过 `ReadFrom`、`WriteTo` 或 `Read`、`Write` 收发数据报。
- 通信完成后关闭 socket。

核心类型：

```
net.PacketConn
net.UDPConn
net.UDPAddr
```

TCP 和 UDP 的主要区别：

| 特性     | TCP                        | UDP                                    |
| -------- | -------------------------- | -------------------------------------- |
| 通信方式 | 面向连接                   | 无连接                                 |
| 数据模型 | 字节流                     | 数据报                                 |
| 可靠性   | 提供可靠、有序传输         | 不保证可靠送达和顺序                   |
| 消息边界 | 需要应用层定义             | 保留每个 UDP 数据报的边界              |
| 常用 API | `Listen`、`Accept`、`Dial` | `ListenPacket`、`ListenUDP`、`DialUDP` |

#### 5.7.2 UDP 服务端的实现

**创建 UDP 服务端**

```go
addr, err := net.ResolveUDPAddr("udp", ":8080")
if err != nil {
    panic(err)
}

conn, err := net.ListenUDP("udp", addr)
if err != nil {
    panic(err)
}
defer conn.Close()

fmt.Println("UDP server listening on", conn.LocalAddr())
```

需要说明：

- `net.ResolveUDPAddr`：将字符串形式的地址解析为 `*net.UDPAddr`。
- `net.ListenUDP`：在指定本地地址和端口创建 UDP socket。
- `":8080"`：监听本地 UDP 8080 端口，通常表示所有本地接口。
- `conn.LocalAddr()`：获取本地 socket 地址。
- UDP 不需要像 TCP 一样调用 `Accept`，因为它不需要为每个客户端建立独立连接。

也可以使用更通用的 `net.ListenPacket`：

```go
conn, err := net.ListenPacket("udp", ":8080")
if err != nil {
    panic(err)
}
defer conn.Close()
```

`ListenPacket` 返回 `net.PacketConn`，适用于统一处理 UDP 等数据报通信场景；`ListenUDP` 则返回功能更具体的 `*net.UDPConn`。

**接收客户端数据报**

```go
buf := make([]byte, 1500)

for {
    n, clientAddr, err := conn.ReadFromUDP(buf)
    if err != nil {
        fmt.Println("read error:", err)
        continue
    }

    fmt.Printf(
        "client=%s message=%s\n",
        clientAddr,
        string(buf[:n]),
    )
}
```

需要说明：

- `ReadFromUDP`：读取一个 UDP 数据报，并返回发送方地址。
- `n`：本次读取到的有效数据长度。
- `clientAddr`：发送该数据报的客户端地址。
- UDP 服务端可以通过客户端地址识别数据报的来源，并向其发送响应。
- 缓冲区过小可能导致数据报被截断，因此应根据应用协议合理设置缓冲区大小。

**向客户端发送响应**

```go
_, err := conn.WriteToUDP(
    []byte("hello client\n"),
    clientAddr,
)
if err != nil {
    fmt.Println("write error:", err)
}
```

`WriteToUDP` 将一个完整的数据报发送到指定地址。发送成功只代表本地发送操作成功，不代表客户端一定收到了数据。

#### 5.7.3 UDP 客户端的实现

**客户端发送数据报**

```go
serverAddr, err := net.ResolveUDPAddr(
    "udp",
    "127.0.0.1:8080",
)
if err != nil {
    panic(err)
}

conn, err := net.DialUDP("udp", nil, serverAddr)
if err != nil {
    panic(err)
}
defer conn.Close()

_, err = conn.Write([]byte("hello server"))
if err != nil {
    panic(err)
}
```

需要说明：

- `net.ResolveUDPAddr`：解析服务端的 UDP 地址。
- `net.DialUDP`：创建一个与指定远端地址关联的 UDP socket。
- 第二个参数 `nil` 表示让系统选择合适的本地地址和端口。
- `Write`：将数据报发送到预先指定的远端地址。
- UDP 的 `DialUDP` 不会像 TCP 的 `Dial` 一样执行 TCP 握手，也不能证明远端服务正在运行。

**接收服务端响应**

```go
buf := make([]byte, 1500)

n, err := conn.Read(buf)
if err != nil {
    panic(err)
}

fmt.Printf("received: %s\n", string(buf[:n]))
```

对于通过 `DialUDP` 创建的 socket，`Read` 用于接收来自关联远端地址的数据报。

需要注意：

- UDP 没有 TCP 那样的连接建立过程。
- `Read` 可能一直等待数据到达，因此可以使用 `SetReadDeadline` 设置读取超时。
- 如果应用要求可靠交付，需要自行设计确认、重传、序号和去重等机制。

#### 5.7.4 UDP 消息边界与数据报特性

UDP 与 TCP 的一个关键区别是：**UDP 保留数据报边界，而 TCP 提供连续字节流。**

例如，客户端连续发送两次数据：

```go
conn.Write([]byte("hello"))
conn.Write([]byte("world"))
```

在正常接收且没有截断的情况下，接收端会分别读取到两个独立的数据报，而不是把它们自动合并成一条 `helloworld` 消息。

需要说明：

- 每次 UDP 发送对应一个数据报。
- UDP 不保证数据报一定送达。
- 数据报可能丢失、重复或乱序。
- 接收缓冲区小于数据报长度时，数据可能被截断；`ReadFromUDP` 不会自动把剩余内容留给下一次读取。
- UDP 数据报有长度限制，实际可用负载还受到 IP 版本、网络路径和 MTU 等因素影响。大数据报可能发生 IP 分片，通常应尽量避免依赖大数据报传输。

**示例：逐个读取数据报**

```go
buf := make([]byte, 1500)

for {
    n, addr, err := conn.ReadFromUDP(buf)
    if err != nil {
        fmt.Println("read error:", err)
        continue
    }

    fmt.Printf("%s -> %s\n", addr, string(buf[:n]))
}
```

这里每次成功调用 `ReadFromUDP` 都会读取一个数据报。应用程序不需要像 TCP 那样使用换行符或长度前缀来恢复 TCP 字节流中的消息边界，但仍需要定义数据报内部的业务格式。
