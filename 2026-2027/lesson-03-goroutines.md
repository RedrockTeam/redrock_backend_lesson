### 协程

如果没有操作系统，程序直接跑到裸机上很容易产生多个程序如何运行，程序出错后如何处理等等问题，操作系统最开始就是为了解决这些问题的。操作系统中介硬件和软件，提供单独的抽象层来调度下层向上层暴露接口，我们来看os如何管理cpu的运行。

首先来看两个基础的概念
- 进程：进程可以理解为：一个正在运行的程序实例，拥有独立地址空间和资源。比如你打开两个浏览器窗口，它们可能是两个进程。每个进程有自己的，虚拟地址空间，页表，打开的文件，信号处理，至少一个线程
- 线程:线程可以理解为：进程内部的执行流，是 CPU 调度的基本单位。同一个进程里的多个线程共享：地址空间全局变量打开的文件但每个线程有自己私有PC(下一条指令地址)SP (栈指针)通用寄存器,栈,线程状态


以一个聊天服务器的程序为例子，假设你写了一个程序 `chat_server`，监听 `8080` 端口，很多用户连上来聊天。你启动程序：

```bash
./chat_server
```

操作系统会创建一个**进程**：

```text
进程 chat_server
  PID: 1234
  虚拟地址空间: 代码、全局变量、堆、栈
  页表: 虚拟地址 -> 物理地址
  文件描述符表:
    0: 标准输入
    1: 标准输出
    2: 标准错误
    3: 监听 socket 0.0.0.0:8080
  全局数据:
    users 用户表
    messages 消息队列
```

聊天服务器不可能只用一个执行流，否则只能一个用户一个用户处理。我们更期待能够同时处理多个用户的信息的数据，所以在实际代码中你创建线程：

```c
int listen_fd = socket(...);
bind(listen_fd, 8080);
listen(listen_fd, 128);

while (1) {
    int conn_fd = accept(listen_fd, ...);
    pthread_create(&tid, NULL, handle_client, &conn_fd);
}

void *handle_client(void *arg) {
    int fd = *(int*)arg;
    char buf[4096];          // 线程私有栈
    while (read(fd, buf, ...)) {
        lock(users);
        update(users, buf);  // 访问共享用户表
        unlock(users);
        broadcast(messages, buf);
    }
    return NULL;
}
```

此时进程里可能有：

```text
进程 chat_server，PID 1234
  |
  +-- 主线程：accept 循环，等待新连接
  +-- 工作线程 A：处理 Alice 的连接
  +-- 工作线程 B：处理 Bob 的连接
  +-- 工作线程 C：处理 Carol 的连接
```

它们的关系是：

```text
线程属于进程；
进程是资源容器；
线程是进程内的执行流。
```

假设你不用线程，而是：

```c
while (1) {
    int conn_fd = accept(listen_fd, ...);
    if (fork() == 0) {
        handle_client(conn_fd);
        exit(0);
    }
    close(conn_fd);
}
```

这样每个客户端一个进程。会发生什么？

```text
进程 A：处理 Alice
进程 B：处理 Bob
进程 C：处理 Carol
```

每个进程有自己独立的：

```text
虚拟地址空间
页表
users 副本
messages 副本
文件描述符表
```

问题来了：

- Alice 登录后，更新的是进程 A 的 `users`；
- Bob 登录后，更新的是进程 B 的 `users`；
- 进程 A 看不到进程 B 的用户表。

要让它们共享用户表，必须用：

```text
共享内存 + 信号量
管道 / socket 传消息
文件锁
消息队列
```

这就是**进程间通信 IPC**，比线程直接读写共享内存麻烦得多。而且 `fork()` 创建进程、切换进程、复制页表，开销都比线程大。

```text
进程 = 容器 + 资源
线程 = 容器里的工人 + 执行流

一个进程至少有一个线程。
线程不能脱离进程独立存在。
进程退出，所有线程终止。
线程共享进程资源，但有自己的执行上下文。
```

我们现在能理解线程抽象的必要性，那么为什么需要“进程”和“线程”两层抽象？因为计算机系统同时需要两个互相矛盾的东西：

```text
1. 隔离：程序之间不能互相破坏，保证安全稳定。
2. 共享：同一程序内部要方便地并发、共享数据、利用多核。
```

单一抽象很难同时做好。

如果只有进程，没有线程：

- 隔离很好，但并发粒度太粗；
- 每个执行流都要独立地址空间；
- 共享数据必须 IPC，编程复杂；
- 创建、切换开销大；
- 服务器处理大量连接时，多进程模型沉重。

比如每个请求 `fork()` 一个进程，内存和页表开销大，进程间共享缓存困难。

如果只有线程，没有进程：

- 所有程序共享一个地址空间；
- 一个线程野指针，可能破坏整个系统；
- 不同用户、不同程序之间无法安全隔离；
- 权限、资源配额、故障隔离都很难做。

比如浏览器所有标签页都在一个地址空间，一个页面崩溃，全部标签页崩溃；一个页面挖矿，所有页面卡顿。

所以需要抽象上的层级分层

```text
进程层：负责隔离、资源、权限、故障边界。
线程层：负责并发、调度、共享、多核利用。
```

现代系统通常是两者结合：

```text
多进程 + 多线程
```

例如：

- Chrome：每个标签页一个进程，进程内多个线程，渲染、网络、UI 各司其职。
- Nginx：多个 worker 进程，每个进程事件循环，部分版本可用多线程。
- 数据库：一个数据库进程，内部多个线程处理查询、写日志、刷盘。
- Go 程序：一个进程，多个 goroutine，运行时映射到多个 OS 线程。

进程是资源容器，负责隔离、安全、权限和资源管理；线程是进程内的执行流，负责并发、调度和共享数据。一个聊天服务器可以是一个进程，内部多个线程共享用户表和消息队列；如果换成多进程，每个进程有独立内存，共享数据就必须 IPC。需要这两层抽象，是因为系统既要“隔离”又要“共享”：进程提供隔离边界，线程提供边界内的高效并发。

但是线程尽管比进程轻，但是在要求频发链接频发断开的，它还是太重（需要切换进入内核态通过系统调用创建）（用户态和内核态，本质上是 CPU 的两种特权级别。用户态：程序受限制地运行，不能直接碰硬件和关键资源。内核态：操作系统内核运行的特权模式，可以执行所有指令、访问所有硬件和内存）

协程更轻，将我们在上面提到的重型上下文切换和从内核态搬到用户态，将内核态处理的事情移动到在用户态，这样，一个协程和一个hello world中printf("hello world");在实际的操作系统概念上差别不大，而go的goroutine就是协程在go中的实现，

```go
 go helloWorld()
```

所以你可以简单理解，协程运行到单个线程之上（正如我们之前所说的协程知识普通用户态程序），当你写下go关键字的时候，你就是在启动这么一个协程，在上面这个例子中让协程轻量化的运行一个函数。

### 协程的infra

我们再来梳理一下进程，线程和协程这三个概念，前两个涉及内核态的系统调用操作，用操作系统背书，协程是用户态的概念，但是，回顾一下我们引出操作系统时的问题，当我们在用户态处理时最大的问题不是怎么去对cpu的状态进行保存或切换，最大的问题在于如何去管理调度协程，正如操作系统对进程和线程的管理和调度。很自然的，我们想到将操作系统的概念和管理去迁移到用户态上去服务协程。

这就是go的runtime所做的事情，这将协程的实现向用户的暴露接口极为简单，用户只需要使用go关键字就可以。所以说上面那段代码可以简单理解成这样创建一个 goroutine，让 helloWorld() 成为一个新的并发执行单元，并交给 Go runtime 调度。

go官方对goroutine的定义如下：：goroutine 是与其他 goroutine 并发执行的函数，并且多个 goroutine 会复用到多个 OS thread 上；

```text
当前 Process
      │
      ├── main goroutine
      │
      └── helloWorld goroutine
```

两个 goroutine 属于：同一个 Go 进程

```text
进程
  ├── 资源：地址空间、页表、堆、文件描述符
  ├── OS 线程 M1、M2、M3
  │       ↑
  │       │ Go runtime 调度
  │       │
  └── goroutine G1、G2、G3...
```

这张图是三者的简陋关系。

go的协程非常适合处理大规模的并发（除了上述根本上的优势还有很多），这也是go最主要的优势，你可以通过简单的关键字来启动和关闭协程，但是，复杂性并不是消失了，而是迁移到了其他地方，我们提到了go的runtime，你可以将runtime理解成程序运行过程中一直工作着的基础设施，go的runtime相当复杂，这也是的程序的运行难以预测，产生了更多的调度工作，同时你可以看到，在go里面指针或和组的一些操作是得到了极大的限制的，你几乎无法像c一样自由的操纵底层内存单元，你只需要调用new()却不像在c底层一样在分配内存后还需要按顺序free()。出了runtime之外go的另一套运行时还有gc（garbage collector）垃圾回收机制，go的自动内存管理很大程度上由这个机制提供。

Go 并没有让计算机系统变简单，而是把很多复杂问题集中到 Runtime和GC，让普通程序员不需要直接面对这些复杂度。

```text

                     Go 程序员
                         │
             ┌───────────┴───────────┐
             │                       │
          写业务代码              写并发逻辑
             │                       │
             └───────────┬───────────┘
                         ↓
                    Go Runtime
                         │
        ┌────────────────┼────────────────┐
        │                │                │
        ▼                ▼                ▼
    Scheduler        Memory             GC
        │                │                │
        ▼                ▼                ▼
   Goroutine          Stack/Heap       自动回收
        │
        ▼
    OS Thread
        │
        ▼
       CPU
```

当然，巨大的runtime出了复杂性上的代码之外还有性能上的代价，因为runtime本质上也在你启动程序的时候在跑，所以go不适合性能敏感的场景。以牺牲性能和底层复杂性的方式来方便实现并发。

简单来看一下go底层scheule的调度方式：GMP模型
- G 代表一个 goroutine 以及与它运行相关的状态。
- M 可以直观理解成：一个 OS thread。
- P 执行 Go 用户代码所需要的一份 runtime 资源。

这里你们会对p的设计可能存在疑惑，runtime还需要哪些 G 可以运行 如何获取 runnable G 调度状态 内存分配相关状态，假设：10000 个 G，8 个 CPU，我们真正希望的是：10000 G对应有限数量的执行资源（os thread）而非10000个G对应10000个thread，Go 希望 runtime 能够更加直接地管理：哪些 G 需要运行。

换句话说，通过这种方式实现对有限物理资源的分配，不止go的线程分配，在其他的场景中你也可以看到类似的设计。

### go关键字的使用

现在回过头来看几个go关键字使用的示范
```go
func hello() {
    fmt.Println("hello")
}

func main() {
    go hello()
}
```

go的关键字后面具体给出调用的函数，go创建协程并在协程中运行这个函数。

```go
func main() {
    go func() {
        fmt.Println("hello from anonymous")
    }()

}
```

匿名函数形式，注意这里最后面的括号意思是函数调用，你也可以在hello后面看到，前面部分可以理解成是定义函数。

```go
func greet(name string) {
    fmt.Println("hello,", name)
}

func main() {
    go greet("Alice")
    go greet("Bob")
    time.Sleep(time.Second)
}
```
带参数的函数调用


```go
for i := 0; i < 3; i++ {
    go func(n int) {
        fmt.Println(n)
    }(i)
}
```
匿名函数的参数传入

来看一个函数调用对比
```go
func work() {
    fmt.Println("working")
}

func main() {
    work()      // 当前 goroutine 执行，阻塞到返回
    go work()   // 新 goroutine 执行，立即返回
}
```

```go
go x + y            // 错误：不是函数调用
go if x { }         // 错误：不是函数调用
go f               // 错误：是函数值，不是调用
go f()             // 正确
go func() {}()     // 正确
go obj.Method()    // 正确
```
