# 第七课：数据库基础与 SQL

可以先看这个视频[Mysql是什么？架构是怎么样的？](https://www.bilibili.com/video/BV1p5qhYsE4f)简单了解一下

## 第一部分：为什么需要数据库

### 1. 你的数据活不过一次重启

先说一个你们所有程序共有的秘密：你们写过的一切数据，都是“阅后即焚”的。

不管你用切片、map 还是结构体，维护的是 200 条的学生名册还是更复杂的数据，这些工具都有一个共同的问题绕不开：程序一退出，数据就没了。

```text
程序运行中：students 里有 200 条数据
        │
        │ Ctrl+C / 断电 / 崩溃
        ▼
程序再次启动：students 里什么都没有
```

原因并不神秘：程序的数据放在内存里，内存是易失性的——一旦断电，里面所有的比特都会丢失。全局变量哪怕在编译时写进了可执行文件的 `.data` 段，重启后拿到的也只是编译时的初始值——运行期间的所有修改都发生在内存里，随内存一起消失。

对一个真实的后端服务来说，这是不可接受的。用户的账号、发过的帖子、下过的订单，不可能因为服务器重启一次就全部清零。所以我们需要一种手段，把数据放到断电后依然还在的地方——磁盘。而“怎么把数据放到磁盘上，并且存得对、存得快、崩了还能恢复”，就是数据库这门课要解决的问题。

### 2. 用文件存数据，麻烦在哪

有同学可能会想：磁盘上的文件不就能持久化吗？C 里用 `fopen`/`fwrite`，Go 里用 `os.WriteFile`，我自己把数据写进文件不就行了？

“能存下来”确实容易。但把文件当作数据的家，麻烦会在四个地方陆续找上门：

**第一，格式全靠自己。** 你得自己定义 200 个学生怎么存：一行一个？逗号分隔？学号存数字还是字符串？写的时候要自己序列化，读的时候要自己解析。内存和磁盘上终究只是字节，含义全靠约定——而自己的约定只有自己懂，换一个人、换一门语言，就得重新对一遍格式。

**第二，查询等于全量读入。** 想找名字叫“小明”的学生，你得把整个文件读进内存，自己写循环一行行比——200 条数据最坏要比较 200 次。200 条还好，200 万条呢？每次查询都全量读盘再全量比对，磁盘会成为整个服务最慢的那一环。

**第三，并发写会互相踩。** 两个进程同时打开同一个文件写——如果没有协调，后写的会把先写的覆盖掉。这种冲突比共享内存里的数据竞争更隐蔽，也更难处理。

**第四，写一半崩溃没有退路。** 假设你要往文件里追加 10 行数据，写到第 5 行的时候断电了。重新启动后，文件处于一个既不是“写入前”也不是“写入后”的中间态，而且你没有任何手段恢复——没有日志、没有备份点，只有半个残缺的文件。

也就是说，存数据这件事，“能存”只占一成，“存得对、查得快、崩了能恢复”占九成，而后面九成全是有标准答案的专门课题。把这个课题交给一个专门的程序去做，就是数据库。

### 3. 数据库：一个专门管数据的程序

数据库（更准确地说，数据库管理系统，DBMS）就是一个专职管理数据的常驻程序。它替你把上面四个麻烦全部接了过去：

| 你自己用文件 | 数据库替你做的事 |
|---|---|
| 自己定义格式、自己解析 | 表结构 + 数据类型，格式统一管理 |
| 全量读入、自己写循环查找 | SQL 查询 + 索引，几百万数据毫秒级定位 |
| 多进程并发写互相覆盖 | 锁 + 事务，并发访问依然正确 |
| 写一半崩溃无法恢复 | 日志机制，崩溃后自动恢复到一致状态 |

常见的数据库产品：MySQL、PostgreSQL、SQLite 是关系型数据库，也就是今天的主角；Redis、MongoDB 这类非关系型（NoSQL）数据库各有擅长的场景，本课不展开。

关系型数据库是我们使用最多的一类，它的核心思想是：用一张张二维表格来组织数据，表与表之间通过关联字段建立联系。具体怎么回事，第二部分展开。

### 4. 客户端与服务器：数据库的网络形态

这里有一个值得停下来想一下的事实：数据库不是你程序里的一个库，它本身就是一个独立运行的进程。

进程是资源隔离的容器。MySQL 是一个进程，你的 Go 程序是另一个进程，它们互相看不见对方的内存。那么你的程序怎么把 SQL 交给 MySQL？答案是网络。MySQL 作为服务器进程监听 3306 端口，任何程序——你的 Go 服务、Python 脚本、运维同学手里的命令行客户端——都可以作为客户端连上来：

```text
  客户端 A（Go 程序）     客户端 B（命令行）
        │                     │
        │  TCP 连接            │  TCP 连接
        ├─────────────────────┤
        │                     │
        ▼                     ▼
   ┌─────────────────────────────┐
   │   MySQL 服务器进程           │
   │   监听 0.0.0.0:3306          │
   │                             │
   │   解析 SQL → 优化 → 执行      │
   │   读写磁盘上的数据文件         │
   └─────────────────────────────┘
                 │
                 ▼
            磁盘上的数据
```

这个“客户端-服务器”的形态带来两个直接的好处。一是同一份数据可以被多个不同的程序共享：你的 Go 服务在写订单，数据分析师的脚本在同一份订单上跑统计，互不干扰。二是运维可以随时拿命令行客户端连上生产数据库，直接排查问题——这在真实公司里是每天都在发生的事。

顺带一提 SQLite：它是个有趣的例外，整个数据库就是磁盘上的一个文件，不需要独立的服务器进程，程序直接读写这个文件。零安装零配置，拿来练手非常友好。但它没有网络服务形态，并发能力也有限，所以生产后端的主力依然是 MySQL、PostgreSQL 这类“服务器型”数据库。本课以 MySQL 为例讲解，SQL 语句在 PostgreSQL 上基本通用。

## 第二部分：关系模型与 SQL

### 1. 表、行、列

关系型数据库用表格组织数据。还是那份学生名册，在数据库里长这样：

```text
students 表
+----+--------+-----+--------+
| id | name   | age | grade  |
+----+--------+-----+--------+
|  1 | 小明   |  18 | 大一   |
|  2 | 小红   |  17 | 大一   |
|  3 | 小刚   |  19 | 大二   |
+----+--------+-----+--------+
```

如果你拿它和 Go 的结构体对比，会发现对应关系严丝合缝：

```go
type Student struct {
    ID    int
    Name  string
    Age   int
    Grade string
}
```

- 列 = 结构体的字段，列名对应字段名，每一列有固定的数据类型；
- 行 = 一个具体的结构体实例，一条记录；
- 表 = 同类型实例的集合，类比 `[]Student`；
- 表头（列的定义）= 结构体类型本身。

区别在于存储位置和生命周期：切片在内存里、随程序消失，表在磁盘上、跨重启存在。当然，磁盘上不会真的存一个 Go 结构体——磁盘上只有字节，数据库会按自己的格式把每一行编码存进数据文件。格式这件事从此不用你操心。

### 2. 关系：用多张表表达世界

只看一张表的话，“关系型”这个名字里的“关系”还没出现。现在把场景做真实一点：除了学生，还要记录每个学生各门课的成绩。

新手最直觉的设计是把所有东西塞进一张表：

```text
students_flat（反面教材）
+----+--------+-----+---------+---------+---------+
| id | name   | age | 数学    | 语文     | 英语     |
+----+--------+-----+---------+---------+---------+
|  1 | 小明   |  18 | 90      | 85      | 92      |
|  2 | 小红   |  17 | 88      | 90      | 79      |
+----+--------+-----+---------+---------+---------+
```

这个设计很快会失控：新学期加一门“体育”，就要 `ALTER TABLE` 加一列，列越加越多；一个学生重修，同一门课出现两个成绩，列名被迫变成“数学_补考”；更根本的是，成绩这个信息和“学生是谁”混在一起，任何一张课表的变动都要动学生的主表。

正确的做法是拆开：学生信息归学生表，课程信息归课程表，成绩单独一张表，用学生和课程的编号把它们关联起来：

```text
students                courses                 scores
+----+--------+         +----+--------+          +------------+----------+-------+
| id | name   |         | id | title  |          | student_id | course_id | score |
+----+--------+         +----+--------+          +------------+----------+-------+
|  1 | 小明   |         | 10 | 数学   |          |     1      |    10     |  90   |
|  2 | 小红   |         | 11 | 语文   |          |     1      |    11     |  85   |
+----+--------+         | 12 | 英语   |          |     2      |    10     |  88   |
                        +----+--------+          +------------+----------+-------+
```

- 一个学生对应多条成绩，“一对多”；外键（`student_id`）放在“多”的那一方；
- 成绩表里不再重复存学生姓名，只存一个 `student_id`——想看名字，沿着编号回 students 表查；
- 加一门课只是 courses 表多一行，改一个学生的名字只动 students 一行，互不牵连。

“关系”指的就是这些表通过编号建立的关联。关系模型用“表格 + 关联”这一套很简单的表达，几乎能装下所有业务数据：用户和订单、帖子评论和点赞、商品和库存，都是这个模式的变体。这个三张表的小库我们后面会反复用到。

### 3. SQL：一门声明式语言

数据放进去了，接下来是怎么查。这就是 SQL（Structured Query Language）的领域——所有关系型数据库通用的标准语言。

SQL 和你学过的 C、Go 最大的思维差异在于：C 和 Go 是命令式语言，你写下“怎么做”——循环怎么走、条件怎么判、指针怎么挪；SQL 是声明式语言，你只写下“要什么”，剩下的交给数据库。

同样是“找出所有 17 岁以上的学生”，Go 里你会这样写：

```go
for _, s := range students {
    if s.Age >= 17 {
        fmt.Println(s.ID, s.Name)
    }
}
```

注意你亲手安排了一切：遍历顺序、判断位置、输出内容。而 SQL 是：

```sql
SELECT id, name FROM students WHERE age >= 17;
```

没有循环，没有 if。怎么遍历这张表、要不要借助索引、先处理哪一步，全部由数据库决定。

这里埋一句话，它是今天整节课的暗线：**你把“怎么找”交出去，数据库才有“怎么找更好”的选择空间。** 只有语言本身不规定执行路径，第四部分要讲的优化器才有发挥的余地。声明式不是偷懒，是把决策权交给更懂磁盘的那一方。

### 4. SQL 的三个组成部分

SQL 语句按用途分成三类，先混个脸熟，第三部分逐个上手：

| 分类 | 全称 | 管什么 | 代表语句 |
|---|---|---|---|
| DDL | Data Definition Language | 表的结构（库、表、列本身） | `CREATE`、`ALTER`、`DROP` |
| DML | Data Manipulation Language | 表里的数据（每一行的增删改） | `INSERT`、`UPDATE`、`DELETE` |
| DQL | Data Query Language | 查询 | `SELECT` |

有时教材会把 `SELECT` 归进 DML 一起说，也有第四类 DCL（`GRANT`/`REVOKE`，权限管理）交给数据库管理员，本课不展开。日常开发中你打交道最多的是 DQL 和 DML——毕竟建表是一次性的，增删改查天天都在发生。

## 第三部分：动手写 SQL

### 1. 准备一个 MySQL

macOS 用 Homebrew 一条命令，Windows 从官网下载安装器：

```bash
# macOS
brew install mysql
brew services start mysql

# 登录（安装时设置的密码，本地练习也可以初始化成空密码）
mysql -uroot -p
```

```text
Windows：https://dev.mysql.com/downloads/installer/
选 mysql-installer-community.msi，一路下一步，记住 root 密码
```

进入 MySQL 交互环境后，先感受两个最基础的命令：

```sql
SHOW DATABASES;   -- 看看这个 MySQL 里有哪些库
USE school;       -- 选中一个库（现在还没有，下面马上建）
```

如果嫌装 MySQL 麻烦，`sqlite3` 也是合法的练习路径——SQLite 同样讲 SQL，建表语句几乎一样。但本课后面涉及 MySQL 特有的行为（比如存储引擎、InnoDB），建议还是以 MySQL 为主。

### 2. 建库与建表（DDL）

创建数据库，指定 `utf8mb4` 字符集——它是 MySQL 推荐的 Unicode 字符集，能正确存储中文和 emoji。新项目统一用它，免得以后数据里出现乱码再迁移：

```sql
CREATE DATABASE school CHARACTER SET utf8mb4;
USE school;
```

然后建 students 表：

```sql
CREATE TABLE students (
    id         INT PRIMARY KEY AUTO_INCREMENT,
    name       VARCHAR(50) NOT NULL,
    age        INT,
    grade      VARCHAR(10),
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

逐个看这些约束的含义：

- `INT PRIMARY KEY`：这一列是主键。主键唯一标识一行，不允许重复、不允许为空——学号、工号、身份证号都是天然的候选主键；
- `AUTO_INCREMENT`：自增。插入行时不指定 id，数据库自动分配 1、2、3……你完全不用操心“下一个学号是多少”这种问题；
- `NOT NULL`：非空约束。名字为空的学生没有意义，让数据库直接拒绝这种插入；
- `DEFAULT CURRENT_TIMESTAMP`：默认值。插入时不给 created_at，就自动填当前时间——“什么时候注册的”这种字段从此不用业务代码操心。

建表的核心决策是给每一列选数据类型。常用就这么几个，先够用：

| 类型 | 用途 | 说明 |
|---|---|---|
| `INT` / `BIGINT` | 整数 | 默认选 `INT`，量级极大（雪花 ID 等）用 `BIGINT` |
| `VARCHAR(n)` | 短文本 | 姓名、标题，n 是最大长度，最常用 |
| `TEXT` | 长文本 | 文章正文、日志，不能设默认值 |
| `DECIMAL(M,D)` | 精确小数 | **金额必用它** |
| `DATETIME` | 时间 | 年月日时分秒 |
| `BOOLEAN` | 布尔 | 本质是 `TINYINT`，存 0/1 |

完整类型清单（浮点、时间戳、二进制、JSON……）不必背，用的时候查文档。但有一个坑现在就要记：浮点数不能存钱。`FLOAT`/`DOUBLE` 和 C、Go 里的 float 一样是二进制浮点，`0.1 + 0.2 != 0.3` 的问题在数据库里原样存在，攒着分分秒秒的误差对账时会出大事。金额一律 `DECIMAL(10, 2)`——十进制定点表示，精确无误。

建好表之后：

```sql
DESC students;   -- 查看表结构：每一列的类型和约束
SHOW TABLES;     -- 查看当前库有哪些表
```

把第三部分第 2 节的另外两张表也建了，后面要用：

```sql
CREATE TABLE courses (
    id    INT PRIMARY KEY AUTO_INCREMENT,
    title VARCHAR(50) NOT NULL
);

CREATE TABLE scores (
    student_id INT NOT NULL,
    course_id  INT NOT NULL,
    score      INT,
    PRIMARY KEY (student_id, course_id)
);
```

注意 scores 的主键是“学生 + 课程”的组合：同一个学生同一门课只允许有一条成绩记录，这个约束交给数据库比交给业务代码可靠。至于 `student_id` 要不要对外声明成指向 students 表的外键（`FOREIGN KEY`）——概念上它确实是外键，但实际工程里很多团队选择不建物理外键约束，只在设计上保证关联，这涉及性能和运维的取舍，现阶段知道有这回事就行。

### 3. 增：INSERT

```sql
INSERT INTO students (name, age, grade)
VALUES ('小明', 18, '大一');

INSERT INTO students (name, age, grade)
VALUES ('小红', 17, '大一'),
       ('小刚', 19, '大二');
```

列名清单和值按位置一一对应；id 和 created_at 没写，走自增和默认值。把三张表的数据补齐：

```sql
INSERT INTO courses (id, title) VALUES (10, '数学'), (11, '语文'), (12, '英语');

INSERT INTO scores (student_id, course_id, score)
VALUES (1, 10, 90), (1, 11, 85),
       (2, 10, 88), (2, 12, 79);
```

一个习惯问题：可以写 `INSERT INTO students VALUES (...)` 省略列名吗？语法上可以，但它要求你按顺序给全所有列的值，表结构一变立刻报错。显式写列名，多打几个字，换的是安全。

### 4. 查：SELECT

SELECT 是整个 SQL 里最重要、也最能体现“声明式”的语句。从最简单开始：

```sql
SELECT * FROM students;
```

`*` 表示所有列。但生产代码里 `SELECT *` 是个坏习惯：你拿到一堆用不上的列（比如大段的 TEXT），也让“少查几列能不能走覆盖索引”这种优化彻底无缘——第五部分会回收这句话。需要什么就写什么：

```sql
SELECT name, age FROM students;
```

带上条件：

```sql
SELECT name, age FROM students WHERE age >= 17;
SELECT name FROM students WHERE grade = '大一' AND age >= 17;
SELECT name FROM students WHERE grade IN ('大一', '大二');
SELECT name FROM students WHERE age BETWEEN 17 AND 19;
SELECT name FROM students WHERE name LIKE '小%';
```

`LIKE '小%'` 是模糊匹配：`%` 匹配任意字符串，这里查所有姓“小”的学生。注意这两个查询在数据库眼里待遇完全不同——`'小%'` 有机会用上 name 列的索引加速，而 `'%明'` 不能。为什么前缀确定就能加速、后缀确定就不能，原因第五部分讲索引时你会彻底明白。

排序和分页，几乎每个列表页背后都是这两句的组合：

```sql
SELECT name, age FROM students ORDER BY age DESC;         -- 按年龄从大到小
SELECT name, age FROM students ORDER BY age DESC LIMIT 2; -- 只取前 2 条
SELECT name FROM students ORDER BY id LIMIT 2 OFFSET 2;   -- 跳过 2 条取 2 条（第 2 页）
```

还有一个容易踩的点：判断一个值是不是 NULL，不能用 `= NULL`：

```sql
SELECT * FROM students WHERE age IS NULL;      -- 正确
SELECT * FROM students WHERE age = NULL;       -- 永远查不到任何行
```

NULL 在 SQL 里表示“未知”，和任何值比较的结果都是未知，所以要用 `IS NULL` / `IS NOT NULL`。

### 5. 改与删：UPDATE 与 DELETE

```sql
UPDATE students SET age = 19 WHERE id = 1;
DELETE FROM students WHERE id = 3;
```

这两条语句威力巨大，而威力来自那个 WHERE。看仔细：

```sql
UPDATE students SET age = 19;      -- 没有 WHERE：全体学生年龄改成 19
DELETE FROM students;              -- 没有 WHERE：整张表清空
```

没有 WHERE 的 UPDATE 和 DELETE 作用于全表——在练习库里是无所谓的教训，在生产环境里是事故通报。养成肌肉记忆：写 UPDATE/DELETE 先写 WHERE，再回头填 SET 和表名。

DELETE 和 TRUNCATE 都能清空一张表，区别一句话：`TRUNCATE TABLE students` 不可回滚、不加条件、重置自增计数，是“格式化”；DELETE 是逐行删除，走第六部分要讲的事务体系，可以回滚。

### 6. 聚合与分组：COUNT 与 GROUP BY

到这里为止，查询都是“把行原样拿出来”。另一类问题是“对行做统计”：全班多少人？平均分多少？

聚合函数把多行压成一个数：

```sql
SELECT COUNT(*) FROM students;            -- 几行
SELECT AVG(score) FROM scores;            -- 平均分
SELECT MAX(score), MIN(score) FROM scores;
SELECT SUM(score) FROM scores WHERE course_id = 10;
```

更有意思的是 GROUP BY：把行按某列分组，每组各自聚合。假设有一份投票记录表 votes，想统计每个人得了几票，用 Go 手写大概是这样一个循环：

```go
count := map[string]int{}
for _, name := range votes {
    count[name]++
}
```

外层遍历、内层查 map、逐个累加，你要亲自安排“怎么分桶、怎么累加”。现在数据库一句：

```sql
SELECT name, COUNT(*) AS cnt
FROM votes
GROUP BY name
ORDER BY cnt DESC;
```

GROUP BY name 把同名的人归为一组，COUNT(*) 对每组数个数，ORDER BY 把票数最多的排前面。“分桶计数”这个你亲手实现过的模式，在 SQL 里是一个关键词。

用成绩表统计每门课的平均分：

```sql
SELECT course_id, AVG(score) AS avg_score
FROM scores
GROUP BY course_id;
```

一个新手常见困惑顺带说清：想筛“平均分高于 85 的课程”，条件写在哪？WHERE 是对原始行过滤，发生在分组之前；“对分组结果”的过滤要用 HAVING：

```sql
SELECT course_id, AVG(score) AS avg_score
FROM scores
GROUP BY course_id
HAVING avg_score > 85;
```

执行顺序是 WHERE → 分组 → 聚合 → HAVING → ORDER BY。现在记不住没关系，写错两次自然就记住了，重要的是知道“过滤行用 WHERE，过滤组用 HAVING”。

### 7. 多表查询：JOIN

单表查询再熟练，业务问题几乎总是跨表的：“每个学生各科成绩是多少？姓名和成绩不在同一张表里。”

JOIN 就是把多张表按关联条件拼成一张临时结果表的语句：

```sql
SELECT students.name, scores.course_id, scores.score
FROM students
JOIN scores ON students.id = scores.student_id;
```

`ON students.id = scores.student_id` 是拼接条件：学生表里的 id 对得上成绩表里的 student_id，就把这两行接起来。执行结果可以脑补成这样：

```text
students JOIN scores ON students.id = scores.student_id

+--------+----------+-------+
| name   | course_id| score |
+--------+----------+-------+
| 小明   |    10    |  90   |
| 小明   |    11    |  85   |
| 小红   |    10    |  88   |
| 小红   |    12    |  79   |
+--------+----------+-------+
```

小明有两行，因为他有两条成绩——“一对多”在查询结果里的直接体现就是 JOIN 后行数变多。

上面写的是 INNER JOIN（默认形态）：只有两边都匹配的行才会出现。如果小红压根没参加考试，她的名字不会出现在结果里——因为 scores 表里没有她的行。想让她也出现（成绩显示为 NULL），用 LEFT JOIN：

```sql
SELECT students.name, scores.score
FROM students
LEFT JOIN scores ON students.id = scores.student_id;
```

LEFT JOIN 保留左表（students）的全部行，右边匹配不上的填 NULL。直觉记法：查“所有人”用 LEFT，查“有成绩的人”用 INNER。

三表连查也就是再 JOIN 一次，把课程名换进来：

```sql
SELECT s.name, c.title, sc.score
FROM students s
JOIN scores sc ON s.id = sc.student_id
JOIN courses c ON sc.course_id = c.id;
```

`s`、`sc`、`c` 是表别名，多表查询里写全名太啰嗦，惯例用短名。这句查询已经是一个真实业务接口的核心了——“查询某学生的成绩单”这个 API，落到数据库上就是它。

## 第四部分：一句 SELECT 敲下回车之后

第三部分你学会了“要什么”，现在回答本课开头埋下的那个问题：敲下回车之后，数据库那边“怎么给”。这部分的每一个环节，都能在 C 语言的编译流程里找到对应。

### 1. 你的 SQL 也是一种“源码”

客户端敲下的 SQL，通过 TCP 连接发到 MySQL 服务器进程。MySQL 拿到手的只是一段文本——`"SELECT name FROM students WHERE age >= 17"`，一个字符串而已。

SQL 是发到服务器执行的文本，而任何一门语言要把文本变成可执行的东西，都要经过编译流水线：词法/语法分析成抽象语法树，逐步翻译成汇编码、机器码，再由 CPU 取指译码执行。数据库收到 SQL 后走的是几乎同构的流程：

```text
C 源码                          SQL 文本
   │                               │
   │  词法/语法分析                 │  词法/语法分析
   ▼                               ▼
抽象语法树                     解析树（语法是否合法？）
   │                               │
   │  语义分析                     │  语义检查（表存不存在？列有没有？）
   ▼                               ▼
中间表示                       预处理后的语法树
   │                               │
   │  编译优化                     │  优化器（下一步的主角）
   ▼                               ▼
优化后的指令                   执行计划（query plan）
   │                               │
   │  执行                         │  执行器（调用存储引擎读数据）
   ▼                               ▼
CPU 运行                       结果集 → 沿 TCP 连接返回客户端
```

所以 MySQL 内置了一门语言的完整前端：词法分析把 `SELECT` 识别为关键字、`students` 识别为标识符，语法分析检查这句 SQL 的结构合不合法，语义检查确认 students 表真实存在、name 列真实存在。写错列名时你看到的 `Unknown column 'nmae'` 报错，就来自这个阶段——和 C 编译器报 `undefined reference` 是一个道理。

### 2. 优化器：同一个“要什么”，多种“怎么给”

编译器的一大本事是对你的代码做优化——死代码消除、循环不变量外提——同样的源码，产出更快的指令。SQL 的优化器做的是同类事情，而且更激进：对同一个“要什么”，它会认真比较几种“怎么给”，选出它认为最便宜的。

看这句 SQL：

```sql
SELECT name FROM students WHERE age >= 17;
```

在有索引的情况下（索引是什么，下一节讲透），数据库至少有两个可选方案：

```text
方案一：全表扫描
  从头到尾逐行读表，逐行判断 age >= 17
  成本估计：读全部行数

方案二：走 age 列的索引
  先在索引里定位所有 >= 17 的值，再回表取 name
  成本估计：索引高度 + 命中行数 × 回表代价
```

优化器根据表里大概有多少行、多少行满足条件，给每个方案估一个成本，挑低的执行。17 岁以上的学生占 90%，方案二可能反而更慢（先查索引再回表，还不如顺序扫一遍），优化器会选方案一；满足条件的只有 3 个人，索引方案完胜。**同一句 SQL，数据分布不同，执行路径可能完全不同**——这就是第三部分说的“声明式给了数据库选择空间”的具体含义。这也是为什么永远不要在 Go 代码里手写查找逻辑去“帮”数据库：你把怎么找写死的那一刻，优化器所有的选择空间就都没了。

想亲眼看这些决策，EXPLAIN 关键字可以把执行计划打印出来：

```sql
EXPLAIN SELECT name FROM students WHERE age >= 17;
```

现在还看不懂它的输出很正常；记住这个命令，学完下一节再回来，你会发现输出里写的正是“用了哪个索引、扫了多少行”。

### 3. 存储引擎：真正碰磁盘的层

执行器拿着优化器选定的计划去取数据。而真正负责“数据在磁盘上怎么摆、怎么读怎么写”的，是 MySQL 架构里更靠下的一层——存储引擎。

MySQL 的一个特色是插件式的存储引擎：上层的连接、解析、优化是一套，底下真正存取数据的部分可以替换，同一台 MySQL 里不同的表可以用不同的引擎。历史上有过很多引擎，今天只需要认识两个：

| | InnoDB | MyISAM |
|---|---|---|
| 事务 | 支持 | 不支持 |
| 行级锁 | 支持 | 只有表锁 |
| 崩溃恢复 | 支持（靠 redo log） | 不支持 |
| 现状 | MySQL 5.5 起的默认引擎 | 已基本淘汰 |

结论就一句：用 InnoDB，现代 MySQL 默认就是它，你没有理由换。接下来所有原理性讨论（索引结构、事务、日志）全部发生在 InnoDB 里。

换个角度描述一下 InnoDB：它本身就是一个巨型 C/C++ 程序，在你的服务器上以一个进程（或者进程里的模块）形态运行，内部有自己的一套“运行时”——缓冲池（buffer pool，用内存缓存磁盘页，减少真实磁盘 IO）、后台线程（负责刷盘、清理）、锁系统、日志系统。它做的事本质上是：在易失的内存和持久的磁盘之间，维护一套“看起来简单、用起来正确”的数据抽象。**把复杂度装进基础设施，把简单留给使用者**——这和 Go runtime 替你管理 goroutine 和内存是同一种思想。

### 4. 一个疑问：为什么感觉不到磁盘慢

现在有个矛盾值得停下来想一想。磁盘比内存慢好几个数量级（内存访问约百纳秒级，SSD 一次随机读约百微秒级，机械硬盘约毫秒级——差三到五个数量级），而你的 MySQL 查询动不动毫秒级出结果，查的还是百万行的表。它怎么敢？

第一层答案是 InnoDB 的缓冲池：磁盘按“页”（默认 16KB）为单位读取，读过的页缓存在内存里，热数据的读写几乎不碰磁盘。那内存和磁盘不一致了怎么办？这就是第五部分 WAL 日志要回答的问题——先记日志再慢慢刷盘，先按下不表。

第二层答案更根本：让一次查询少读页、只读该读的页。这就是索引存在的意义，也是接下来一整节的主角。

## 第五部分：索引——B+ 树登场

索引是数据库原理里最值得花时间的一讲。它回答的是一个贯穿始终的问题：**查找到底能有多快**。

### 1. 从线性查找到哈希表，再到今天

先把内存里你已经熟悉的两种查找摆出来：一条链表（或数组）从头找到尾，是最朴素的线性查找；一个 map（哈希表）按键哈希直接定位，平均 O(1)。在 Go 里给 200 条学生记录建个 `map[string]Student`，查找几乎不花时间。

但哈希表有一个代价：**无序**。键被哈希函数打散到各个桶里，“找一段连续范围的键”、“按键排序输出”、“找最大的键”这些操作它都做不了，只能全量拉出来重新排。内存场景下这个代价尚可接受，数据一旦搬到磁盘上，它就变成了致命伤——后面马上会看到为什么。

数据库需要的是另一种结构：既要有哈希表级别的定位速度，又要天然有序、还要对磁盘友好。它叫 B+ 树。

1. **范围查询**：`WHERE age BETWEEN 17 AND 19`、`ORDER BY age`、`LIKE '小%'` 都要求“按大小顺序找到一段”，哈希表把顺序彻底打散，只能精确匹配单个键；
2. **磁盘友好**：数据在磁盘上以页为单位读写，一次 IO 读一整页。哈希表随数据增长要频繁扩容重排，且键的分布和磁盘布局毫无关系，范围扫描意味着大量随机 IO；
3. **有序遍历**：最值（MAX/MIN）、前缀匹配、排序，全都依赖“下一个元素在哪”这个信息。

哈希表这三个要求一个都满足不了。数据库需要的是一种**为磁盘而生**的有序结构。它叫 B+ 树。

### 2. B+ 树长什么样

B+ 树是多叉的有序树。直接上存放学生数据的例子（以 id 为索引键，示意结构，节点数做了压缩）：

```text
                          ┌─────────────────┐
                          │  [ 30, 60 ]      │   <- 根节点（非叶子）
                          └───┬─────┬─────┬─┘
              ┌───────────────┘     │     └───────────────┐
              ▼                     ▼                     ▼
      ┌───────────────┐     ┌───────────────┐     ┌───────────────┐
      │  [ 10, 20 ]    │     │  [ 40, 50 ]    │     │  [ 70, 80 ]    │  <- 中间节点
      └───┬────┬────┬─┘     └───┬────┬────┬─┘     └───┬────┬────┬─┘
          ▼    ▼    ▼           ▼    ▼    ▼           ▼    ▼    ▼
        ┌────┬────┬────┐     ┌────┬────┬────┐     ┌────┬────┬────┐
        │1..10│11..20│  ...  │31..40│41..50│      │61..70│71..80│ ...│  <- 叶子节点
        └────┴────┴────┘     └────┴────┴────┘     └────┴────┴────┘
              │                   │                    │
              └───────────────────┼────────────────────┘
                      叶子节点之间用双向链表串联
```

它有几条铁律，每一条都直指磁盘：

- **叶子节点存全部数据，且从小到大有序**，叶子之间用链表串起来；
- **非叶子节点不存数据，只存键和指向儿子的指针**，作用纯粹是“导航”：键 k 下面的子树，存的都是小于 k 的（或介于两个键之间的）数据；
- **每个节点就是磁盘上的一页（16KB）**，节点里的键填得越满，树越矮——这是它和二叉树最大的区别。

### 3. B+ 树为什么快：一次磁盘 IO 一个节点

在 B+ 树里查 id = 45：

```text
[ 30, 60 ]  45 落在 30 和 60 之间 → 走中间分支        （IO 1：读根节点那一页）
[ 40, 50 ]  45 落在 40 和 50 之间 → 走第二个分支      （IO 2：读中间节点那一页）
[ 41..50 ]  在叶子内有序数据里找到 45                  （IO 3：读叶子节点那一页）
```

三次磁盘 IO（根节点和热节点大概率已在缓冲池里，实际更少），定位完成。关键在于树有多矮。每个节点一页 16KB，假设每个键加指针占 16 字节，一页能容纳约 1000 个导航项——也就是每个节点可以有一千个分叉：

```text
1000 个分叉，3 层的 B+ 树能容纳：1000 × 1000 × 1000 = 10 亿行
10 亿行数据，一次查找 = 3 次节点访问 = 约 3 次磁盘 IO
```

对比一下：二叉搜索树存 10 亿行，高度约 30 层，最坏 30 次随机磁盘 IO；哈希表虽然快但没有范围查询。**B+ 树把“树的层数”和“磁盘 IO 次数”划上等号，然后用一千个分叉把层数压到个位数**——这就是“为磁盘而生”的全部含义。这也解释了它为什么叫“多叉”：不是设计美学，是磁盘按页读写的物理现实逼出来的。

现实世界的数字更保守也更有说服力：真实的索引键更胖（比如 `VARCHAR(50)` 的名字），一页大约容纳几百个分叉，于是一张**千万行级别的表，B+ 树大约 3～4 层**——这正是大量真实 MySQL 表“千万行、毫秒级主键查询”的底层原因。一句话总结索引的量级直觉：**三层 B+ 树 ≈ 千万行 ≈ 三次 IO**。

范围查询同样是它的主场。查 `id BETWEEN 41 AND 45`：先按单个值的方式定位到 41 所在的叶子，然后沿着叶子间的链表向右走，直到超过 45 停下——顺序就在链表里，范围扫描不需要回到树上重新查找。`ORDER BY id`、`MAX(id)`（最右叶子最后一个元素）同理，全都吃“叶子有序”这一口饭。

### 4. 回到那句 LIKE

现在可以回收第三部分埋的伏笔了。比较这两个查询：

```sql
SELECT * FROM students WHERE name LIKE '小%';   -- 可以用 name 的索引
SELECT * FROM students WHERE name LIKE '%明';   -- 不能用
```

B+ 树的查找从根开始，每一步都在用“大小关系”选分支——'小%' 的前缀确定，就能定位到“以小开头的名字”在树上连续的那一段，本质上是范围查询。而 '%明' 只约束了结尾：以任何字开头的数据都可能命中，在树上不连续，索引帮不上忙，只能全表扫描。

由此得到一个工程直觉：**索引能加速的查询模式，取决于这棵树上“数据连续”的方向**。等值和前缀确定的查询快，中间夹着函数运算的（`WHERE UPPER(name) = 'XIAOMING'`）、前缀不确定的，都会让索引失效。

### 5. 索引的代价与使用纪律

主键自带一棵 B+ 树（InnoDB 的数据就存在主键的叶子节点上，这棵树叫聚簇索引）。非主键列需要单独建索引：

```sql
CREATE INDEX idx_students_age ON students(age);
```

但索引不是免费的，三笔账摆在这里：

- **空间**：每棵 B+ 树都是数据的一份有序副本，索引越多，磁盘占用越大；
- **写放大**：`INSERT` 一行，不止写数据页，这表上每棵索引树都要插入对应条目。索引加速了读，拖慢了写——读和写之间的取舍，是存储系统里永恒的主题；
- **优化器可能不用**：选择性差的列（比如性别，只有两个取值），走索引回表反而更慢，优化器会放弃它。给“低选择性”列建索引往往是白花空间。

使用纪律，现阶段记四条：

1. 主键必须建，InnoDB 要求每张表有主键——没有显式主键它会偷偷找一个唯一列或隐式生成一个；
2. 高频出现在 WHERE、JOIN ON、ORDER BY 里的列才值得建索引；
3. 索引列上别套函数和运算，会直接失效；
4. `SELECT *` 改成只取需要的列——如果这些列全在索引里，连“回表读数据页”都省了（覆盖索引），这是少查几列的隐藏红利。

### 6. 三种结构，一个问题

到这里可以把本部分开头的三个结构放在一起看：

```text
数组/链表    线性查找        最坏比较 N 次
map          哈希表          平均 O(1)，代价：无序
B+ 树索引     多叉有序树       O(树高)≈3 次磁盘 IO，天然有序
```

三个结构回答的是同一个问题——“怎么找到我要的数据”，而答案被存储介质塑造：内存里的哈希表可以任性重排，磁盘上的 B+ 树必须迁就“按页读写”的现实。数据结构从来不是凭空设计的，它是硬件物理规律在软件里的投影。以后你见到其他存储结构（LSM 树、跳表……）时，都可以用同一个问题去拷问它们：**你在迁就哪种介质的哪种物理特性？**

## 第六部分：事务与日志——数据为什么不会丢

最后一部分回答两个更底层的问题：并发写会不会出错，以及断电了数据为什么不会丢。

### 1. 并发写的问题，数据库同样要面对

想象两个用户同时买最后一件库存商品。你的 Go 服务里可能有两个 goroutine 同时执行“查库存 → 判断 → 扣减 → 创建订单”。查和扣之间如果没有任何保护，两个 goroutine 都会看到“还有 1 件”，都下单——超卖了。

在 Go 里解决这个问题靠 `sync.Mutex` 或 channel：一段逻辑要么整体执行完、要么别开始，中间不许任何人插手。数据库面对的是同一个问题，只是战场更大——不只是同一进程内的 goroutine，而是几十个客户端进程同时发来的读写请求。数据库给出的答案叫**事务**。

### 2. 事务：要么全做，要么全不做

事务（transaction）是把一组 SQL 打包成原子单位的机制：

```sql
START TRANSACTION;        -- 开启事务

UPDATE products SET stock = stock - 1 WHERE id = 1001;
INSERT INTO orders (product_id, user_id) VALUES (1001, 42);

COMMIT;                   -- 全部成功，落盘生效
-- 或者出错时：
ROLLBACK;                 -- 撤销本事务内的一切修改
```

COMMIT 之前，这两条 SQL 的效果对其他连接不可见、对磁盘“不负责任”；ROLLBACK 可以让它们像从未发生过。于是“扣库存 + 创建订单”要么都成功，要么都没有——超卖的窗口被事务关上了。

事务的标准承诺是 ACID 四个词：

| 字母 | 含义 | 一句话解释 |
|---|---|---|
| A | Atomicity 原子性 | 一组操作要么全做要么全不做，不存在做一半 |
| C | Consistency 一致性 | 事务前后，数据必须满足所有约束（库存不为负等） |
| I | Isolation 隔离性 | 并发的事务互相看不见对方的中间状态 |
| D | Durability 持久性 | COMMIT 之后的数据，断电也不会丢 |

原子性和隔离性是理解的重点，下面两节分别拆开。一致性更多是结果——A、I、D 加上你设计的约束共同保证的最终状态；持久性的实现机制（WAL）在日志一节讲。

### 3. 隔离性：锁的老朋友

两个事务并发执行时会发生什么？经典问题是“丢失更新”：

```text
事务 A：读余额 100 ────────── 写入 90（扣 10）
                              │
事务 B：        读余额 100 ────────── 写入 80（扣 20）

结果：两次扣款只生效了一次 —— A 的写入被 B 覆盖，10 块钱凭空消失
```

这就是共享变量并发读写的经典问题：两个执行流读写同一个共享变量，中间的判断基于过期的旧值。Go 里你用 Mutex 划出临界区，数据库用锁做同样的事——事务 A 更新某行时对这行加锁，事务 B 想更新同一行就得等 A 提交或回滚后才能继续，A 读到 B 写了一半的中间状态这种事，被隔离级别挡在门外。

数据库在这个基础上走得更远：它给了“锁多严”一个可调的旋钮——隔离级别。隔离越严，并发性能越差，于是标准里定义了几档从“基本不隔离”到“完全串行”的级别，让业务按需选择。详细的级别名和各自的怪异现象（脏读、不可重复读、幻读）留给你们在遇到问题时查阅——现阶段记住结论即可：**InnoDB 的默认隔离级别（可重复读）已经足够好，绝大多数业务不需要动它**。

并发在数据库里是一等公民，这点和 Go 的哲学不谋而合：不回避并发，而是提供原语（锁、事务、隔离级别）把并发变成可控的东西。

### 4. WAL：先写日志，再刷数据

最后是持久性，也是本课最漂亮的一处设计。

现在问一个刁钻的问题：COMMIT 的时候，MySQL 必须把改过的数据页从内存刷到磁盘吗？按直觉该刷——不刷怎么叫“持久”？但注意两点：其一，一个 UPDATE 可能只改了一页里的几个字节，却要把整页 16KB 写回磁盘；其二，COMMIT 高频发生，如果每次都等真实磁盘写入，数据库的写入吞吐会被磁盘拖死。

InnoDB 的答案叫 WAL——Write-Ahead Logging，预写日志。它把“改了什么”和“数据本身”分成两条路径：

```text
传统做法（慢）：
  COMMIT ──> 把改过的数据页（16KB×N）刷到磁盘 ──> 返回成功

WAL 做法（快）：
  修改数据 ──> 1. 数据页先在内存（缓冲池）里改，暂时不落盘
           ──> 2. 把"第几页第几行从 A 改成 B"这样一条记录
                 顺序追加写入磁盘上的 redo log 文件（几百字节）
           ──> 3. redo log 落盘成功 = COMMIT 成功
           ──> 4. 脏页由后台线程在空闲时慢慢刷回磁盘
```

 redo log 快在哪？两个词：**顺序**和**小**。磁盘最怕随机 IO、最爱顺序 IO——机械盘的磁头不用来回跑，SSD 的顺序写也远快于随机写；而日志条目只有“哪一页改了什么”几百字节，远小于整页数据。用一次顺序的小写，替代一次随机的整页写，这笔账在磁盘的世界里稳赚。

崩溃恢复是 WAL 的另一半收益。断电重启后：

```text
1. 检查 redo log：最后一笔成功落盘的事务记到哪了
2. 数据页可能还没刷盘（停在旧状态）→ 重放（replay）日志，把改动重新做一遍
3. 未 COMMIT 的事务日志直接丢弃 → 它们的修改从未生效
```

于是出现了那个初看反直觉、细想必然的结果：**磁盘上的数据文件可以是“旧的”，只要日志是新的，正确状态就能随时重演出来**。先记日志再改数据——这就是 Write-Ahead 的含义，也是“写一半崩溃无法恢复”这个文件方案死穴的解药。第三部分说数据库“崩了能自动恢复”，靠的就是它。

你可能还听过 binlog（归档日志，MySQL 服务层的日志，用于主从复制和数据备份）。redo log 和 binlog 的分工、两阶段提交这些细节，等你们真正运维一个 MySQL 时再深究不迟。

## 总结

本课沿着“一句 SELECT 敲下回车之后发生了什么”这条主线，讲了六件事：

1. **为什么需要数据库**（第一部分）：内存易失，自己用文件存数据有格式、查询、并发、崩溃四个死穴，所以需要一个专职管理数据的独立进程；
2. **关系模型**（第二部分）：用二维表组织数据，表与表之间靠编号关联，三张表就能表达学生和课程的一对多关系；
3. **SQL**（第三部分）：DDL 管表结构，DML 管表里的数据，DQL 查询——一门声明式的、只写“要什么”的语言；
4. **执行流程**（第四部分）：SQL 文本要经过解析、优化、执行三步，优化器会基于数据分布选一条成本最低的路径；
5. **索引**（第五部分）：B+ 树为磁盘而生，把千万行数据的查找压到三四次磁盘 IO；它加速读、拖慢写，要用在刀刃上；
6. **事务与日志**（第六部分）：用原子性解决并发写冲突，用 WAL 让断电后的恢复成为可能。

其中 2、3、5、6 不是 MySQL 一家的专利，而是所有主流关系型数据库共享的通用知识——学会了它们，你就有了一把打开所有关系型数据库的钥匙。

把这节课的三句话带走：

> 数据不在内存里，在磁盘上；一切设计都迁就磁盘的物理特性。
>
> SQL 是声明式：你只说要什么，怎么找由数据库决定——所以它才能找得又快又对。
>
> 先写日志再改数据：顺序小写换随机大写，崩溃后可以重放。
